# Работа над JudeOS / Judo Pride

- В начале новой задачи прочитай этот файл и проверь git status и ветку. В новой сессии прочитай CONTRIBUTING.md и краткий planning/STATUS.md. planning/README.md используй как указатель; остальные документы выбирай по задаче согласно правилам ниже.
- planning/DECISIONS.md сохраняет подтверждённые требования и происхождение позднего baseline. Текущие рабочие документы — planning/ARCHITECTURE.md 0.4 и planning/MVP-DEVELOPMENT-PLAN.md 1.1; модель и сценарии согласованы с ними. Не превращай технические рекомендации или отсутствующие D26–D63 в новые подтверждения пользователя. planning/archive содержит исторические источники, не параллельную спецификацию.
- Подтверждённый backend — Go, база — PostgreSQL. Первый выпуск предназначен для сотрудников, интерфейс mobile-first/PWA. Telegram — основной канал уведомлений. Протокол iPay описан в docs/integrations/ipay/README.md; его актуальность и профиль подключения клуба ещё не установлены.
- Разрабатывай на синтетических данных. Не коммить реальные сведения детей, родителей, платежей, медицинские документы, ключи и .env с секретами.
- Перед редактированием проверяй git status и существующие инструкции репозитория. Не перезаписывай чужие изменения. Одна задача — одна ветка; интеграция через PR.
- Меняй документацию вместе с поведением. Новые подтверждённые требования добавляй в DECISIONS.md с источником; технический выбор фиксируй отдельным ADR с причинами и статусом.
- Перед завершением выполни проверки, подходящие к изменению, и сообщи, что проверено и что не удалось проверить.
- Обновляй planning/STATUS.md при смене этапа, существенном блокере или передаче незавершённой работы: результат, ветка/PR, проверки, открытые вопросы и следующий шаг. Не включай секреты или персональные данные; не превращай файл в журнал каждой задачи.

## Облачная и совместная работа

- Каждый разработчик использует свой аккаунт ChatGPT/Codex и изолированное облачное окружение JudeOS. История чатов и рассуждения агентов автоматически не синхронизируются; общий контекст передаётся через документы, Issues, коммиты и PR в GitHub.
- В облачной среде найди и используй существующий checkout. Проверь git status, текущую ветку и HEAD; сохрани существующие изменения. Дополнительный worktree создавай только по явному запросу. Не предполагай доступ к окружению коллеги; отдельное окружение для того же репозитория подходит для совместной работы.
- Первое ознакомление выполняй в режиме чтения: изучи документы и проверь среду и GitHub-доступ. Реализацию начинай только по указанной или согласованной с пользователем задаче.
- Задачи ведём в GitHub Issues: у каждой один ответственный, понятная цель, границы и критерии готовности. Перед началом проверь Issue, её обсуждение, связанные ветки и PR, чтобы не дублировать работу коллеги. При неясной занятости сначала согласуй ответственность.
- Планируем канбан GitHub Projects: Backlog → Ready → In progress → Review → Done. Перед использованием проверь наличие доски, автоматизаций и прав; включённая функция Projects сама по себе не подтверждает наличие доски.
- Одна задача — одна ветка, например feat/12-attendance-api. Интеграция через PR и ревью коллеги. Связывай PR с Issue; для закрытия после merge используй Closes #12. Не пушь напрямую в main и не используй force-push.
- Не начинай зависимую работу на основании несогласованного контракта. Сначала согласуй и зафиксируй общий API или модель данных в репозитории; технические предложения отделяй от подтверждённых требований.
- После merge обнови свой checkout основной ветки; коллеге также нужно получить актуальную main. Уже запущенные облачные задачи автоматически не обновляются. Перед обновлением сохрани незавершённую работу.
- GitHub-аутентификацию проверяй операцией чтения, прежде чем просить дополнительный доступ. Учитывай, что GitHub-коннектор и CLI могут иметь разные возможности. Не проси присылать токены или секреты в чат.

## Выборочное чтение контекста

- planning/README.md — карта текущих документов, включая MVP-DEVELOPMENT-PLAN.md и действующие ADR. Не читай все Markdown-файлы перед каждым сообщением. Используй уже прочитанный контекст; перечитывай при изменении файлов, смене задачи, получении изменений коллеги или нехватке контекста.
- Начинай с цели и критериев готовности запроса или Issue. Связанные Issues и PR читай через доступные GitHub-инструменты: git pull не загружает их обсуждения.
- Через rg находи нужные файлы и разделы; читай связанные требования, код и контракты. Расширяй чтение при неизвестных зависимостях; экономия токенов не оправдывает догадки.
- Бизнес-правила: соответствующие решения DECISIONS.md. Выбор этапа: NEXT-STEPS.md. Данные: DATA-MODEL.md и существующие миграции. Архитектура: нужные разделы ARCHITECTURE.md и ADR. Интерфейс: правила дизайна выше.
- RESEARCH.md, OWNER-INTERVIEW.md и ACTIONS.md — справочные материалы; читай их при необходимости проверки источника, а не по умолчанию.
- Перед реализацией получай актуальные изменения безопасным способом, учитывая незакоммиченную работу. Не выполняй слепой pull в чужую ветку. Изменения общего API и модели данных согласовывай через Issue/PR.

## Сохранение контекста

- Храни актуальные описания вместо расшифровок чатов. Не дублируй решения: используй ссылки. Историю изменений сохраняют Git и PR.
- Код и проверки — в исходниках; изменения базы — в миграциях и при необходимости описании модели; API — в контракте; запуск — в README или инструкции эксплуатации.
- Подтверждённые требования — в DECISIONS.md с источником. Существенные технические решения — в отдельных ADR в planning/adr/: статус (предложено/принято/заменено), контекст, выбор, альтернативы и последствия. Не обозначай предложение агента принятым без согласования; смена утверждённого стека требует согласования.
- Результат задачи, проверки и оставшуюся работу описывай в PR и связанной Issue. Не добавляй отчёт о каждой задаче в AGENTS.md.
- Устаревшие описания обновляй; завершённые планы при необходимости архивируй со ссылкой; у заменённых ADR указывай новое решение.
- При авторизованной передаче работы сохрани изменения в коммите, отправь рабочую ветку и открой PR. Не объединяй PR автоматически. Если commit, push или PR не выполнены, явно сообщи, что осталось локальным и недоступным коллеге.
