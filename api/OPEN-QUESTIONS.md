# Открытые решения первого среза

Статус: реестр пробелов для [#16](https://github.com/StarMadeGalaxy/JudeOS/issues/16), не подтверждённые требования. Ответственный ниже — нужная роль принимающего решение, а не назначенный assignee: конкретные имена фиксируются в соответствующей Issue при взятии. D26–D63 зарезервированы для настоящих первичных источников.

| Вопрос / источник | Рабочее предложение | Кто принимает / где | Что блокирует |
|---|---|---|---|
| Wire пути, DTO, ошибки, CSRF, версии/idempotency — архитектура §§3–6, #16 | Семь операций OpenAPI; консервативный scope текущего coach, атомарные ответы/история | Два разработчика, PR по #16 / ADR 0006 | Зависимые #19/#23 до согласования и merge |
| Минимальные поля D54 — план §6; первичный список отсутствует | Только ID/имя/участие в roster; контакт/допуск добавить с отдельными правами | Владелец/менеджер и разработчики, #26 | Реальный реестр/расширенный журнал S1 |
| Административное закрытие, бывший тренер, исторический scope — модель/план §6 | Не давать неявные права manager/admin; текущий coach может исправить closed по baseline | Владелец/менеджер и разработчики, #26 перед #31/#33 | Соответствующие команды/исторические контакты |
| Кто последний владелец и как передать полномочия — архитектура §5 | Последний active administrator защищён lock/SQL trigger; сначала пригласить и активировать второго. ADR 0010 предложен в #21 | Владелец клуба и access-разработчик, #21 | Административный отзыв/управление ролями |
| Логин, приглашения/reset, хеширование, TTL, rate limit — S0.4/#21 | Реализованы preauth 10m/session 8h/invite 24h/reset 30m, Argon2id и DB rate limit: docs/access, ADR 0010; review #21 подтверждает технический выбор | Два разработчика, #21 | Приёмка #21 и rollout принятого schema 4 release |
| Срок OperationResult/ID, восстановления — DATA-MODEL, S4/#52 | В синтетическом каркасе не очищать результаты; production TTL/tombstone и recovery согласовать до включения | Разработчики и ответственный эксплуатации, #18/#52 | Реальные сроки хранения и replay после очистки/restore; офлайн |
| Обработка «болел», допуска/контактов, аудит, устройства/копии — S0.2/#18 | Только синтетические данные до условий и назначенного ответственного | Владелец и специалист по данным/эксплуатации, #18 | Узкий реальный пилот #37 |
| Таблицы, договорный профиль iPay/ID/подпись — #17, разбор PDF | PDF описывает on-line XML, не доказывает актуальность или формат реестра | Владелец/менеджер, поставщик iPay и разработчик, #17 | Настоящий адаптер #41/перенос данных; не синтетический журнал |
| Четыре отчёта D61 отсутствуют — план §6 | Проверяемые образцы/формулы отдельно; не восстанавливать D61 по догадке | Владелец/менеджер и разработчики, #38 | Финансовые отчёты/общая приёмка S2/S5 |
| Telegram: получатели, исправления, unknown — план §6 | Не отправлять Attendance; политика двух типов событий отдельно | Владелец/менеджер и разработчики, #46 | Активация доставки S3 |
| Freshness, сроки команд/совместимость и epoch — план §6/S4 | Не вводить offline-контекст в онлайн PUT; отдельный контракт snapshots/команд | Разработчики, #52 | S4; не ближайший онлайн-прототип |
| RPO/RTO, хранение/удаление и реальное размещение — план §5, #18/#24 | Определить и измерить до реального пилота; прежние числа — предложение | Владелец и назначенный ответственный эксплуатации | Production/pilot; не схематический контракт |

При получении ответа обновляется действующий документ и эта строка со ссылкой на источник; подтверждение пользователя сохраняется в DECISIONS, техническое согласование — в ADR. Статус выполнения и конкретные исполнители находятся в Issues/PR, история чата сюда не переносится.
