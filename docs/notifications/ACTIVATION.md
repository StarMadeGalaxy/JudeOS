Все условия означают **приёмку и интеграцию результата**, а не только open PR или зелёную схему. Прямая зависимость документального #46 — принятый #26/merged PR102. Финансовый PR112 не merged; его документы изучены как проект, а final review/merge проверяются перед интеграцией. Финансовые тексты и семантика изменений повторно сверяются с принятым #38 до #50. Переносы могут включаться раньше финансов; не требуется ждать S2 для #49.

Конкретные даты/версии нельзя выдумывать. Владелец в T46-03 согласовал тексты и сохранение событий выключенными; строка фиксирует этот источник, но `activated_at` и `activation_version` остаются неназначенными. Критерий фактической даты/версии остаётся условием будущего включения. Синтетическая дата в EXAMPLES не переносится в этот реестр.

Предлагаемый обязательный акт активации каждого типа содержит клуб/контур, точное UTC/RFC3339 время (для людей также Europe/Minsk), activation_version, template/policy_version, источник решения владельца, ответственного manager/оператора, ссылки на merged PR и приёмку, проверенный ручной fallback. Для реального контура отдельно #18/#24; synthetic не разрешает production. Акт хранится в защищённой конфигурации/аудите будущей реализации; здесь нет схемы БД или CLI.

Граница выбирается сервером: подтверждённая бизнес-команда после записанной активации и версии порождает событие атомарно с изменением. Импорт исторических денежных фактов не должен превращаться в рассылку старой истории из-за сегодняшнего recorded_at; различие исторической загрузки и нового распределения подтвердить перед #50. Старые операции/события не достраиваются автоматически задним числом. Повтор операции с тем же результатом не создаёт новое событие. Уже существовавшее занятие, которое после активации действительно перенесли, может породить новую сводку; старый перенос до границы — нет.

## До активации: подтверждённая ответственность и предлагаемые детали

1. Manager разрешённого клуба отвечает за связь; administrator может назначить замещающего сотрудника с теми же разрешениями. Отсутствие ответственного блокирует включение.
2. Перенос/отмена: перечитать актуальное занятие, roster и разрешённый контакт; связаться через существующий проверенный канал. Не копировать общий roster в семейный чат. Если контакт не подтверждён или отозван — сначала разбор, без раскрытия ребёнка.
3. Финансы: работать в действующем процессе сверки. Подтвердить поступление и распределение, затем при необходимости сообщить только разрешённую сводку через проверенный контакт. Несопоставленная строка/unknown источника не объявляется полученной поддержкой.
4. Фиксировать минимум: клуб, внутренний объект/версия, Person, время, ответственный, канал, исход `связались / не удалось / нужен разбор`, без тела сообщения, телефона, chat_id, сырого платежа или медицинских причин в общем журнале. Хранилище, права и срок этой отметки требуют #18/#24; в репозиторий не попадают реальные записи.
5. Объяснить, что автоматическая доставка ещё не включена. Само включение не рассылает накопленные изменения. Нет обещания будущей компенсационной рассылки всей истории.

## Пауза и возобновление

Пауза запрещает новые внешние попытки, но сохраняет ожидающие задания; после уже выполненной отправки её эффект не откатывается. Предложено фиксировать тип/клуб/причину-код/время/ответственного без тела и PII. При активированном типе исходные изменения во время паузы сохраняются вместе с событиями по будущему атомарному контракту; пауза не равна первому включению.

Manager продолжает ручной процесс. Отметка о состоявшейся ручной связи направляет соответствующее ожидающее уведомление на разбор, чтобы возобновление не повторило его автоматически. Простая отметка «пытались связаться» не доказывает получение. Семантика terminal/manual-suppressed и идемпотентность ручного решения будут согласованы в #48; здесь новых статусов DTO нет.

Перед возобновлением ответственный проверяет: текущие binding/GuardianLink и права, клуб, roster, последнюю бизнес-версию, ручные контакты, границу активации и флаг. Устаревший перенос не отправляется; ожидающая версия исправления заменяется актуальной. Unknown/blocked не массово retry. Если невозможно доказать актуальность или права — ручной разбор/запрет. Включение канала не отменяет отдельную паузу типа или клуба.

## Матрица исходов и безопасного повтора

| Исход | Автоматическое действие | Ручное действие / новая проверка |
|---|---|---|
| Нет попытки, событие актуально и разрешено | Будущий #48 может начать первую попытку после активации | При pause — продолжение вручную |
| Определённый временный отказ до приёма, retry_after | Ограниченный повтор; соблюдать retry_after, новые права/версия перед каждой попыткой | Числа попыток/backoff/deadline устанавливаются и проверяются #48 до включения |
| message_id получен | Принято Telegram; повтор этого job запрещён | Прочтение неизвестно; новое реальное изменение — новая версия |
| Таймаут после возможного приёма, потерян ответ / lease | Unknown, **нет автоматического повтора F** | Manager проверяет исход по доступным достоверным свидетельствам; отсутствие message_id не доказывает неотправку |
| Unknown для S | По T46-02 также ручной разбор | Manager при необходимости явно повторяет только актуальную сводку, предупреждая о возможном дубле |
| Blocked / недоступный чат | Остановить попытки; права не переносить на другой chat_id | Проверка через существующий контакт, новая подтверждённая привязка в #47; возобновление не автоматическое |
| Отозванный/истёкший доступ, чужой клуб, непроверенный получатель | Не отправлять, не искать fallback по семье | Зафиксировать безопасный исход без запрещённых данных; повтор после восстановления не безусловен |
| Устаревшая версия / занятие уже закончилось | Не посылать старую версию | Проверить актуальный факт и необходимость новой сводки; срок свежести утверждается до #49/#50 |

Для ручного повторения F после unknown требуются явное решение manager, текущие подтверждённые деньги/распределения, разрешённая проекция и проверка, что сводка не создаёт ложного нового поступления. Для S — актуальное состояние занятия/roster. В обоих случаях сохраняется связь с исходной попыткой/версией и добавляется «Повтор актуальной сводки». Это не гарантирует отсутствие дубля; принятый message_id не используется как повод для автоматического resend. Спорный финансовый факт остаётся на финансовом разборе, без Telegram-сводки.

После restore отправка остаётся выключенной вне восстанавливаемой БД; восстановленные токены/права перепроверяются по независимому источнику. Окно возможной уже выполненной внешней доставки переводится на ручной разбор без массового retry. Runbook #24/#48 дополняется фактической реализацией и тестами, этот документ не выполняет восстановление.
