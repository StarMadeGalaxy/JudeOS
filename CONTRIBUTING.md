# Совместная разработка JudeOS

Согласованный процесс для двух разработчиков: общий репозиторий, GitHub Issues, короткие ветки от основной ветки, Pull Request и ревью второго разработчика. Прямой push в main и force-push не использовать. 8 октября 2026 пользователь включил защиту main; branch API подтвердил protected=true и четыре обязательных CI contexts. Настройки и границы read-back описаны в [docs/operations/releases.md](docs/operations/releases.md#защита-main-после-появления-checks), текущая передача — в [planning/STATUS.md](planning/STATUS.md).

## Варианты

| Вариант | Когда выбирать | Как работать |
|---|---|---|
| Общий репозиторий + ветки + PR | Два доверенных разработчика с правом записи; рекомендуемый старт | Владелец приглашает коллегу в Collaborators; каждый работает в своей ветке, другой проверяет PR |
| Fork + PR | Нет права записи либо нужен независимый репозиторий | У каждого свой fork; origin указывает на fork, upstream на StarMadeGalaxy/JudeOS; изменения идут через PR |
| Git worktree поверх любого варианта | Несколько одновременных задач Codex на одном компьютере | Отдельная ветка и каталог на каждую задачу; в облачной среде дополнительный worktree создаётся только по явному запросу |

## Общий контекст для Codex

Каждый разработчик использует свой аккаунт ChatGPT/Codex и изолированное облачное окружение JudeOS. Git хранит документы и код, но не переносит автоматически историю чатов, рассуждения агентов или память Codex. Нельзя предполагать доступ к окружению коллеги. Если общая конфигурация среды недоступна, отдельное окружение для того же репозитория подходит для работы.

В облачной среде используйте существующий checkout, без дополнительного клонирования; дополнительные worktree создавайте только по явному запросу. Перед работой проверьте git status, ветку и HEAD, сохраните существующие изменения. На другом компьютере без checkout клонируйте репозиторий и откройте его каталог как проект Codex.

Начальный запрос для новой сессии: «Следуй AGENTS.md: проверь git status, ветку, HEAD и прочитай краткий статус. Выбирай остальные документы по задаче. Если задача уже указана, сначала проверь занятость, назначь её текущему GitHub-пользователю и подтверди In progress в Project #1; лишь затем выполняй. При продолжении повторно проверь собственный claim. Если поручен выбор следующей задачи, следуй planning/ISSUE-HANDOFF.md: проверь актуальный backlog, последние закрытые задачи/merged PR и предложи один готовый свободный шаг; до резервирования не начинай предметную работу. Не превращай рекомендации в утверждённые требования».

Планирование находится в planning/, дизайн — в DESIGN.md и design-system/. Пакет документов интегрирован в main через [PR #1](https://github.com/StarMadeGalaxy/JudeOS/pull/1). Исторические ACTIONS.md и README.md описывают состояние на момент написания; актуальное состояние передачи отмечается в STATUS.md.

## Issues и канбан

У каждой Issue один ответственный, понятная цель, границы и критерии готовности. Перед началом проверьте назначение, обсуждение и связанные ветки/PR, чтобы не дублировать работу коллеги. Если ответственность неясна, сначала согласуйте её. Задача должна быть указана или согласована с пользователем до реализации; назначение и подтверждённый In progress обязательны до предметного анализа/работы по каждому запросу.

Пользователь выбрал [GitHub Project #1](https://github.com/users/StarMadeGalaxy/projects/1) со статусами Backlog → Ready → In progress → Review → Done. Его состав, настройки и автоматизации пока не прочитаны: текущая среда получает Forbidden при обращении к GitHub API. Issues опубликованы, применение milestones и добавление задач в Project отслеживает [Issue #8](https://github.com/StarMadeGalaxy/JudeOS/issues/8). Точная разбивка, условия статусов и воспроизводимая настройка — [planning/ISSUE-BACKLOG.md](planning/ISSUE-BACKLOG.md).

Оба разработчика равноценны как разработчики и project managers. Задачи заранее не назначаем: каждый выбирает свободную готовую задачу, проверяет занятость и назначает себя при старте; другой проводит ревью. Открытые зависимости или неподтверждённый внешний контракт не позволяют начать зависимую реализацию. Отложенные задачи после MVP остаются Backlog до подтверждения своего триггера.

## Выбор задач и передача между чатами

[Единый порядок и шаблон промпта](planning/ISSUE-HANDOFF.md) обязательны перед новой задачей и после подтверждённого завершения текущей Issue. Анализируем весь актуальный открытый backlog, последние закрытые Issues/merged PR команды и текущего разработчика; проверяем зависимости, занятость и реальные результаты. Выбираем один готовый свободный шаг, учитывая непрерывность работы без постоянного закрепления ролей. Передача не резервирует будущую Issue; новый чат повторяет проверку и подтверждает In progress.

Одна Issue — один чат. После подтверждения назовите чат `Issue #N — название`; после создания PR — `PR #M · Issue #N — название`. После проверки завершения текущей Issue один раз дайте следующий номер/ссылку, причину/условия и готовый самостоятельный промпт. Открытый PR, ревью, исправления и статусные ответы не запускают передачу. Если нет готовых задач, укажите блокер и условный шаг. Не создавайте новый чат автоматически без явного запроса.

## Рабочий цикл

1. Проверить или создать согласованную Issue, зависимости и живую занятость. Выполнить резервирование по разделу ниже: текущий GitHub-login → единственный assignee → карточка Project #1 In progress → read-back → claim-комментарий. Только после этого анализировать решение и выполнять задачу.
2. Сохранить существующие изменения, обновить основную ветку через git pull --ff-only и создать одну ветку для задачи: feat/<issue>-<name>, fix/<issue>-<name> или docs/<issue>-<name>.
3. Согласовать и зафиксировать API-контракт или модель данных в репозитории до зависимой работы над backend и frontend. Миграции координировать отдельно, чтобы не создавать одинаковые номера.
4. Выполнить задачу, обновить связанные документы, провести подходящие проверки.
5. Отправить ветку и открыть PR с результатом, проверками и связью с Issue: Closes #12 закрывает её после merge. Второй разработчик проверяет код и бизнес-сценарий; проверка Codex помогает ревью, но не заменяет договорённость команды.
6. После merge обоим разработчикам получить актуальную main в своих checkout. Уже запущенные облачные задачи автоматически не обновляются. Продолжение задачи в другом окружении требует commit и push рабочей ветки, затем fetch/checkout там.

Первый шаг — совместно согласовать модель данных и API по Issue #16; форматы #17 и условия реальных данных #18 можно исследовать параллельно. Затем свободные задачи каркаса #19 и прототипа #23 допускают работу вдвоём без постоянного закрепления frontend/backend за человеком. API и UI ближайшего среза используют один принятый контракт; финансовый адаптер ждёт фактических форматов iPay. Подробная последовательность — [planning/NEXT-STEPS.md](planning/NEXT-STEPS.md) и [backlog](planning/ISSUE-BACKLOG.md).

При конфликте DECISIONS.md или ADR сверить смысл вместе, не выбирать механически одну сторону. Важные результаты сохранять в GitHub: подтверждённые требования — в DECISIONS.md с источником, технические предложения — отдельно с причинами и статусом, результат задачи — в PR и Issue, общий этап и передача незавершённой работы — в STATUS.md. Не приписывать пользователю неподтверждённые решения.

Не редактировать одни и те же файлы из двух задач в одном checkout. На локальном компьютере для одновременных задач использовать отдельные worktree; в облаке использовать изолированные окружения, а дополнительный worktree — только по явному запросу.

Доступ к GitHub сначала проверять операцией чтения через существующую аутентификацию. Возможности коннектора и CLI проверять отдельно; не запрашивать токены или секреты в чате. Для разработки использовать только синтетические данные, без реальных платежей, медицинских документов и персональных сведений.

## Что передавать

После push передать ссылку на Issue и ветку/PR с результатом и проверками. При смене этапа, существенном блокере или передаче незавершённой работы обновить planning/STATUS.md по AGENTS.md. Проверенный репозиторий публичный; для общей работы через ветки требуется право записи. У аккаунта NikishGum оно подтверждено GitHub-коннектором, административных прав нет. Для закрытого репозитория владелец должен пригласить коллегу.

Архив JudeOS-onboarding.zip, упомянутый в историческом пакете передачи, не заменяет актуальный checkout. Чаты и внешняя память в GitHub автоматически не переносятся.

## Инструкция в настройках проекта Codex

Каждый разработчик добавляет у себя короткую инструкцию ниже. Полную копию AGENTS.md в настройки не переносите: общие правила обновляются через репозиторий.

> Источник правил и контекста проекта — репозиторий JudeOS. Перед работой прочитай корневой AGENTS.md и следуй применимым инструкциям. Выбирай документы по задаче согласно AGENTS.md; не перечитывай весь репозиторий на каждое сообщение. Получай актуальный контекст связанных Issues и PR. Обновляй затронутые документы, контракты и миграции; сохраняй решения и результаты по правилам AGENTS.md. При передаче работы сообщай состояние commit, push и PR. История чата не является единственным источником контекста.

Настройки Codex не синхронизируются через Git. После получения изменений коллеги агент перечитывает затронутый контекст. Обсуждения Issues/PR доступны через GitHub-инструменты, а не через git pull.

## Документация входит в Definition of Done

Backend использует Go + net/http + chi v5: [ADR 0004](planning/adr/0004-chi-and-api-documentation.md). Каждый PR обновляет относящиеся к изменению правила, модель/миграции, конфигурацию, интеграции, запуск и эксплуатацию. Неочевидные решения объясняются в ADR/комментариях; документация должна позволять другому разработчику сопровождать продукт.

Для HTTP-изменения обязательны OpenAPI, реестр endpoint’ов, примеры, права/ошибки и совместимость; удаление операции тоже обновляет документы. Ревью проверяет покрытие маршрутов и соответствие контракту, CI — его валидность и сборку клиента, Swagger UI — отображение. Полный порядок и поля: [docs/API-DOCUMENTATION.md](docs/API-DOCUMENTATION.md). Будущие операции описываются по срезам, а каждый реально существующий endpoint покрывается сразу.

## Резервирование задачи до начала работы

Это обязательный старт каждого запроса на выполнение, включая Web-агентов, документацию и исследование; не отложенное действие перед первым коммитом. Сначала разрешено лишь чтение, необходимое для определения порученного объёма и выбора карточки. Задачи выбирают свободно, но выбранная работа немедленно становится видимой коллегам.

- Прочитать актуальные Issues, assignees, Status существующего Project #1, обсуждения/claim-комментарии, связанные PR и зависимости. Не полагаться на старый чат/manifest/слово «свободна» в описании Issue. Незавершённый результат зависимости не позволяет начать зависимую реализацию.
- Получить login текущей аутентификации через API (`gh api user --jq .login` или эквивалентный коннектор). Назначение выполнять тем же проверенным аккаунтом пользователя. Git author, владелец репозитория и список прошлых исполнителей не определяют личность текущего исполнителя. Не использовать фиксированный login для всех агентов.
- Сразу перед изменением повторно прочитать занятость. Любой чужой assignee или активная работа означает остановку выбора этой Issue, даже если Status ещё Ready. In progress/Review без понятного assignee тоже требует выяснения. Не снимать назначение коллеги. Один login с другим активным чатом/веткой также считается занятой работой.
- Назначить себя единственным assignee, найти существующую карточку (при отсутствии добавить Issue в Project #1), перевести Status в In progress и проверить оба значения повторным чтением. Существующие IDs и варианты Status получать из API/UI; колонка Board должна использовать именно поле Status. Не создавать дубликат карточки.
- Добавить claim-комментарий после подтверждения: `Работает @<login>; chat/run=<идентификатор>; Issue #N; объём=<кратко>; ветка=<имя или ещё не создана>; Status=In progress подтверждён.` Уникальный run-ID нужен для различения агентов одного аккаунта. Если начальная запись не завершилась, комментарий прямо указывает частичный результат и блокер, без фразы об успешном резервировании.
- Перечитать assignees/Status/claim перед основной работой. Если возникло второе назначение/конкурирующий claim, остановиться и договориться об одном исполнителе; не решать конфликт снятием чужого assignee. Read-back снижает риск гонки, но последовательные GitHub-записи не дают атомарного lock.

При продолжении существующей работы каждый новый запрос проверяет тот же claim, assignee и статус. Не создаются дубликаты Issue/карточки/комментария; после Review возврат к правкам собственного PR явно переводит карточку в In progress. Если задача закрыта или передана, сначала проверить границы нового поручения и оформить новую Issue при необходимости. Резервировать только непосредственно выполняемые задачи, не все возможные будущие карточки.

**Недоступность GitHub/Projects — блокер старта:** нельзя начать основную работу, если assignee и In progress не подтверждены. Описать, какой шаг не выполнен, сохранить видимое частичное назначение, попросить исправить доступ или установить значения вручную. Если есть работающий альтернативный авторизованный канал, использовать его без повторного запроса разрешения. После ручного изменения проверить значения; когда чтение Projects недоступно, достаточно явного подтверждения пользователя или скриншота нужной карточки/исполнителя/статуса; агент записывает источник подтверждения и продолжает без повторного блокера API. Не заменять статус labels, комментариями или локальной документацией.

При готовом PR статус Review; для draft/активной доработки In progress; после merge/приёмки и выполнения критериев Done. Пауза сохраняет assignee/In progress с описанием блокера. Освобождение/передача требует явного сообщения, прекращения собственной работы и согласованного изменения assignee/Status. Автоматическая синхронизация backlog не резервирует задачи за агентами.

Инструкции находятся в корневом AGENTS.md и действуют на весь репозиторий для обоих разработчиков. В Codex Web каждый агент должен получить актуальную main; работающий чат со старым checkout требуется обновить и повторно прочитать инструкции до продолжения. Личные глобальные настройки аккаунта коллеги этим PR не изменяются.

## Компактный запрос ручного In progress

При недоступности Projects API до основной работы агент предоставляет прямую ссылку каждой выбранной Issue, её название, подтверждённый GitHub-login исполнителя, результат назначения и действие: добавить в Project #1 при отсутствии, установить assignee и In progress. Заканчивает блок вопросом «Исполнитель и In progress установлены?» и явно ждёт ответа. Пример сообщения и полный порядок — [AGENTS.md](AGENTS.md#первое-сообщение-при-ручном-резервировании).

«Да» в ответ на конкретный блок, однозначное «готово» или скриншот нужной карточки с assignee/Status подтверждают ручной шаг. Отсутствие ответа/«нет» не разрешают старт. Перед подтверждением разрешены только проверка занятости, выбор/создание Issue и доступное назначение; разработка, предметный анализ решения и редактирование документов ждут. Проверку API выполнить, если она доступна; отсутствие чтения Projects после ручного подтверждения не останавливает работу повторно. Известные конфликтующие назначения требуют разрешения независимо от ответа.

Повторный запрос в том же чате по той же работе не требует снова перемещать карточку при отсутствии изменений назначения/статуса/объёма. Несколько непосредственно выполняемых карточек перечисляются в одном блоке; подтверждение относится ко всему набору. При завершении агент аналогично показывает ссылку и ручное действие Review/Done, если не может обновить Status сам.
