# ADR 0004: chi и обязательная документация API

Дата: 7 октября 2026 года. Статус: **принят**. Источник: прямое поручение пользователя после сравнения роутеров — использовать Chi во всём стеке и документировать endpoint’ы для Swagger и поддержки продукта. Подтверждения: [DECISIONS.md](../DECISIONS.md), U2026-10-07-CHI-01 и U2026-10-07-DOCS-01. Issue: [#74](https://github.com/StarMadeGalaxy/JudeOS/issues/74).

## Контекст

Модульному Go API нужны общие и групповые middleware сессий, контекста клуба и прав. Приложение ещё не создано; миграции существующих обработчиков нет. Стандартный ServeMux с Go 1.22 поддерживает методы/параметры, но chi упрощает регистрацию групп и модулей без собственного фреймворкового контекста. Для дальнейшей поддержки недостаточно списка путей: нужен точный контракт запросов, ответов и прав.

## Решение

Использовать chi v5 поверх стандартного net/http, стандартные http.Handler/HandlerFunc и middleware. Chi остаётся в HTTP-слое; application services не зависят от роутера, предметные права и транзакции не заменяются проверкой группы маршрутов. Patch-версию/совместимость закрепить в S0. HEAD/OPTIONS, слеши/редиректы, 404/405 и Allow определить явно.

Вести contract-first OpenAPI 3.0.3 в api/openapi/openapi.yaml, краткий реестр api/ENDPOINTS.md, Swagger UI и генерируемый TS-клиент. Контракт ближайшего среза согласуется до зависимой реализации; каждый существующий endpoint документируется в том же PR. Покрытие включает REST, интеграции и служебные маршруты с явными исключениями для автоматических/статических обработчиков. Все существенные изменения продукта сопровождаются документацией. Поля, процедуры и проверки — [docs/API-DOCUMENTATION.md](../../docs/API-DOCUMENTATION.md).

## Альтернативы

ServeMux остаётся подходящим вариантом без внешних зависимостей, но требует собственной организации групп. Gorilla/mux полезен для сложных matchers, которых пока нет. Gin/Echo добавляют собственный контекст и больше фреймворковых решений; Fiber меняет HTTP-основу на fasthttp. Chi выбран ради композиции, а не обещания ускорения.

Markdown/комментарии без OpenAPI не дают Swagger UI готовую спецификацию. Генерация из аннотаций возможна, но исходный подход использует один контракт вместо двух источников истины; менять его следует отдельным решением.

## Последствия и проверка

Добавляется зависимость chi и работа по сопровождению контракта. CI должен валидировать OpenAPI, сравнивать маршруты chi и контракт, проверять запросы/ответы и сборку клиента. Swagger UI проверяется на отображение схем/примеров. Эти инструменты создаются в S0; данное решение не утверждает, что они уже работают. Другие технические рекомендации и границы MVP этим ADR не меняются.

Источники сравнения: [Go routing](https://go.dev/blog/routing-enhancements), [chi](https://github.com/go-chi/chi), [Alex Edwards](https://www.alexedwards.net/blog/which-go-router-should-i-use). Формат: [OpenAPI 3.0.3](https://spec.openapis.org/oas/v3.0.3), [Swagger UI](https://swagger.io/tools/swagger-ui/).
