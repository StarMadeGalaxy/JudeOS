## Что уже закреплено baseline

Ровно два типа: подтверждённое распределённое поступление и перенос/отмена занятия. Нет просьб о поддержке, уведомлений посещаемости, болезни, медицинских причин и сырого платёжного реестра. Изменение рекомендации или импорт ещё не подтверждённой строки не порождает финансовое сообщение.

Ссылка, /start, chat_id, имя плательщика и семья сами по себе не подтверждают получателя. Перед раскрытием данных нужны проверенные представительство и Telegram-получатель. Перед каждой попыткой проверяются **текущие** клуб, связь, область конкретных сведений, версия события, актуальность и флаг доставки. Отзыв/истечение немедленно запрещают новую отправку; уже отправленное нельзя обещать удалить из Telegram или с устройства.

Активация хранит отдельные дату/версию каждого события, история до границы не рассылается. Пауза сохраняет очередь, возобновление перепроверяет права и актуальность. message_id означает приём Telegram, не прочтение; внешняя exactly-once доставка не обещается. Финансовый unknown требует ручного разбора.

## Подтверждённая основа проверки и предлагаемые детали

Владелец [подтвердил T46-01](https://github.com/StarMadeGalaxy/JudeOS/issues/46#issuecomment-6095725343): каждого получателя проверяет manager/administrator через уже проверенный контакт; основной контакт не исключает остальных, семья/chat_id не дают прав. Порядок шагов, конкретный способ внешней проверки и техническая проекция ниже — предложение для #47/#48:

1. Manager/administrator разрешённого клуба проверяет Person и действующий GuardianLink через уже проверенный контакт; фиксирует основание/период по принятому реестру без копий документов в уведомлении.
2. До связи с Telegram этот же сотрудник подтверждает, что запрос принадлежит проверенному Person, через независимый существующий контакт. Данные ребёнка до подтверждения не выдаются. Совпадение телефона, пересланная ссылка и ранее успешная привязка другого клуба проверку не заменяют. Не установлен конкретный способ доказательства личности для реального пилота — он остаётся условием #18/#47.
3. Каждый подтверждённый представитель — отдельный получатель. Основной контакт используется для ручной связи, но не выдаёт больше прав и не исключает других представителей автоматически. При отсутствии основного контакта/неясном получателе сотрудник разбирает случай, не выбирает произвольного члена семьи.
4. Разрешённая область задаётся отдельно для ребёнка и вида информации. GuardianLink необходим, но не выдаёт автоматически все финансовые/расписные поля. Неизвестная область означает запрет. Сотрудничество/роль coach/manager/platform сами по себе не добавляют Telegram-получателя; служебные предупреждения сотруднику отделяются от этих двух шаблонов и требуют будущего согласования.
5. Непосредственно перед попыткой строится новая минимальная проекция. Все дети/суммы, недоступные получателю, исключаются **до** группировки и подсчёта итогов. Отзыв binding блокирует канал; отзыв только одного GuardianLink удаляет только его область, оставшиеся сведения требуют новой проекции. Восстановленный из копии доступ не считается актуальным без независимой проверки.

Общая семья никогда не расширяет права. Даже получателю обоих детей не нужны плательщик, bank/source IDs, общий остаток поступления, контакты или финансовые сведения другого клуба. Родительские кабинеты и чат не добавляются этим документом.
