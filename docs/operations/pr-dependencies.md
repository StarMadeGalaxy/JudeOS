# Зависимости PR и порядок интеграции

GitHub Actions запускает workflow по событиям репозитория и публикует результаты.
`PR dependency gate` вычисляет required check **PR dependencies** на текущем head
каждого открытого PR в main. Это условие порядка интеграции; оно не заменяет CI,
независимый Approve, ручную приёмку или актуальность ветки относительно main.

## Объявление зависимостей

В описании каждого PR оставьте ровно одну строку вне code block и HTML-комментариев:

```text
Merge after: none
```

или перечислите прямые зависимости в этом же репозитории:

```text
Merge after: #101, #105
```

Шаблон PR содержит этот блок. `none` означает отсутствие необходимых предшествующих
PR, а не готовность к merge. Объясните причины зависимостей рядом со строкой.
Указывать произвольный порядок создания PR нельзя. Общие файлы сами по себе
не доказывают зависимость; принятый контракт/результат другой задачи — доказывает.
Не зависеть от собственного настроечного PR для первоначального включения gate.

Проверка требует, чтобы все перечисленные номера были PR с `merged=true` и той
же base веткой main. Закрытая без merge задача/PR, Issue вместо PR, другая base,
недоступная зависимость, дубликат, self-dependency, отсутствующая/неправильная строка
не проходят. Циклическая группа остаётся заблокированной: сначала исправить
неверные зависимости, не обходить проверку. Максимум 25 прямых зависимостей.
При обновлении описания декларация пересчитывается; повторный push привязывает
новую проверку к новому head SHA.

## Где видеть очередь

Actions → **PR dependency gate** → последний завершённый run → **Summary** содержит
общую таблицу открытых PR, их зависимостей и причины блокировки. В каждом PR
Checks → **PR dependencies** показывает его результат. Таблица означает только
готовность зависимостей: у PR могут оставаться review/CI/acceptance blockers.

Workflow пересчитывает все открытые PR при opened/edited/synchronize/reopened,
смене draft, закрытии PR, push в main, ручном Run workflow. Сверка каждые 15 минут
страхует пропущенные события; GitHub может задерживать scheduled runs.
Запуски сериализованы и всегда читают текущее состояние, включая пагинацию.
Если данные PR меняются во время вычисления, результат failure до повторной сверки.

После каждого merge обновить затронутые ветки обычным merge из main, повторить
нужные проверки и ревью изменившейся части. После изменения зависимостей дождаться
нового завершённого run; изменение описания и обновление check асинхронны, поэтому
старый зелёный результат сразу после редактирования не подтверждает новую декларацию.
Gate проверяет заявленные зависимости, не выводит смысловые зависимости из кода.
Независимые зелёные PR можно принимать в любом порядке.

## Первое включение — отдельный обязательный этап

До merge workflow в main механизм **не активирован**. Этот настроечный PR проходит
существующие четыре required checks и обычное независимое ревью.

1. Принять/merge PR по #103. Не добавлять required context до появления workflow в main.
2. Заполнить декларации существующих открытых PR по их фактическим зависимостям.
   Отсутствующая строка намеренно блокируется; не назначать `none` автоматически.
3. Actions → PR dependency gate → Run workflow на main. Проверить Summary и результаты
   PR dependencies: на независимом PR success, на PR с открытой зависимостью failure.
   После merge зависимости проверить автоматическое обновление ожидающего PR.
4. Settings → Branches → protection rule для main → required status checks: добавить
   **PR dependencies** от GitHub Actions. Сохранить **Go**, **Web and contract**,
   **Migrations**, **Image and HTTPS**, strict/up-to-date, один независимый Approve,
   dismiss stale approvals, conversation resolution, запреты force/deletion и обхода.
   Требуется repository admin. Не делать job **Reconcile dependency checks** required:
   он относится к общему запуску, а не к head конкретного PR.
5. Перечитать настройки защиты API или получить явное подтверждение оператора.
   Проверить, что PR с открытой зависимостью нельзя объединить стандартным Merge.

Действующий baseline четырёх проверок — `main-protection.json`. Предлагаемый payload
после интеграции/проверки gate — `main-protection-pr-dependencies.json`; файл сам
по себе настройки GitHub не применяет. При недоступном API действовать через UI,
не считать включение выполненным по наличию файлов/зелёному unit test.

## Безопасность и отказ

`pull_request_target` получает contents/pull-requests read и checks write. Checkout
строго default branch, persist-credentials=false; PR head/описание не исполняются.
GitHub token передаётся через env, не пишется в отчёт. REST ошибки дают нейтральный
failure; недоступность API не превращается в success. Summary не включает чужие
описания/HTML/токены. Нет dispatch стороннего кода, автоматического merge, deploy,
изменений VPS или отдельного PAT. Ошибка общего workflow может оставить проверки
pending/устаревшими: проверить run и перезапустить, не принимать их как свежую сверку.

Тесты: `python3 -m unittest discover -s .github/scripts -p 'test_*.py'`.
Workflow выполняется только после интеграции trusted версии; его end-to-end проверка
и required-check read-back обязательны до закрытия #103.
