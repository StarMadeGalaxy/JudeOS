# Предложение контракта настройки занятия для #34

**Статус: proposed, ожидает явного согласования владельцем.** Это не описание существующего API. Ни одна новая команда/схема из этого документа не используется UI, пока предложение не принято. [Основной OpenAPI](../../../../api/openapi/openapi.yaml), runtime и принятый snapshot восьми операций остаются прежними.

Источник бизнес-правил: [дата/время, зал, роль, состояния и необязательная причина](https://github.com/StarMadeGalaxy/JudeOS/issues/34#issuecomment-6098111977); [administrator-only первоначальный выбор тренеров и отдельный отзыв доступа](https://github.com/StarMadeGalaxy/JudeOS/issues/34#issuecomment-6098369503). Владелец согласует предложение напрямую; [уведомление исполнителю #29 о границе](https://github.com/StarMadeGalaxy/JudeOS/issues/29#issuecomment-6098371967). Это продолжение #34 в PR116, не резервирование/реализация backend #30.

Машиночитаемый вариант и синтетические примеры: [отдельный proposed OpenAPI](contract/session-configuration.proposed.openapi.json); причины и альтернативы — [отдельный ADR со статусом proposed](SESSION-CONFIG-ADR.md). Его ссылки разрешаются в существующие схемы/параметры основного OpenAPI. Новые пути и request DTO ниже — предложение для согласования, не принятые endpoint. Технический предел reason500 совпадает с SetAttendanceRequest; он не объявляется ответом владельца о длине комментария.

## Операции

Все пути ниже имеют префикс `/api/v1/tenants/{tenant_id}`. Cookie session, текущий tenant/scope, CSRF/exact HTTPS Origin, no-store, request_id и существующая серверная проверка административной области сохраняются. Manager/coach-only не получают административную возможность от выбора учебной роли. Принятое распространение административных прав в сети не переопределяется этим предложением.

| Операция | Предлагаемый HTTP-контракт | Тело | Результат |
| --- | --- | --- | --- |
| rescheduleSession, новая | POST `/sessions/{session_id}/reschedule` | operation_id, base_version, starts_at, ends_at; необязательная reason | Существующий TrainingSession |
| cancelSession, новая | POST `/sessions/{session_id}/cancel` | operation_id, base_version; необязательная reason | Существующий TrainingSession со state=cancelled |
| setSessionCoaches, ревизия существующей | PUT `/sessions/{session_id}/coaches` | Существующий operation_id/base_version/coach_membership_ids; добавляется необязательная reason | Существующий SessionCoaches |
| createManualSession, ревизия существующей | POST `/sessions` | Существующий CreateManualSessionRequest без новых полей | Существующий результат операции |

Новые тела строгие: неизвестные поля запрещены; operation_id — UUID, base_version — положительная Session.version. Дата/время — UTC RFC3339 с Z, отображение и дата списка — Europe/Minsk. ends_at строго позже starts_at; venue/group/tenant/state/автор/история не принимаются из тела настройки. Отсутствие reason и пустая строка эквивалентны, null запрещён; пояснение сохраняется с историей изменения, не становится заметкой Attendance. Поля ответов/авторов/контактов не расширяются.

## Права и состояния

Administrator может изменить время или список тренеров и отменить Session только в planned/in_progress. Предлагаем проверять явное состояние Session; время само по себе не закрывает занятие и не создаёт новый переход состояний. Перенос сохраняет текущее состояние. closed/cancelled запрещают новую настройку времени, отмену и добавление/замену тренеров; восстановления отменённого занятия здесь нет.

При создании administrator выбирает coaches. Manager сохраняет создание ручного занятия с **пустым** coach_membership_ids, но не выбирает тренеров: непустой список от manager —403, без автоматического назначения GroupCoach. Пустые coaches уже допустимы действующим DTO. Назначение тренеров такому занятию отдельно выполняет administrator. Остальные поля, первоначальный roster и права создания не расширяются. Текущий backend #29 разрешает прежний выбор manager, поэтому эта ревизия ещё требует серверной реализации.

В closed/cancelled administrator может отдельно отозвать доступ: setSessionCoaches принимает только подмножество текущих membership_id. Уже снятое назначение не возвращается; новый ID запрещён. Сохраняются строки истории с серверным valid_until; новый список не меняет дату/время, отметки или состояние. Manager и coach-only не выполняют эту команду. Отзыв клубной роли продолжает немедленно прекращать доступ по принятому access-контракту.

listStaff и getSessionCoaches используются в своих прежних формах для выбора действующих coach и чтения текущих/исторических назначений; новые endpoint поиска сотрудников не добавляются. Права/tenant, действующий coach grant и текущие назначения перечитываются на сервере; UI не считается защитой.

## Версии, повтор и история

Новая настройка, отмена или изменение назначений проверяет base_version после текущих прав/ссылок/применимости. При реальном изменении Session.version увеличивается один раз; Attendance.version и прежние отметки сохраняются. Неизменные время/список тренеров — no-op без новой версии/строки изменения; пояснение само по себе не создаёт изменения расписания. Отмена сохраняет roster, unmarked, сделанные факты и историю; обычные правила cancelled посещаемости/отчётов остаются прежними.

Session ID и исходный ключ генерации сохраняются. Повтор генерации не создаёт занятие на прежнем месте и не воскрешает отмену. Настройка не изменяет Enrollment, GroupCoach, шаблон или другие занятия. Серверная история и audit атомарны с эффектом и сохранённым результатом; endpoint просмотра подробного журнала изменений здесь не добавляется.

Ключ повтора — tenant/actor/operation_id. Typed canonical hash включает операцию, target, payload и исходную base_version; reason нормализуется как выше, список coaches как набор UUID, даты как моменты UTC. Один ключ/hash возвращает сохранённый результат, включая терминальный409, без нового эффекта; другой hash —409 OPERATION_ID_REUSED. Новая устаревшая команда —409 SESSION_VERSION_CONFLICT. Решение конфликта требует перечитывания и отдельного подтверждения с новым UUID/версией.

**Сначала проверяются текущие права/tenant/доступные ссылки, затем уже сохранённый результат, затем применимость состояния и версия новой команды.** Это позволяет вернуть ответ потерянной отмены, когда собственная команда уже сделала Session cancelled. Аналогично старый успешный перенос/назначение после последующего закрытия возвращает прежний результат без повторного изменения. Отзыв права блокирует даже replay. Старый результат не объявляет текущее состояние: после ack/replay UI читает свежий журнал и назначения. Такая ревизия порядка replay должна быть согласована/реализована для всех четырёх команд; действующий #29 не объявляется соответствующим ей автоматически.

Время и coaches имеют отдельные подтверждения и команды. UI не обещает атомарное сохранение обеих секций: перед второй командой перечитывается текущая версия; успех первой не выдаётся за успех второй. Это сохраняет существующий setSessionCoaches и не создаёт ещё один дублирующий DTO общей замены Session.

## Ошибки и UX

| Ответ | Значение и действие UI |
| --- | --- |
| 400 | Некорректный JSON/UTC/интервал/поля; текущая форма исправляется без заявления об успехе |
| 401/403/404 | Прежние нейтральные access/object ошибки; журнал/контакты/формы скрываются, synthetic fallback отсутствует |
| 409 новых команд | Существующий S1CommandConflict: SESSION_VERSION_CONFLICT / SESSION_CLOSED / SESSION_CANCELLED / OPERATION_ID_REUSED и другие применимые accepted коды; current_version не выдумывается |
| 409 назначения | Существующий TrainingCommandConflict; SESSION_ROSTER_LOCKED для запрещённого добавления в closed/cancelled, SESSION_VERSION_CONFLICT / OPERATION_ID_REUSED / COACH_INACTIVE как прежде |
| 413/415/429 | Прежние лимиты тела/типа/rate limit; форма не отмечается сохранённой |
| Разрыв/5xx | Результат может быть неизвестен; только явный повтор того же UUID/body/base_version, новая попытка не маскирует предыдущую |
| Offline | Запись и повтор заблокированы до S4; локальной очереди/постоянного storage нет |

UI разделяет ожидание, подтверждённый результат, неизвестный исход и конфликт. В synthetic adapter подтверждение называется результатом демонстрации; серверное сохранение не заявляется. Проверяются изменение даты в одном зале, сохранение ID/состава, отмена с отметками, lost-response/replay, конкурирующие версии, denied роли, закрытые/отменённые состояния и отзыв доступа. Клавиатура/focus/контраст/200% текст/reduced-motion сохраняются. Live API/RLS/CSRF/SQL-конкуренция — #36; физические устройства отдельно.

## Граница принятия

Согласование владельца принимает только этот узкий общий wire для UI #34 и будущей реализации соответствующих backend-команд; оно не принимает готовый код #30 или весь план генерации. Шаблон, горизонт генерации, миграции, SQL и серверное выравнивание прав остаются отдельной работой #30; их номера/PR не резервируются. #31/#32/#36 и synthetic-only ограничения сохраняются. После явного принятия wire обновляются основной OpenAPI/примеры/описание затронутых прав и snapshot, затем реализуется и проверяется UI в той же ветке/PR116. До принятия PR116 остаётся draft/In progress; зависимой реализации нет.
