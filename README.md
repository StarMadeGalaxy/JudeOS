# JudeOS

Внутренняя система Judo Pride и основа будущего продукта для спортивных клубов. Первый выпуск предназначен для сотрудников: люди и семьи, занятия, посещаемость, добровольная поддержка и сверка поступлений, Telegram и ограниченный офлайн.

Реализованы синтетическая Go/PostgreSQL/web основа, реестр людей/семей/проверенных представителей, единый вход и явные сетевые/платформенные права сотрудников. Runtime требует schema9; OpenAPI/Swagger содержит45 реализованных операций из52. Семь операций журнала остаются planned, а отдельный мобильный прототип имитирует сервер в памяти.

Рабочая последовательность начинается с S0/S1: синтетический запуск и онлайн-журнал. Полный MVP сохраняет финансовую сверку, Telegram, офлайн и внедрение в четырёх залах. Новый разработчик сначала читает инструкции и актуальный статус, затем берёт конкретную задачу.

Backend: **Go + net/http + chi v5**, PostgreSQL. Документация — обязательная часть каждого изменения: [правила API/OpenAPI и Swagger UI](docs/API-DOCUMENTATION.md), [принятый ADR 0004](planning/adr/0004-chi-and-api-documentation.md). Первый контракт принят в #16; реализованные access/служебные маршруты и planned журнал разделены в [реестре API](api/ENDPOINTS.md).

## Локальный синтетический запуск

Нужны Docker Engine/Compose v2, Python 3 и Make. Из корня:

```sh
make up
```

Открыть http://127.0.0.1:8080/; Swagger — http://127.0.0.1:8080/docs. `make down` останавливает среду и сохраняет БД. Случайный локальный пароль создаётся в игнорируемом `.env`; реальные данные и credentials не коммитятся. Обычный запуск не требует CA-файла на host; дополнительный CA для HTTPS-прокси подключается явно по ops/README.md.

Запуск без контейнера приложения, версии, миграции/seed, конфигурация, проверки и восстановление — [ops/README.md](ops/README.md). Технический выбор каркаса — [ADR 0007, предложено для ревью](planning/adr/0007-synthetic-scaffold.md). #20/#21/#22/#23 интегрированы. HTTP loopback служит проверке основы; для Secure-cookie входа нужен [отдельный HTTPS стенд](docs/access/README.md). Worker/PWA/offline добавляются с потребителями.

Для проверки: `make build && make check`, `make db-up && make check-db`; при работающем API — `npm --prefix api run check:runtime` и браузерные команды в ops/README. Полный API-контракт и runtime-контракт разделены по признаку реализованности, имеют один источник OpenAPI и проверяются через настоящий chi.Walk.

## Выбор следующей карточки и новый чат

[Порядок выбора следующей Issue и передачи](planning/ISSUE-HANDOFF.md) обязателен: перед выбором проверить актуальный backlog, последние закрытые задачи/merged PR команды и текущего пользователя, зависимости и занятость. Только после подтверждённого завершения текущей Issue один раз дать следующую Issue и готовый промпт; во время работы/ревью/исправлений и статусных ответов новую задачу не предлагать; открытый PR не считается принятой зависимостью, рекомендация не резервирует задачу. Одна Issue — один чат, название после создания PR содержит номера PR и Issue. Новый чат повторяет проверку и подтверждение In progress.

## Вход сотрудников (#21)

[Запуск HTTPS, первое приглашение владельца и права](docs/access/README.md). Настройте exact `PUBLIC_ORIGIN`; пустой origin закрывает access API. Миграция00004 реализует прежний access; новые00005–00009 добавляют реестр/сеть и требуют schema9; first-owner CLI запускается явно с migrator credential, без default password и без bootstrap при старте API. Browser login/logout, invite/reset и staff roles используют только synthetic data; session/link/password не сохраняются в localStorage/IndexedDB. Deployment на существующий VPS требует отдельного принятого релиза, этот PR его не выполняет.

## Реестр, сеть и платформа (#27)

[Правила, роли, миграции, operator-only bootstrap платформы и проверки](docs/people/README.md). Люди и спортсмены не требуют Account; семья/телефон/поступление не дают прав. Владелец настраивает свою сеть и клубы, отдельный администратор платформы — все сети, менеджер назначает тренеров только своего клуба. Единый вход не объединяет профили разных клубов. Приглашение готового входа требует согласия получателя, клубный reset не захватывает сетевые/многоклубные входы. Кабинеты родителей/спортсменов и журнал остаются отдельными задачами; только синтетические данные.
