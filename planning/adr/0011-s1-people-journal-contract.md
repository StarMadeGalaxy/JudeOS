# ADR 0011: предложенный wire-контракт людей и журнала S1

Дата: 8 октября 2026. Статус: **предложено**, не заменяет принятый ADR 0006. Issue: [#26](https://github.com/StarMadeGalaxy/JudeOS/issues/26). Источники: [рекомендации по поручению владельца](https://github.com/StarMadeGalaxy/JudeOS/issues/26#issuecomment-6060282984), [техническая граница #21](https://github.com/StarMadeGalaxy/JudeOS/issues/21#issuecomment-6059940617).

## Контекст

Принятый #16 определяет минимальный журнал текущего назначенного coach. Для S1 нужны люди без обязательного Account, проверенное представительство, основной контакт и явная матрица истории/закрытия/состава. Источник нового варианта — рекомендации агента; отдельной приёмки каждого бизнес-правила владельцем нет. Особенно заметен выбор закрытия: в #26 консервативно закрывает тренер, рекомендация разрешает только administrator/manager. Его нельзя объявить принятым через описание схемы.

## Предложение

Использовать один [OpenAPI](../../api/openapi/openapi.yaml): девять новых planned/proposed операций и помеченные proposed расширения трёх операций #16. Отдельные CreatePerson/CreateAthlete не смешивают профиль/участие/вход. PrimaryContact — минимальная nullable проекция имени/телефона; полная карточка и GuardianLink остаются административными DTO. DOB/семьи/финансы/документы не входят в журнал. Optional расширения RosterEntry сохраняют валидность прежних fixtures; клиент всё равно обновляется для чтения расширения.

Команды используют operation_id, версию соответствующего агрегата и атомарный эффект/историю/результат по #16. У Attendance своя версия. S1CommandConflict добавляется отдельно, чтобы не менять общую Error/auth-схему без разрешения #21. Числовые wire-лимиты и формы DTO — техническое предложение, не новый обязательный бизнес-реквизит. Подробные правила, матрица и негативные сценарии — [S1-CONTRACT](../../api/S1-CONTRACT.md).

## Альтернативы и последствия

Выдача полной карточки тренеру раскрыла бы другие связи/основания проверки. Автоматическая замена контакта после отзыва дала бы новые права без решения. Профиль на телефон/Account вместо стабильного ID смешал бы участников и вход. Физическое удаление roster уничтожило бы происхождение фактов. Незаметная смена принятых ролей закрытия подменила бы согласование; поэтому выбор вынесен в явный пункт ревью.

Нет миграций/предметной реализации. Схемные fixtures/TS/Swagger проверяют только контракт, runtime-права проверяются с реализацией #27/#29/#31/#33. Принятие бизнес-варианта и интеграция merged #21 с общими проверками необходимы до использования новых прав зависимой работой. Опубликованный VPS/schema3/manifest сохраняется; deploy не выполняется.
