# ADR 0003: входящий платёжный протокол iPay

Дата: 7 октября 2026 года. **Статус: предложено**, требуется ревью финансового контракта и подтверждение профиля подключения. ADR 0001 не заменяется. ADR 0002 описывает отдельное предложение backlog из объединённого [PR #71](https://github.com/StarMadeGalaxy/JudeOS/pull/71).

## Контекст

Предоставлен [PDF и разбор протокола](../../docs/integrations/ipay/README.md): iPay вызывает пять XML-сообщений на сервере поставщика. TransactionStart ещё не означает оплату; RequestId общий для цепочки; результат повторяется, не содержит суммы и не допускает Error в ответе. Настройки договора клуба, подпись, сроки и реестр не установлены. Существующее представление «сначала файл, API неизвестен» нуждается в уточнении, но подключение API не подтверждено.

## Предложение

1. Сохранить границу финансового модуля Go/PostgreSQL: входящий XML-адаптер отдельно от REST API сотрудников и файлового импорта. Реальный режим выбрать по договору; наличие PDF не включает новый компонент в production.
2. Если on-line режим подключён, долговременно принимать проверенное сообщение с областью provider account/услуги/tenant, типом, корреляционными ID и результатом обработки. Tenant определяется настройками подключения, а не ФИО или Agent. Внешний ответ следует после сохранения; точную стратегию не-200 при сбое БД согласовать с iPay. Подпись проверяется на согласованных байтах до доверия данным; не подставлять придуманный алгоритм. Для endpoint предлагается HTTPS и ограниченный XML parser без DTD/внешних сущностей, с лимитами размера/времени.
3. Сохранять начало операции, сумму/валюту/лицевой счёт и устойчивый ServiceProvider_TrxId длиной до 12 символов. Повтор начала возвращает исходный ID; внутренний UUID остаётся отдельным. Деньги преобразуются точно в копейки, без float; транспорт windows-1251 остаётся на границе адаптера.
4. Только результат успешной оплаты создаёт факт подтверждения on-line операции. Банковское зачисление и распределение поддержки остаются отдельной сверкой. Результат без сохранённого начала или с конфликтующими данными попадает в разбор, а не создаёт Receipt с придуманной суммой. Не отправлять Error в XML-ответе TransactionResult; предупреждение в Info не заменяет надёжное внутреннее состояние.
5. RequestId не использовать как единственный ключ уникальности входа/поступления. Область TransactionId уточнить договором; ключ обработки учитывает тип сообщения и исходную транзакцию. Нужны сериализация повторов, сохранённый ответ и выявление изменённого содержимого. Для нескольких сторно без отдельного ID сначала согласовать возможность отличить повтор от нового события; не закреплять универсальный ключ заранее.
6. StornStart не меняет финансовый итог. При подтверждённом StornResult=Y компенсировать Receipt/распределения атомарно с историей; N сохраняет факт неуспешной попытки. Частичный возврат через iPay не обещать без подтверждения. После restore сверять внешние результаты до возобновления автоматического применения/доставок.

## Альтернативы

- Только файловый адаптер остаётся допустимым, если у клуба нет on-line подключения. PDF не описывает формат файла, поэтому эта ветка требует другого первоисточника.
- Считать TransactionStart или HTTP 200 поступлением — потеря различия между доставкой/началом/успехом и риск ложных денег.
- Обрабатывать callback только в памяти — риск потери результата и нового ID при повторе. Универсальный inbox для всех будущих интеграций заранее увеличивает схему; конкретные таблицы добавляются с адаптером.

## Последствия и принятие

Потребуются конкретный endpoint/транспортный контракт, схема начала/входа/результатов, миграции и интеграционные проверки при реализации. Сейчас они не создаются. Необходимы договорные параметры и разрешение разрыва Debt/добровольной поддержки из [списка вопросов](../../docs/integrations/ipay/README.md#что-получить-перед-адаптером-judo-pride). Принятие фиксируется ревью контракта в #17/#41; предложение не объявлено требованием пользователя и не снимает блокировку настоящего адаптера.
