# ADR 0012: отдельный контур и условия реального онлайн-пилота

Дата: 9 октября 2026 года. Статус: **предложено для согласования и технического ревью; согласование отложено пользователем**. Issue: [#18](https://github.com/StarMadeGalaxy/JudeOS/issues/18). Реализация production/restore — [#24](https://github.com/StarMadeGalaxy/JudeOS/issues/24). Требование будущего размещения персональных данных в аттестованном ЦОД РБ подтверждено в DECISIONS U2026-10-09-REALDATA-DIRECTION; конкретный оператор/ЦОД, основания, ответственные, сроки и RPO/RTO не подтверждены.

## Контекст

Синтетическая S0 принята через PR #109; access #21, реестр людей/семей/представителей, сетевой вход и восстановление #27 интегрированы в main/schema11 через PR #111. Минимум #26 принят через PR #102; [источники приёмки и текущая передача](../STATUS.md). Действующий Hostinger test использует frozen release2/schema3; журнал main — planned, прототип имитирует сервер. Synthetic restore-check, приёмка реестра и назначенный test-оператор не доказывают реальную production-готовность.

[Пакет согласования](../../docs/operations/real-data-conditions.md) содержит единый реестр RD-01–11, матрицу полей/доступов/сроков и условия пилота. Подтверждения фиксируются в DECISIONS с источником; этот ADR фиксирует предложения, не создаёт согласий или юридических ролей.

## Предложенный выбор

1. Сохранить действующий synthetic test. Выделить отдельный production-контур с собственными credentials/volumes/domain/admin-доступом и независимым шифрованным хранилищем копий. Конкретный провайдер/ЦОД выбирается по RD-02/09 после проверки оператором подтверждённого требования аттестованного ЦОД РБ, включая copy/WAL с персональными данными. Это требование пользователя, не самостоятельный вывод об обязательной локализации по закону.
2. Начать с одной VM только при принятой единой точке отказа/времени восстановления, закрытой БД и раздельных runtime/migrator/backup/admin полномочиях. Разнести API/DB позже по измерениям; две VM без схемы резервирования не обеспечивают failover.
3. Предпочтительный для обсуждения вариант A: целевой RPO 15 минут / RTO 4 часа, базовые копии + независимый WAL/PITR и монитор восстановимости. Это **не утверждённый SLA**. Daily dump недостаточен для этой цели. Вариант B: RPO 24 часа с независимым daily dump; RTO «следующий рабочий день» требует числового предела/календаря до принятия.
4. Предложить P1: один согласованный зал/группа, сотрудники и онлайн-журнал, ограниченный двухнедельный период оценки; без медицинских файлов/диагнозов, платежей, активного Telegram и офлайна. «Болел»/допуск требуют отдельного решения RD-05; до него реальные данные не запускаются. Этот ADR не удаляет sick из существующего synthetic контракта.
5. Применять retention по классам/началу отсчёта и включить экспорт, audit, copy/WAL, метаданные доступа, устройства и провайдеров. Числовые варианты T1/T2 в пакете остаются предложениями. Архив не заменяет удаление; UUID/digest не доказывает обезличивание.
6. Проверять restore в изоляции до открытия доступа: запуск с запретом исходящих действий вне восстановленной БД; schema/RLS/целостность, отзыв sessions/invite/reset, актуальные grants и удаления/отзывы по независимому источнику, сверка потерянного окна и явное возобновление. Специфика S3/S4 добавляется при реализации, не объявляется существующей сейчас.

## Альтернативы

| Вариант | Причина рассмотреть | Ограничение |
|---|---|---|
| Отдельный production у нового выбранного провайдера в аттестованном ЦОД РБ (C1) | Проверяется соответствие требованию пользователя | Провайдер/область аттестации, правовая пригодность и стоимость не подтверждены |
| Отдельный ресурс/account у текущего провайдера (C2) | Возможность использовать знакомую технологию | Только при подтверждённом аттестованном ЦОД РБ и договорах/допуске; Hostinger test этим не аттестован и не преобразуется |
| Daily dump и ручная сверка (B) | Проще эксплуатация, меньше инфраструктуры | Больше допустимая потеря; числовой RTO, часы поддержки и дельта требуют согласования |
| Несколько VM/managed PostgreSQL/failover | Возможны после согласования более строгой доступности/измерений | Дополнительные договоры, цена, доступы и испытания; количество VM само по себе не решение |
| Продолжать только synthetic | Допустимо пока обязательные решения неизвестны | #18 остаётся открытой и #24 не разблокирована |

## Последствия и условия принятия

Оператор подтверждает основания, роли/регионы/поля/сроки; владелец — пилот/бюджет/допустимую потерю; принимающие обязанности сотрудники — ответственность/замещение/поддержку. Совмещение ролей у человека не предполагается. Для принятия ADR нужны заполненные RD-01–11, независимое техническое ревью и подтверждения с источниками. Реализация выбранного контура и измеренный restore принимаются отдельно в #24 до реальных данных.

Этот PR меняет документы. OpenAPI, DTO, routes и SQL не меняются: новые TTL/права/cleanup/health-policy/backup/PITR здесь не реализуются. Последующая реализация обновит модель/API/OpenAPI и добавит новые миграции по фактическому изменению; применённые миграции не переписываются. Синтетические проверки подтверждают текущую основу, не выбранный SLA или юридическое соответствие.
