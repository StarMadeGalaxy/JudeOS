# ADR0017 — настройка конкретного занятия

Статус: **принят wire для UI/fixtures; backend #30 planned**. 10 октября 2026. [Явное принятие владельца](https://github.com/StarMadeGalaxy/JudeOS/issues/34#issuecomment-6098890491) опубликованного d49d05a проекта; [общий контракт](../../api/SESSION-CONFIGURATION-CONTRACT.md). Это не приёмка готового backend или генерации.

## Контекст и выбор

#34 требуются настройка даты/времени и отмена Session, отсутствовавшие в основном API. Приняты две узкие команды rescheduleSession/cancelSession с существующим TrainingSession в ответе. Для coaches сохраняются setSessionCoaches/SessionCoaches, добавлена optional reason и administrator-only область; первоначальный выбор createManualSession также administrator-only. Closed/cancelled разрешают только отдельный отзыв текущих назначений. DTO roster/Attendance и существующие права people/access не меняются.

Время и coaches имеют отдельные подтверждения, версии и результаты: после первой команды читается текущее состояние перед второй. Текущие права/доступные ссылки проверяются до replay, а состояние/версия новой команды — после него. Это возвращает результат потерянной отмены, уже сделавшей занятие cancelled, без повторного эффекта. После ack/replay читается актуальный журнал; старый результат не заменяет новый snapshot. No-op не меняет историю/версию; reason не является заметкой Attendance.

## Альтернативы

Единая атомарная команда времени/тренеров потребовала бы дополнительного DTO и дублировала setter. Произвольный PATCH Session позволил бы случайно изменить venue/group/state/ключ. Один setSessionCoaches не покрывает дату/отмену и сохраняет прежние manager права. Раздельные команды сохраняют existing DTO и делают частичный успех явным.

## Последствия и граница runtime

Основной OpenAPI содержит принятый целевой wire. Новые команды planned; existing create/set coaches отмечены x-session-configuration-status: planned, сохраняя implemented статус маршрута. Live /docs через pinned runtime-legacy/session-configuration-v1.json продолжает точно описывать реализованный #29, включая старый request без reason и manager права. Проверки не допускают выдачи будущей ревизии за работу сервера. После #30 маркер/override снимаются с серверными тестами; файл не редактируется как второй источник новых схем.

#34 реализует только синтетический UI/adapter. Backend #30 обеспечивает права, состояние, версии, audit/history/idempotency, исходный ключ, шаблон/генерацию/SQL. #36 выполняет live-приёмку. Номер миграции не резервируется; ADR0016 остаётся отдельной #39. Никакие реальные данные, релиз или рабочие тома этим решением не разрешены.
