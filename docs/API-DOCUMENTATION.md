# Документация продукта, endpoint’ов и Swagger UI

Статус: обязательные правила разработки по поручению пользователя от 7 октября 2026 года. Backend — Go + стандартный net/http + chi v5; решение и причины — [ADR 0004](../planning/adr/0004-chi-and-api-documentation.md). Приложения пока нет: перечисленные ниже контракт, реестр, Swagger UI и CI создаются при реализации S0, а не считаются уже работающими.

## Источник контракта

Основной машиночитаемый HTTP-контракт — `api/openapi/openapi.yaml` в формате OpenAPI 3.0.3; эта версия выбрана как исходный формат для совместимости Swagger UI и генераторов. Совместимость конкретных закреплённых инструментов проверить в S0; смену формата фиксировать отдельным ADR. `$ref` могут ссылаться на соседние файлы, но итоговый bundled-документ должен валидироваться и отображаться в Swagger UI. Схемы принадлежат контракту, не копируются вручную в несколько документов.

Swagger UI читает OpenAPI YAML/JSON. Комментарии Go, Markdown и экспорт дерева chi сами по себе не дают полноценной Swagger-документации. Исходный подход — contract-first: ближайший API согласуется до зависимой реализации, затем код и контракт обновляются вместе. Генератор из Go-аннотаций не является вторым источником истины; переход на такой подход требует отдельного решения и сохранения проверок покрытия/соответствия.

`api/ENDPOINTS.md` — краткий реестр для проверки полноты, со ссылками на операции контракта. Каждая строка содержит method/path, operationId, модуль/ответственного, аудиторию (REST, интеграция, служебный), авторизацию/scope, статус (запланирован/реализован/deprecated/удалён), ссылку на Issue/PR и контракт. Пара method/path уникальна. Реестр не дублирует схемы; по возможности генерируется из контракта с метаданными. Запланированные операции отделяются от опубликованного контракта работающего релиза.

## Обязательное описание каждой операции

- HTTP-метод, точный путь, стабильный уникальный `operationId`, `tags` модуля, краткое назначение и описание бизнес-поведения.
- Path/query/header/cookie параметры: тип, обязательность, формат, диапазоны, значения по умолчанию и ограничения. Path-параметры всегда обязательны.
- `requestBody`: Content-Type, обязательность, схемы и синтетические примеры; различие отсутствующего/null/пустого значения, единицы и формат денег/времени по применимости.
- Все предусмотренные успешные и ошибочные ответы: HTTP-коды, Content-Type, схемы, безопасные примеры, значимые заголовки. Описать применимые 400/401/403/404/405/409/422/429/5xx; не добавлять коды, которые операция не возвращает. Для пакетных команд — applied/conflict/rejected и частичный результат, для фоновых операций — постановку задания и получение статуса.
- `securitySchemes` и `security`: серверная cookie-сессия или способ проверки интеграции; публичные операции явно используют `security: []`. Описать tenant/scope, предметные права и CSRF/Origin для изменяющих запросов с cookie. Параметр клуба сам по себе не даёт доступ.
- Версии/совместимость, ключи идемпотентности и правила повтора, конфликты/base_version, пагинация/сортировка/фильтры, лимиты размера/частоты и таймауты — где применимо.
- Значимые побочные эффекты, аудит, атомарность, доставка уведомлений и ограничения отключённого модуля; ссылки на модель данных, бизнес-правило и протокол интеграции.

Права и бизнес-ошибки документируются независимо от middleware chi. Swagger UI не проверяет безопасность и не заменяет интеграционные проверки.

## Полнота маршрутов и интеграции

Учитываются все реальные HTTP endpoint’ы: `/api/v1`, вход/приглашения/восстановление, входящие iPay/Telegram callbacks, health/readiness, метрики, служебные операции и выдача документации. Конкретные пути выбираются при реализации, этот список не создаёт готовых маршрутов.

XML/iPay описывается с реальными media types, кодировкой, заголовками и схемами/примерами; подробный протокол остаётся в [документации iPay](integrations/ipay/README.md). Документирование не означает автоматическую генерацию XML-моделей или подписи.

Автоматические HEAD/OPTIONS, статические ресурсы Swagger UI/PWA и catch-all описываются общей политикой/записью реестра. Если у них отдельное поведение/права, нужна отдельная операция. Исключения из сравнения chi/OpenAPI перечисляются явно с причиной; скрытых недокументированных маршрутов быть не должно. Для 405 описать `Allow`; контракт ошибок покрывает неизвестные пути и неправильные методы. Решения о слешах/редиректах фиксируются при сборке роутера.

В S0 предоставить Swagger UI и bundled-спецификацию в среде разработки/test; путь и команды запуска записать в README. Публичное размещение внутренней документации не подразумевается: production-доступ определяется явно, служебные схемы/маршруты ограничиваются. Для cookie-auth описать вход/CSRF; кнопка Try it out не обходит эти проверки и не считается автоматическим приёмочным тестом. Никаких реальных персональных данных или секретов в примерах.

## Изменение и проверка API

1. Уточнить ближайший сценарий и права, проверить действующий контракт/реестр. Согласовать изменение общего API в Issue/PR до зависимой работы.
2. Изменить OpenAPI и реестр в том же PR, что обработчики chi и клиент. Обновить примеры, правила данных/интеграций и инструкции сопровождения.
3. При breaking change описать последствия для TS-клиента/PWA, поддерживаемых версий и офлайн-команд; при необходимости обеспечить период совместимости. Удалённые endpoint’ы не оставлять в текущем опубликованном контракте; историю сохраняют Git/PR и отметка реестра.
4. Выполнить проверки ниже; ревью отклоняет рассинхронизированные реализацию/контракт/реестр.

При создании каркаса/CI закрепить инструменты и воспроизводимые команды для:

- валидации OpenAPI, разрешения `$ref`, уникальности operationId и обязательности path-параметров;
- сравнения зарегистрированных маршрутов через `chi.Walk` с method/path контракта и реестра; нормализовать вложенные маршруты, учитывать только явно описанные исключения;
- контрактных проверок значимых запросов/ответов: схемы, коды, заголовки, ошибки, авторизация и частичные результаты; одна проверка наличия пути не доказывает соответствие;
- генерации и сборки TS-клиента, проверки отсутствия устаревших генерируемых файлов;
- загрузки bundled-контракта в закреплённом Swagger UI, разрешения схем и просмотра примеров; первичную проверку отображения выполнить в S0, повторять при изменении инструмента/формата или проблемных конструкций.

Проверки OpenAPI/покрытия/клиента обязательны для каждого API-изменения; ручной просмотр Swagger UI — для новых или изменённых операций. PR сообщает команды, результаты и ограничения. Пока приложения/CI нет, это требования к будущему каркасу, а не заявление о выполненных проверках.

## Документация остальных частей продукта

Документируется всё существенное для сопровождения: назначение модулей и бизнес-правила, права/tenant/scope, данные и миграции, интеграции и состояния отказа, конфигурация и её значения, локальный запуск, релизы/совместимость, мониторинг, backup/restore и поддержка. Обновлять затронутые документы одновременно с поведением. Неочевидный алгоритм или ограничение поясняется возле кода; не нужен комментарий, повторяющий каждую строку. Существенный выбор фиксируется ADR с причинами и статусом. Документы ссылаются друг на друга и на контракт, вместо нескольких расходящихся копий.
