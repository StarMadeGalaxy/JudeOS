# ADR 0006: контракт входа и первого онлайн-журнала

Дата: 7 октября 2026 года. Статус: **предложено**; требует согласования двумя разработчиками в PR по [#16](https://github.com/StarMadeGalaxy/JudeOS/issues/16). Не заменяет [ADR 0004, принят](0004-chi-and-api-documentation.md) и не добавляет подтверждённых предметных требований. Источники: архитектура §§3–6, план S0.1/§6, модель данных и критерии #16.

## Контекст

Каркас и мобильный прототип зависят от общего wire-контракта. API ещё нет; проектировать финансы/чаты/офлайн целиком заранее не требуется. Account, профиль спортсмена, представительство и семья имеют разный смысл. Точные поля D54 и административный/исторический scope остаются неизвестными, но минимальный сценарий назначенного тренера можно подготовить на синтетических данных.

## Предложение

Использовать семь операций [OpenAPI 3.0.3](../../api/openapi/openapi.yaml): CSRF bootstrap, login, session, logout, список назначенных занятий за локальную дату, занятие с сохранённым roster и PUT одной отметки. Все пока запланированы в [реестре](../../api/ENDPOINTS.md). Cookie-сессия остаётся серверной; CSRF связывается с anonymous preauth или сессией, Origin проверяется и на login. После входа токен запрашивается заново. Применить exact paths без редиректов, без CORS/автоматических HEAD; 404/405/Allow описаны в [API README](../../api/README.md). Служебные операции добавляются с каркасом, не называются работающими.

Tenant пути проверяется через membership/grants, затем object scope и разрешённые поля. Первый сценарий ограничить активным coach с текущим SessionCoach; административное закрытие/исторические права не выводить из роли. DTO журнала содержит только ID/имя/участие/trial и отметку. Контакты/допуск/прочие поля согласовать в #26. Словарь различает Account/Person/Athlete/GuardianLink/Household и фиксирует общие денежные инварианты без финансового API.

Версии Attendance независимы по спортсмену; version 0 — ещё не записанный unmarked. Команда содержит operation_id/base_version/status и необязательную reason. Атомарно сохранять отметку, историю и OperationResult, сериализуя проверку состояния/назначения с их изменениями. Любое новое принятое намерение увеличивает версию; одинаковый ID/payload не создаёт нового эффекта. Hash включает версию/тип/target/base_version/status/reason, отсутствие и пустая reason эквивалентны. Точный повтор возвращает прежний успех или терминальный конфликт версии только после проверки текущих прав/отмены/архива. Иной payload того же ID — конфликт. После сетевой ошибки повторять исходную команду; после явного разрешения конфликта создавать новый ID. Replay не является свежим состоянием; клиент перечитывает журнал.

Не выбирать production TTL результатов/ID и recovery-policy без #18/#52; до согласования синтетический каркас не очищает результаты. Числа из примеров токенов не становятся настройками TTL. Wire IDs — UUID, версии — безопасные для TS целые, время — UTC, локальная дата — Europe/Minsk. Подробности параметров/схем только в контракте; [открытые вопросы](../../api/OPEN-QUESTIONS.md) связывают пробелы с владельцем решения и блокируемой функцией.

## Альтернативы

Один общий номер версии журнала заставил бы конфликтовать отметки разных детей. Last-write-wins скрывает правку другого тренера. Idempotency только по телу без actor/tenant/target/hash допускает подмену и двойной эффект при потерянном ответе. Версия без operation_id не отличает повтор уже принятой команды от новой конкурирующей правки. Bearer в localStorage ухудшает отзыв/изоляцию и противоречит текущей архитектуре.

Полный будущий API увеличивает объём несогласованных правил; Markdown без машиночитаемого контракта нарушает ADR 0004. Расширенные права по названию роли подменили бы незаданные предметные решения. Вместо этого готовится небольшой контракт с явными ограничениями до #26.

## Последствия и приёмка

Понадобятся version/уникальные ключи и атомарность OperationResult при #31; SessionCoach/roster и правила сериализации — #29/#31; FK/RLS — #20. SQL-миграции этим ADR не создаются. Invite/reset/revoke и эксплуатационные endpoint'ы добавятся в своих задачах с обновлением контракта. Позитивные/негативные примеры и воспроизводимые схемные/TS/Swagger-проверки — [API README](../../api/README.md).

Проверки схем не доказывают RLS, cookie/CSRF, конкурентный commit или работающий журнал. Интеграционные проверки выполняются с реализацией. До согласования/merge #16 зависимости #19/#23 остаются открытыми; автоматического merge нет. После ревью статус этого ADR обновляется явно, с источником принятия или заменяющим ADR.
