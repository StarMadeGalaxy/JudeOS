# JudeOS

Внутренняя система Judo Pride и основа будущего продукта для спортивных клубов. Первый выпуск предназначен для сотрудников: люди и семьи, занятия, посещаемость, добровольная поддержка и сверка поступлений, Telegram и ограниченный офлайн.

Реализован синтетический Go/PostgreSQL/web каркас: web-оболочка, служебные проверки и Swagger UI. Вход и предметные бизнес-операции пока запланированы.

- [Архитектура 0.4](planning/ARCHITECTURE.md)

- [Совместная разработка](CONTRIBUTING.md), [инструкции агента](AGENTS.md), [дизайн-система](DESIGN.md)

Рабочая последовательность начинается с S0/S1: синтетический запуск и онлайн-журнал. Полный MVP сохраняет финансовую сверку, Telegram, офлайн и внедрение в четырёх залах. Новый разработчик сначала читает инструкции и актуальный статус, затем берёт конкретную задачу.

Backend: **Go + net/http + chi v5**, PostgreSQL. Документация — обязательная часть каждого изменения: [правила API/OpenAPI и Swagger UI](docs/API-DOCUMENTATION.md), [принятый ADR 0004](planning/adr/0004-chi-and-api-documentation.md). Первый контракт принят в #16; служебные маршруты каркаса #19 документированы, семь бизнес-операций ещё запланированы.

Перед каждым запросом на выполнение агент обязан [зарезервировать задачу](CONTRIBUTING.md#резервирование-задачи-до-начала-работы): текущий GitHub-пользователь в assignee и подтверждённый In progress в Project #1. Только после этого начинается работа; при недоступном API требуется явное ручное подтверждение выбранной карточки, после которого старт разрешён.


## Локальный синтетический запуск

Нужны Docker Engine/Compose v2, Python 3 и Make. Из корня:

```sh
make up
```

Открыть http://127.0.0.1:8080/; Swagger — http://127.0.0.1:8080/docs. `make down` останавливает среду и сохраняет БД. Случайный локальный пароль создаётся в игнорируемом `.env`; реальные данные и credentials не коммитятся. Обычный запуск не требует CA-файла на host; дополнительный CA для HTTPS-прокси подключается явно по ops/README.md.

Запуск без контейнера приложения, версии, миграции/seed, конфигурация, проверки и восстановление — [ops/README.md](ops/README.md). Технический выбор каркаса — [ADR 0007, предложено для ревью](planning/adr/0007-synthetic-scaffold.md). #20 (изоляция БД), #21 (auth), #22 (CI/HTTPS/размещение) остаются отдельными задачами. Worker/PWA/offline добавляются с потребителями.

Для проверки: `make build && make check`, `make db-up && make check-db`; при работающем API — `npm --prefix api run check:runtime` и браузерные команды в ops/README. Полный API-контракт и runtime-контракт разделены по признаку реализованности, имеют один источник OpenAPI и проверяются через настоящий chi.Walk.

## Выбор следующей карточки и новый чат

[Порядок выбора следующей Issue и передачи](planning/ISSUE-HANDOFF.md) обязателен: перед выбором проверить актуальный backlog, последние закрытые задачи/merged PR команды и текущего пользователя, зависимости и занятость. Только после подтверждённого завершения текущей Issue один раз дать следующую Issue и готовый промпт; во время работы/ревью/исправлений и статусных ответов новую задачу не предлагать; открытый PR не считается принятой зависимостью, рекомендация не резервирует задачу. Одна Issue — один чат, название после создания PR содержит номера PR и Issue. Новый чат повторяет проверку и подтверждение In progress.
