# Работа над JudeOS / Judo Pride

- При каждом запросе на выполнение задачи сначала прочитай этот файл, проверь git status и ветку, затем выполни обязательное резервирование Issue/карточки по разделу ниже. До подтверждения assignee и In progress разрешён только минимальный анализ для выбора/проверки задачи; предметное проектирование и изменения не начинай. В новой сессии прочитай CONTRIBUTING.md и краткий planning/STATUS.md. planning/README.md используй как указатель; остальные документы выбирай по задаче согласно правилам ниже.
- planning/DECISIONS.md сохраняет подтверждённые требования и происхождение позднего baseline. Текущие рабочие документы — planning/ARCHITECTURE.md 0.4 и planning/MVP-DEVELOPMENT-PLAN.md 1.1; модель и сценарии согласованы с ними. Не превращай технические рекомендации или отсутствующие D26–D63 в новые подтверждения пользователя. planning/archive содержит исторические источники, не параллельную спецификацию.
- Подтверждённый backend — Go + net/http + chi v5 для маршрутизации, база — PostgreSQL. Первый выпуск предназначен для сотрудников, интерфейс mobile-first/PWA. Telegram — основной канал уведомлений. Протокол iPay описан в docs/integrations/ipay/README.md; его актуальность и профиль подключения клуба ещё не установлены.
- Разрабатывай на синтетических данных. Не коммить реальные сведения детей, родителей, платежей, медицинские документы, ключи и .env с секретами.
- Перед редактированием проверяй git status и существующие инструкции репозитория. Не перезаписывай чужие изменения. Одна задача — одна ветка; интеграция через PR.
- Меняй документацию вместе с поведением. Новые подтверждённые требования добавляй в DECISIONS.md с источником; технический выбор фиксируй отдельным ADR с причинами и статусом.
- Перед завершением выполни проверки, подходящие к изменению, и сообщи, что проверено и что не удалось проверить.
- Обновляй planning/STATUS.md при смене этапа, существенном блокере или передаче незавершённой работы: результат, ветка/PR, проверки, открытые вопросы и следующий шаг. Не включай секреты или персональные данные; не превращай файл в журнал каждой задачи.

## Облачная и совместная работа

- Каждый разработчик использует свой аккаунт ChatGPT/Codex и изолированное облачное окружение JudeOS. История чатов и рассуждения агентов автоматически не синхронизируются; общий контекст передаётся через документы, Issues, коммиты и PR в GitHub.
- В облачной среде найди и используй существующий checkout. Проверь git status, текущую ветку и HEAD; сохрани существующие изменения. Дополнительный worktree создавай только по явному запросу. Не предполагай доступ к окружению коллеги; отдельное окружение для того же репозитория подходит для совместной работы.
- Первое ознакомление выполняй в режиме чтения: изучи документы и проверь среду и GitHub-доступ. Реализацию начинай только по указанной или согласованной с пользователем задаче.
- Задачи ведём в GitHub Issues: у каждой один ответственный, понятная цель, границы и критерии готовности. Перед работой обязательны проверка занятости, назначение текущему GitHub-пользователю и подтверждённый In progress в Project #1. Порядок и действия при недоступности API — ниже и в CONTRIBUTING.md.
- Пользователь выбрал GitHub Project #1: Backlog → Ready → In progress → Review → Done. Перед стартом читай живой Status и проверяй права. Само назначение assignee, комментарий или локальный manifest не заменяют перевод карточки в In progress.
- Одна задача — одна ветка, например feat/12-attendance-api. Интеграция через PR и ревью коллеги. Связывай PR с Issue; для закрытия после merge используй Closes #12. Не пушь напрямую в main и не используй force-push.
- Не начинай зависимую работу на основании несогласованного контракта. Сначала согласуй и зафиксируй общий API или модель данных в репозитории; технические предложения отделяй от подтверждённых требований.
- После merge обнови свой checkout основной ветки; коллеге также нужно получить актуальную main. Уже запущенные облачные задачи автоматически не обновляются. Перед обновлением сохрани незавершённую работу.
- GitHub-аутентификацию проверяй операцией чтения, прежде чем просить дополнительный доступ. Учитывай, что GitHub-коннектор и CLI могут иметь разные возможности. Не проси присылать токены или секреты в чат.

## Выборочное чтение контекста

- planning/README.md — карта текущих документов, включая MVP-DEVELOPMENT-PLAN.md и действующие ADR. Не читай все Markdown-файлы перед каждым сообщением. Используй уже прочитанный контекст; перечитывай при изменении файлов, смене задачи, получении изменений коллеги или нехватке контекста.
- Начинай с цели и критериев готовности запроса или Issue. Связанные Issues и PR читай через доступные GitHub-инструменты: git pull не загружает их обсуждения.
- Через rg находи нужные файлы и разделы; читай связанные требования, код и контракты. Расширяй чтение при неизвестных зависимостях; экономия токенов не оправдывает догадки.
- Бизнес-правила: соответствующие решения DECISIONS.md. Выбор этапа: NEXT-STEPS.md. Данные: DATA-MODEL.md и существующие миграции. Архитектура: нужные разделы ARCHITECTURE.md и ADR. Интерфейс: правила дизайна выше.
- RESEARCH.md, OWNER-INTERVIEW.md и ACTIONS.md — справочные материалы; читай их при необходимости проверки источника, а не по умолчанию.
- Перед реализацией получай актуальные изменения безопасным способом, учитывая незакоммиченную работу. Не выполняй слепой pull в чужую ветку. Изменения общего API и модели данных согласовывай через Issue/PR.

## Сохранение контекста

- Храни актуальные описания вместо расшифровок чатов. Не дублируй решения: используй ссылки. Историю изменений сохраняют Git и PR.
- Код и проверки — в исходниках; изменения базы — в миграциях и при необходимости описании модели; API — в контракте; запуск — в README или инструкции эксплуатации.
- Подтверждённые требования — в DECISIONS.md с источником. Существенные технические решения — в отдельных ADR в planning/adr/: статус (предложено/принято/заменено), контекст, выбор, альтернативы и последствия. Не обозначай предложение агента принятым без согласования; смена утверждённого стека требует согласования.
- Результат задачи, проверки и оставшуюся работу описывай в PR и связанной Issue. Не добавляй отчёт о каждой задаче в AGENTS.md.
- Устаревшие описания обновляй; завершённые планы при необходимости архивируй со ссылкой; у заменённых ADR указывай новое решение.
- При авторизованной передаче работы сохрани изменения в коммите, отправь рабочую ветку и открой PR. Не объединяй PR автоматически. Если commit, push или PR не выполнены, явно сообщи, что осталось локальным и недоступным коллеге.

## Документация и API — обязательная часть готовности

- Документируй каждое изменение поведения в том же PR: назначение/правила модуля, права и область данных, модель/миграции, интеграции, конфигурацию, запуск, эксплуатацию и восстановление — по затронутой области. Объясняй причины и ограничения; комментарии к неочевидному коду дополняют документы. Не дублируй исходники и не создавай отчёт ради отчёта.
- Перед изменением HTTP API прочитай docs/API-DOCUMENTATION.md и planning/adr/0004-chi-and-api-documentation.md. Используй chi v5 поверх net/http; сохраняй стандартные обработчики, бизнес-правила в application services.
- Любой новый/изменённый/удалённый endpoint документируется вместе с реализацией: OpenAPI в api/openapi/openapi.yaml, реестр api/ENDPOINTS.md, примеры и описание поведения. Охватывай REST, входящие интеграции и служебные маршруты. Не объявляй запланированный endpoint реализованным.
- Для операции указывай стабильный уникальный operationId, method/path, tags, назначение, параметры/тело, схемы и примеры всех ответов, ошибки, авторизацию/tenant/scope, CSRF, версии/идемпотентность и ограничения по применимости. Swagger UI читает OpenAPI; prose и список chi-маршрутов не заменяют контракт.
- Перед завершением API-задачи проверь валидность OpenAPI/$ref/operationId, покрытие реальных маршрутов, соответствие запросов/ответов, сборку TS-клиента и отображение в Swagger UI. Документы, контракт и реализация должны совпадать; опиши невыполненные проверки. Подробности и правила исключений — в docs/API-DOCUMENTATION.md.

## Обязательное резервирование перед каждым запросом на работу

Правило действует для всех агентов в этом репозитории, включая Codex Web, документацию, исследование по Issue, код, тесты и продолжение работы. Полный порядок — [CONTRIBUTING.md](CONTRIBUTING.md#резервирование-задачи-до-начала-работы). Обычный ответ на вопрос или чтение для выбора задачи не требуют резервировать карточку; переход к выполнению требует.

1. Минимально прочитай запрос, текущие Issues/Project/обсуждения/PR и зависимости. Выбери только нужную свободную задачу; если подходящей нет, создай Issue для порученного объёма. Не резервируй весь backlog и не меняй чужие активные карточки.
2. Определи текущий login чтением аутентифицированного GitHub API/коннектора, которым выполняется назначение. Не выводи его из git author, имени пользователя в чате, владельца репозитория или прежнего assignee. Для каждого разработчика используется его собственный аккаунт; не хардкодь StarMadeGalaxy/NikishGum. Если разные инструменты представляют разные аккаунты, выбери канал пользователя и проверь его идентичность до записи; при неясности остановись.
3. Непосредственно перед записью перечитай Issue и карточку. Чужой assignee, In progress/Review, активный claim-комментарий или связанная работа означают занятость. Не перехватывай её; выбери независимую свободную Issue либо согласуй передачу. Для того же login тоже проверь активный чат/ветку: два агента одного человека не получают одну задачу автоматически.
4. Назначь единственным assignee текущий login, добавь Issue в существующий Project #1 при отсутствии карточки и выставь фактический Status In progress. Используй ID проекта/поля/варианта из API; не предполагай числовые ID или написание варианта. Не удаляй чужие назначения и не создавай вторую карточку одной Issue.
5. Прочитай результат обратно: assignee ровно текущий login, нужная карточка In progress, конкурирующей работы нет. Запиши в Issue короткий комментарий: исполнитель, chat/task ID или уникальный идентификатор запуска, объём, ветка (если известна), факт подтверждения статуса. Только затем начинай предметную работу и сообщи пользователю номер Issue/исполнителя.
6. В следующем запросе-продолжении снова проверь живое назначение/Status/claim; продолжай подтверждённую собственную работу без новой Issue и повторных одинаковых комментариев. Существенное расширение объёма оформляется отдельной свободной Issue и резервируется перед работой.
7. Если чтение, назначение или изменение Status недоступно/отклонено, не объявляй резервирование успешным и не начинай основную работу. Сохрани доступное назначение и опиши частичный результат/блокер. Попроси восстановить доступ или вручную выставить assignee и In progress; после подтверждения проверь повторно через доступный канал. Комментарий/локальная пометка не являются обходом. Это обязательное требование пользователя, а не необязательная настройка доски.
8. При готовом PR переведи карточку в Review и проверь результат; draft остаётся In progress. Done — после принятия/merge и выполнения критериев. При паузе не освобождай задачу молча: укажи блокер/следующий шаг; возврат в Ready и снятие assignee — только при явной передаче/отказе от задачи с прекращением работы.

GitHub assignee/Status не являются атомарной блокировкой. При двух назначениях или competing claim после read-back останови изменения и согласуй одного исполнителя; не продолжай параллельно до разрешения. Просроченность комментария сама по себе не разрешает перехват.
