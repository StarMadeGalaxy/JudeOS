## Ближайший сценарий

1. Браузер получает CSRF через `getCsrfToken`, отправляет `loginStaff` с preauth-cookie, CSRF и Origin. Пароль и секреты не сохраняются в localStorage/IndexedDB. После входа запрашивает новый CSRF для новой сессии; при перезагрузке получает сессию и CSRF заново.
2. Из активных memberships выбирает клуб. `listAssignedSessions` получает разрешённые занятия за конкретную локальную дату; пустой список допустим. Cursor непрозрачный, сортировка по времени начала/ID; смена фильтра требует нового списка. Между страницами перенос может изменить порядок, поэтому это не снимок.
3. `getSessionJournal` возвращает сохранённый roster и независимую версию каждой отметки. Клубный профиль, контакты, допуск и финансы не выдаются этим DTO. Их предложенное расширение описано в S1-CONTRACT; новые поля/права ждут принятия #26.
4. `setAttendance` содержит новый `operation_id`, прочитанный `base_version`, один из четырёх статусов и необязательную причину. Клиент показывает «Сохранено» только после подтверждения 200. При 409 версия требует явного решения; клиент перечитывает журнал, затем создаёт новый ID/версию. Закрытие не меняет `unmarked` на `absent`; команды закрытия нет в этом срезе.
5. После сетевой ошибки/500/503 клиент повторяет **те же ID и payload**, поскольку commit мог произойти. Replay возвращает исходный результат с `Operation-Replayed: true`; он не означает, что отметку с тех пор никто не менял. Затем клиент обновляет журнал. Отзыв доступа/отмена/архив блокируют replay до выдачи результата.

Поля авторства и времени вычисляет сервер; body с клиентским автором/tenant отклоняется. `trial` — отдельный roster-флаг, не статус посещаемости. Новый гость/добавление известного участника, закрытие, административное редактирование и офлайн-команды расширяют контракт в своих задачах, без заглушек и обещания реализованности.

## Права и атомарность

Принятый первый сценарий #16 задаёт узкое право **активного coach, назначенного сейчас конкретному занятию**. Membership и RoleGrant проверяются на каждом чтении/записи/повторе. Расширение #26 отдельно фиксирует собственные административные права и закрытие в [S1-CONTRACT](S1-CONTRACT.md); они не требуют выдавать administrator/manager роль coach. Историческое назначение само по себе не заменяет текущую проверку. Чужой объект даёт 404, отсутствие членства/grant — 403, отозванная сессия — 401; ошибки не раскрывают объект/контакты другого клуба.

Attendance изменяется отдельно для каждого Athlete. `Session.version` описывает расписание/состав/назначения, а не общий номер всех отметок. При записи сервер проверяет актуальное состояние занятия, roster, Athlete и scope в той же транзакции; перенос или смена тренера не обходятся старым ответом чтения. Изменение назначения/отмена/архив и отметка должны сериализоваться на уровне БД; конкретный lock order фиксируется с миграциями #20/#29/#31. Результат, история до/после и отметка фиксируются атомарно.

Сначала проверяются текущие права/состояние, затем ключ `(tenant_id, actor_account_id, operation_id)` и канонический hash команды. Hash включает тип/версию контракта, target, base_version, status и reason; отсутствие и пустая reason эквивалентны, null запрещён. Чужой target не раскрывается проверкой hash. Повтор успешного результата или сохранённого конфликта версии не создаёт нового эффекта. Конфликт версии терминален для ID; новый выбор требует нового ID. Некорректные/неавторизованные запросы и текущий запрет отмены/архива не сохраняются как принятые команды. Параллельные повторы защищаются уникальностью OperationResult; любое новое принятое намерение повышает версию на 1 и сохраняет историю, даже если status совпал.

Первая отметка до записи представляется как `unmarked`, version 0, автор/время null. Явное сохранение любого статуса, включая unmarked, создаёт version 1; далее версия возрастает. Повторный GET не создаёт факт отметки. Сроки хранения OperationResult и запрет переиспользования ID после очистки остаются в #18/#52: синтетический каркас не удаляет результаты автоматически. Это не production-политика бессрочного хранения и не контракт офлайн replay/recovery.

## Общая HTTP-политика предложения

- Один HTTPS origin web/API, CORS выключен. Серверная cookie `__Host-judeos-session`: Secure, HttpOnly, SameSite=Lax, Path=/, без Domain. CSRF-токен хранится в памяти, секрет сессии только в cookie; anonymous bootstrap использует отдельную preauth-cookie. Login ротирует сессию и отзывает preauth. Точные TTL, нормализация логина, пароль, приглашения/восстановление, rate limits — #21. Примеры сроков не задают значения конфигурации.
- Login/logout/setAttendance проверяют обязательный Origin по настроенному origin и CSRF, привязанный к действующей preauth/session. Отсутствующий/null Origin отклоняется. GET csrf не выдаётся сторонним Origin/Fetch Metadata, даже при допустимой cookie. Try it out должен следовать тем же правилам в будущем приложении; локальный preview его отключает.
- Вход — JSON UTF-8, максимум 16 KiB. Лишние поля, неверные типы/форматы/enum, неизвестный cursor — 400; неподдержанный Content-Type — 415, слишком большое тело — 413. Отдельного 422 в этом контракте нет. Пустые списки — 200. 429 и 503 содержат Retry-After в секундах; точные частоты выбираются в #21/#22.
- Все API-ответы, включая ошибки: `Cache-Control: no-store`, `X-Request-ID`. Реализованный HTTP-слой генерирует ID сам (32 hex), игнорирует клиентский X-Request-ID и передаёт ID в context для логов/будущего аудита; tenant/actor не извлекаются из заголовков. Ошибки содержат безопасный code/message/request_id без SQL, stack, контактов или секретов. 405 возвращает Allow для реального пути, неизвестный путь — 404 по схеме Error. Неверный метод не выполняет бизнес-операцию.
- Предложение для #19: только точные пути без редиректа слешей, автоматические HEAD выключены; OPTIONS не включает CORS и возвращает 405 на известном пути. 404/405/OPTIONS используют общую схему Error; исключения явно отражаются в реестре/chi.Walk при реализации. Статика Swagger не является предметным API; будущие маршруты health/readiness, метрик и выдачи spec документируются в #19. Локальный preview ниже — только инструмент чтения файла, не маршрут приложения.
- UUID — непрозрачные стабильные ID, не имя/телефон; версии — целые 0..2^53−1, безопасные для TS. Дата — YYYY-MM-DD; время событий — RFC 3339 UTC с Z, зона клуба Europe/Minsk. Деньги — целые копейки BYN только в будущих финансовых командах, не float и не «долг» по отсутствию поддержки.

## Примеры для приёмки реализации

Схемные fixtures находятся в [first-online.json](examples/first-online.json). Эта таблица задаёт будущую проверку поведения; пока проверяется совместимость схем, а не реальный backend.

| Сценарий | Ожидаемый результат |
|---|---|
| Coach A, клуб A, своё занятие, version 0 → present | 200, version 1, автор сервера, один эффект/история |
| Точный повтор после потерянного ответа | Прежний 200 и Operation-Replayed true, без нового эффекта |
| Два тренера меняют одного спортсмена с version 0 | Один 200, второй 409 с текущей версией; никакого молчаливого перезаписывания |
| Два разных спортсмена одного занятия | Независимые версии; конфликт одного не блокирует второго |
| Тот же ID и другая отметка/target | 409 OPERATION_ID_REUSED после проверки текущих прав |
| Повтор конфликта версии | Прежний 409, без применения; для разрешения новый ID |
| Сессия отозвана до повтора | 401, сохранённый результат не выдаётся |
| Назначение тренера убрано до повтора | 404, scope проверен заново; отсутствие grant/membership — 403 |
| UUID занятия клуба B запрошен через клуб A | 404; ни roster B, ни его факт существования не раскрываются |
| Клиент подставил tenant B без membership | 403, tenant-контекст не устанавливается из body |
| Athlete не входит в roster | 404; PUT не добавляет визит |
| Занятие отменено / Athlete архивирован | 409 SESSION_CANCELLED / ATHLETE_ARCHIVED, прежний результат не выдаётся |
| Назначенный coach исправляет closed | Новая версия/история, причина необязательна; unmarked остаётся отдельным статусом |
| Manager/administrator без coach grant/назначения | 403; административное право не подразумевается |
| Неверный/нет CSRF или Origin | 403 CSRF_REJECTED; запись/вход не выполняются |
| trial как статус, отрицательная/отсутствующая версия, клиентский автор | 400; негативные fixtures не проходят схему |
| Повтор после 503/потери сети | Тот же ID/payload, затем перечитать журнал; новый ID не создаётся автоматически |

## HTTP-политика основы S0

Один origin: Go отдаёт web, API и `/docs`; Vite dev proxy сохраняет тот же origin. CORS выключен; cookie/auth/CSRF реализованы #21 с exact HTTPS PUBLIC_ORIGIN. Worker и PWA/offline ещё не реализованы. HTTP loopback допустим для служебной синтетической проверки; вход требует HTTPS. Test #22 интегрирован, production ждёт #18/#24. `/healthz` проверяет процесс, `/readyz` — БД, ровно текущую версию миграций (4) и безопасную техническую роль runtime (без владения таблицами, SUPERUSER/BYPASSRLS/DDL или членства в migrator/audit_reader). Readiness не обещает готовность предметных модулей или всех RLS-политик. При недоступной/старой/более новой БД или привилегированном runtime возвращается 503, Retry-After: 2; подробности соединения не выдаются.

Все ответы получают `Cache-Control: no-store` и новый случайный `X-Request-ID`; присланный ID не принимается. Неизвестные пути, включая все запланированные бизнес-операции, возвращают 404 Error. Неверный метод существующего маршрута — 405 Error с `Allow`, зависящим от method/path. HEAD/OPTIONS не регистрируются; на HEAD тело отсутствует по net/http. Только точные пути: `/healthz/` и `/docs/` дают 404, перенаправлений слешей нет. Статическая выдача игнорирует Range/условные запросы и возвращает полный 200: no-store сохраняется на всех ответах, listing/редиректы/частичные ответы отсутствуют.

Статические исключения сравнения [chi.Walk](checks/routes.cjs) перечислены в [static-routes.json](static-routes.json). `/` отдаёт только web index, `/assets/*` — только одиночные regular files сборки, без listing/traversal/SPA fallback. `/docs/assets/swagger-ui.css` и `/docs/assets/swagger-ui-bundle.js` — закреплённые локальные файлы Swagger UI. Web использует настоящий access API #21; отдельный прототип #23 с имитацией входа/журнала не подменяет этот API.

`npm run bundle` создаёт полный `dist/openapi.json`, runtime-контракт только `x-status: implemented` и локальные Swagger assets. `npm run preview` показывает полный контракт для разработки; работающий `/docs` — тринадцать реализованных операций. Try it out отключён в обоих видах. OpenAPI остаётся единственным источником схем.

После `make build`: `npm run check:routes` сравнивает настоящий chi tree и runtime OpenAPI. При запущенном API — `npm run check:runtime` проверяет HTTP/схемы/заголовки и точное совпадение опубликованного runtime OpenAPI с собранным артефактом, `JUDEOS_CHROMIUM_PATH=/usr/bin/chromium npm run check:browser` проверяет построенную web-оболочку и настоящий Swagger UI. `npm run check:swagger` проверяет полный контракт. Команды выполняются в api; `JUDEOS_BASE_URL` задаёт origin живого API при другом порте.

## Реализованный staff access #21

Runtime контракт показывает 13 реализованных операций; полный контракт — 25: три операции журнала и девять новых S1 остаются planned. Access login/logout/session/CSRF из #16 реализованы, добавлены redeem/listStaff/inviteStaff/issueStaffReset/changeStaffAccess. TTL, CSRF/Origin, роли/последний владелец, ручная передача ссылок, запуск и ограничения — [access](../docs/access/README.md). Каждая операция содержит own security; runtime bundler сохраняет cookie security scheme. 405 Allow зависит от method/path, HEAD/OPTIONS выключены.
