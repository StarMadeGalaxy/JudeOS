# Flow приложения Judo Pride

Версия 0.3 от 7 октября 2026 года. Сценарии обновлены по разговору с владельцем и остаются проектными предложениями. Первая версия — сотрудники. Родители и спортсмены показаны как будущий этап; подробные права и доступность модулей ещё согласуются.

## Вход и совмещение ролей

```mermaid
flowchart TB
    Entry["Открыть PWA"] --> Auth["Войти: приглашение сотрудника и серверная сессия"]
    Auth --> Context["Определить связи с клубами, роли и область доступа"]
    Context --> Count{"Несколько рабочих контекстов?"}
    Count -->|"да"| Choose["Выбрать клуб и режим работы"]
    Count -->|"нет"| Home["Главный экран доступной роли"]
    Choose --> Home
    Home --> Guard["Каждое действие: backend проверяет права и область данных"]
    Home --> Switch["Переключить режим: например, тренер / родитель"]
    Switch --> Context
```

Переключатель не создаёт права. Одно лицо может иметь несколько назначений. Локальные данные разделяются по аккаунту и клубу; правила очистки при переключении уточняются.

## Менеджер / сотрудник учёта

```mermaid
flowchart TB
    Home["Задачи на сегодня"] --> Member["Спортсмен / семья: контакты и состав"]
    Member --> Enroll["Назначить группы и условия поддержки"]
    Enroll --> Recommend["Предлагаемая сумма: семейные условия и ручные корректировки"]
    Recommend --> Invite["Приглашение поддержать клуб по согласованным правилам"]
    Invite --> Telegram["Telegram родителя с подтверждённой связью"]
    Home --> Import["Получить реестр / уведомления iPay: способ подтвердить"]
    Import --> Match{"Платёж сопоставлен?"}
    Match -->|"да"| Allocate["Подтвердить связь с плательщиком, ребёнком и периодом"]
    Match -->|"нет"| Queue["Очередь ручной сверки"]
    Queue --> Allocate
    Allocate --> History["Обновить историю фактической поддержки"]
    History --> Notify["Сообщить о поступлении по выбранным правилам"]
    Notify --> Telegram
    Home --> Guest["Разобрать гостей и пробные посещения"]
```

Функции сверки могут принадлежать отдельной роли бухгалтера, если она нужна клубу. Объём полномочий менеджера не фиксируется ограничениями меню из исходного файла. Рекомендация поддержки и фактическое поступление различаются; отсутствующая добровольная поддержка не создаёт задолженность. Неоднозначный платёж по имени проходит ручную сверку.

## Тренер

```mermaid
flowchart TB
    Home["Мои занятия сегодня"] --> Session["Открыть конкретное занятие"]
    Session --> Roster["Состав, несколько тренеров, визиты из других групп и гости"]
    Roster --> Mark["Выбрать отметку; неотмечен отличается от отсутствия"]
    Roster --> Visitor["Добавить визит из другой группы или гостя"]
    Visitor --> Mark
    Mark --> Network{"Есть связь?"}
    Network -->|"да"| Send["Отправить команды с operation_id и base_version"]
    Network -->|"нет"| Local["Атомарно сохранить отметку и operation_id в IndexedDB"]
    Local --> Reconnect["Связь восстановлена / PWA открыта"]
    Reconnect --> Send
    Send --> Check{"Права и версия записи актуальны?"}
    Check -->|"да"| Saved["Подтверждено сервером"]
    Check -->|"нет"| Conflict["Показать актуальную запись: конфликт / отказ; новую команду не отправлять молча"]
    Saved --> Journal["История ребёнка и outbox; уведомление по правилу закрытия/исправления"]
    Journal --> Fix["Исправление тренером / уполномоченным сотрудником с аудитом"]
    Fix --> Network
```

Посещение ребёнка не должно превращаться в «отсутствовал» только из-за недоставленной отметки; «не отмечен» предлагается отдельным состоянием учёта. Статусы завершения занятия, область доступа и допустимые сроки исправления ещё не выбраны. Разовый визит не меняет автоматически основную группу. Отмена ошибочной отметки и разрешение конфликта сохраняют историю.

## Уровень платформы — предложение для продажи клубам

```mermaid
flowchart TB
    Platform["Администратор платформы"] --> Club["Подключить клуб"]
    Club --> Brand["Оформление и домен"]
    Club --> Modules["Включённые модули"]
    Club --> Contract["Условия: процент поступлений + фиксированная плата; продажа — отдельно"]
    Contract --> Direct["Поддержка родителей поступает напрямую клубу"]
    Direct --> Billing["Отдельный расчёт платы платформе: ставки и период уточнить"]
    Club --> Isolation["Настроить размещение и изоляцию данных"]
    Club --> Owner["Пригласить администратора клуба"]
```

Доступ оператора платформы к данным клиентов ограничивается согласованными процедурами поддержки и аудитом. Прямое поступление денег клубам и сочетание процента с фиксированной платой подтверждены; ставки, расчётные правила, схема продажи и способ изоляции остаются открытыми. Автоматическое удержание комиссии iPay не подтверждено.

## Привязка Telegram и доставка

```mermaid
flowchart TB
    Manager["Менеджер подтверждает представителя и его контакт"] --> Invite["Одноразовое приглашение без имени ребёнка в URL"]
    Invite --> Start["Представитель запускает бота; проверить токен и назначение"]
    Start --> Confirm["Подтверждённая связь Telegram с представителем"]
    Event["Изменение посещения / поступление / перенос"] --> Outbox["Событие в транзакции с изменением данных"]
    Outbox --> Job["Задание получателю; повторно проверить доступ и актуальность"]
    Confirm --> Job
    Job --> Send["Отправить через адаптер Telegram"]
    Send --> Result{"Результат"}
    Result -->|"message_id"| Accepted["Принято Telegram; прочтение не подтверждено"]
    Result -->|"ограничение / временная ошибка"| Retry["Повтор по правилам и retry_after"]
    Retry --> Job
    Result -->|"таймаут с неизвестным исходом"| Unknown["Неизвестный результат; политика разбора по типу сообщения"]
    Result -->|"получатель заблокировал бота"| Blocked["Прекратить доставку; задача менеджеру"]
```

## Синхронизация и конфликт отметки

```mermaid
flowchart TB
    Mark["Тренер выбирает статус"] --> Local["Сохранить локально: команда + текущая версия"]
    Local --> Pending["Показать недоставленную отметку"]
    Pending --> Sync["Связь / открытие / ручная синхронизация"]
    Sync --> API["API: сессия, клуб, права, operation_id"]
    API --> Repeat{"Операция уже обработана?"}
    Repeat -->|"да; содержимое совпало"| Old["Вернуть прежний результат"]
    Repeat -->|"нет"| Version{"Запись актуальна и действие разрешено?"}
    Version -->|"да"| Tx["Транзакция: отметка, новая версия, аудит, outbox, результат"]
    Version -->|"нет"| Conflict["Вернуть conflict / rejected и разрешённые актуальные данные"]
    Conflict --> Resolve["Тренер видит причину; исправление разрешённой новой командой"]
    Old --> Ack["Удалить из очереди только по понятному подтверждению"]
    Tx --> Ack
```

Совпадающий operation_id с другим содержимым отклоняется. Результат пакета возвращается по каждой команде. Отозванный доступ не разрешает показать новые данные; разбор может требовать менеджера. Обновление/выход PWA не удаляет очередь молча. Разовый гость и визит уже известного спортсмена используют разные проверяемые операции.
