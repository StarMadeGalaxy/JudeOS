# Выбор следующей Issue и передача в новый чат

Уточнено 8 октября 2026 года по [#99](https://github.com/StarMadeGalaxy/JudeOS/issues/99); исходный процесс — [#93](https://github.com/StarMadeGalaxy/JudeOS/issues/93). Применяется перед явно порученным выбором новой задачи и однократно после проверенного завершения текущей Issue, а не после подготовки PR или каждого ответа. Один чат ведёт одну Issue; новую работу передавать в новый чат. Ревью, исправления и продолжение текущей Issue остаются в её чате. Этот файл — единый порядок; живые статусы находятся в GitHub.

## Проверка завершения до автоматической передачи

Сначала проверь текущую/предыдущую Issue этого чата: выполнены ли все критерии, принят ли результат и интегрированы ли необходимые PR. Используй живые Issue/PR и подтверждения приёмки; отсутствие жалоб, зелёные тесты, готовый PR и один merged подготовительный PR не заменяют завершение. Закрытие без реализации (отказ/дубликат) само по себе не означает принятый результат. Если внешние результаты остались, задача продолжается даже после merge кода. При недоступном чтении можно опереться на конкретное подтверждение пользователя; без доказательств завершение не предполагать.

| Состояние | Ответ агента | Автоматический следующий Issue/промпт |
|---|---|---|
| Реализация, тесты, исправления, пауза или блокер | Прогресс/результат и следующий шаг текущей задачи | Нет |
| PR открыт, ожидается ревью/merge | Ссылка на PR, проверки, Review и что остаётся | Нет |
| PR merged, но критерии/приёмка/внешний результат не завершены | Продолжение текущей Issue | Нет |
| Критерии выполнены, результат принят, необходимые PR merged | Подтверждение завершения и однократная передача | Да |
| Передача уже выдана, новых обстоятельств нет | Ответ на текущий вопрос без повтора промпта | Нет |

Не анализировать следующий backlog заново на каждом прогресс-сообщении. В Issue/STATUS достаточно компактно отметить факт передачи, ссылку на следующую рекомендацию и основание завершения, без копирования промпта во все файлы. Если задачу возобновили, остановить автоматическую передачу до её повторного завершения.

Явный запрос пользователя выбрать независимую параллельную задачу или обновить передачу допускает отдельную рекомендацию: обозначить, что текущая Issue ещё не завершена, проверить отсутствие пересечения и сохранить её исполнителя/статус. Это исключение не запускается инициативой агента.

## Перед выбором

1. Прочитать AGENTS/CONTRIBUTING и краткий STATUS, проверить checkout/ветку/HEAD/чужие изменения. Определить текущий аутентифицированный GitHub-login, не брать имя из автора старого коммита.
2. Получить полный актуальный список открытых Issues, включая добавленные вне manifest. Учитывать пагинацию и ограничения инструмента; неполную выдачу не называть анализом всего backlog. Просмотреть цели, этапы, прямые зависимости и блокеры всех карточек; детали и обсуждения читать у готовых кандидатов и их зависимостей. Отложенные гипотезы и обзорные карточки не подменяют исполнимые задачи.
3. Посмотреть последние закрытые Issues и merged PR команды, особенно текущего разработчика. История помогает продолжить знакомый срез, но не вводит постоянного разделения ролей. Проверить приёмку, фактический merge/результат и незавершённые критерии: закрытая без реализации Issue и подготовительный merged PR не разблокируют зависимость автоматически.
4. Проверить открытые PR/ветки, assignee, последние claim-комментарии, Project Status и активные передачи. Пустой assignee сам по себе не доказывает свободу. Текущую чужую работу не перехватывать; если доказательств не хватает, явно обозначить неопределённость и запросить только недостающее подтверждение. Недоступность Projects обрабатывается существующим ручным порядком.
5. Выбрать один готовый свободный шаг, который продвигает ближайший рабочий срез или снимает важный блокер. При равной готовности учитывать продолжение завершённой работы этого разработчика, число разблокируемых задач, конфликты общих файлов и независимость от коллеги. Не выбирать по одному номеру, дате или последнему автору. Для явного поручения пользователя выполнить указанную задачу после проверки, не заменять её автоматически более удобной.
6. Показать номер, прямую ссылку, краткую причину и необходимые условия. Рекомендация ещё не резервирует задачу. При поручении выполнять — assignee и подтверждённый In progress по AGENTS, затем claim/ветка/работа. При ручном режиме дождаться ответа пользователя; не начинать на основании молчания.

Если готовых свободных задач нет, назвать конкретный блокер/PR для ревью и условный следующий шаг. Не придумывать готовность и не брать занятую задачу ради непрерывности цепочки. При недоступности GitHub передать предварительный вариант с ограничением и проверкой в новом чате.

## Один чат — одна Issue

После выбора и подтверждения задачи назвать текущий чат `Issue #N — краткое название`. После создания PR переименовать его в `PR #M · Issue #N — краткое название`. До создания PR номер не выдумывать. Если одна Issue требует нескольких PR, оставить номер Issue и основной/актуальный PR, остальные перечислить в передаче. Если инструмент переименования недоступен, предоставить точное название пользователю.

Новые чаты автоматически не создавать без явного поручения пользователя. После разрешённого перехода дать готовый промпт, который пользователь вставит в новый чат проекта. Уже существующие многоцелевые чаты не разбивать и не переименовывать массово; использовать правило с текущей выбранной задачей. История чата не заменяет GitHub/репозиторий.

## При подготовке PR и завершении Issue

При подготовке PR обновить результат/проверки/ограничения в Issue/PR и необходимую передачу текущей работы в STATUS. Сообщить ссылку на PR и требуемый Review; не заявлять merge, Done или приёмку без доказательств. Здесь ответ заканчивается без автоматического предложения другой задачи и без промпта нового чата.

Только после проверки завершения по разделу выше повторить анализ актуального backlog и один раз предложить **одну** следующую Issue с короткой причиной и самостоятельным промптом. Если готового шага нет, назвать конкретный блокер и условие будущего выбора; не выдумывать исполнимую задачу ради шаблона. Повторять передачу только по явному запросу пользователя или при существенном изменении её актуальности, объяснив причину изменения.

Не назначать заранее следующую Issue, не менять её Status и не начинать предметную работу в завершаемом чате. Новый чат проверяет занятость повторно: рекомендация может устареть за минуты. Не переносить старое ручное подтверждение In progress на другую Issue. Завершение очередного ответа само по себе не означает завершение Issue.

## Шаблон самостоятельного промпта

Подставлять реальные номера/названия/ссылки и фактические условия; не оставлять пользователю собирать ссылки по истории чата.

```text
Проект JudeOS, GitHub StarMadeGalaxy/JudeOS. Рекомендуемая задача: Issue #N — название, https://github.com/StarMadeGalaxy/JudeOS/issues/N.
Завершённая предыдущая задача: Issue #K — ссылка; принятый результат и merged PR #M — ссылка. Основание завершения: выполненные критерии и подтверждение приёмки/интеграции. Для явно запрошенной параллельной задачи вместо этого укажи незавершённую Issue и границу независимости.
Почему следующий шаг: краткая причина и условия готовности; не считать открытый PR принятой зависимостью.
Следуй AGENTS.md, CONTRIBUTING.md и planning/ISSUE-HANDOFF.md. Проверь git status, ветку, HEAD, получи актуальную main без потери чужой работы; прочитай краткий STATUS и документы по задаче. Повторно проверь все открытые Issues, последние закрытые задачи/merged PR команды и текущего GitHub-пользователя, зависимости, обсуждения/claim и занятость. Если рекомендация устарела или задача занята, предложи актуальный свободный шаг и объясни замену.
До работы назначь выбранную Issue текущему GitHub-пользователю и подтверди In progress. Если Projects API недоступен, дай прямую ссылку/исполнителя и дождись ручного подтверждения пользователя. Не начинай раньше.
Назови чат «Issue #N — название» после выбора и подтверждения. Выполни только объём этой Issue, одна ветка/PR, подходящие проверки и документация. Не расширяй MVP, не используй реальные данные и не объединяй PR автоматически. После создания PR переименуй чат «PR #M · Issue #N — название», укажи результат/проверки и ручной Review при необходимости. Пока эта Issue не завершена (критерии, приёмка и merge необходимых PR), не предлагай следующий Issue/промпт в прогрессе, ожидании ревью, исправлениях или статусных ответах. После проверенного завершения один раз выбери следующую свободную готовую задачу и дай её номер, причину и промпт для отдельного чата; заранее её не резервируй и не повторяй передачу без причины/явного запроса.
```

Не копировать секреты, расшифровки диалога или устаревшие списки статусов. Полезный контекст — ссылки на интегрированные решения, принятый контракт, открытый блокер и проверенный результат. Передача достаточно подробна для нового агента, но не дублирует спецификацию Issue.
