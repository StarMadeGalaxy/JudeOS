Только синтетические данные. Это реализация принятого минимума [#26/#102](https://github.com/StarMadeGalaxy/JudeOS/pull/102) и уточнений владельца по [единому входу](https://github.com/StarMadeGalaxy/JudeOS/issues/27#issuecomment-6082017900) и [администратору платформы](https://github.com/StarMadeGalaxy/JudeOS/issues/27#issuecomment-6082178440). [ADR0013](../../planning/adr/0013-network-and-registry.md) описывает техническое решение для независимого review; [OpenAPI](../../api/openapi/openapi.yaml) — источник wire-схем, [реестр маршрутов](../../api/ENDPOINTS.md) — покрытие реализации.

## Работа сотрудника

После входа выберите клуб. «Люди» создаёт отдельные карточки с отображаемым именем и необязательным телефоном. Имя и телефон не уникальны; одинаковые имена показываются отдельными карточками с коротким номером. Поиск — буквальная подстрока имени, страницы идут по стабильному UUID. Список не содержит телефонов, документов, оснований проверки или остальных полей полной карточки. Кнопка в карточке человека записывает его как regular/guest Athlete без Account; ID Athlete сохраняется при смене вида участия.

«Семьи» содержит самостоятельное название и периоды участия людей; членство не делает человека представителем. В карточке спортсмена сотрудник отдельно проверяет конкретного представителя, указывает краткое основание без документов/диагнозов, период [from,until) и подтверждает проверку. Сервер записывает автора проверки. Даты интерфейса относятся к Europe/Minsk, wire — UTC Z. Основной контакт один и необязателен; выбрать можно только действующую проверенную связь этого спортсмена. Снятие выбора, отзыв, истечение или архив представителя скрывают контакт без замены другим представителем.

Архивирование человека скрывает/очищает его телефон, архивирует его Athlete, отзывает его GuardianLink и снимает выбранные контакты. Архивирование Athlete оставляет Person и историю. ID, имя, исторические связи/периоды и metadata audit остаются доступны разрешённому административному сотруднику. DELETE/восстановление из архива не предлагаются. Account не связывается с Person автоматически: независимые рабочие права сотрудника не исчезают от архивирования одноимённой карточки. Parent/athlete кабинеты и TelegramBinding выключены; архив не обещает отзыв ещё не реализованных каналов. Реальные сроки/основания хранения, erasure и восстановление остаются #18/#24/#52.

## Область прав

| Кто | Реестр | Настройки | Сотрудники |
|---|---|---|---|
| Администратор платформы с отдельным явным полномочием | Все клубы | Все сети и их клубы | Владельцы, менеджеры, тренеры; отдельные администраторы платформы |
| Явный владелец сети | Клубы своей сети | Название своей сети, названия/адреса её клубов, добавление клуба | Владельцы своей сети, менеджеры и тренеры клубов сети |
| Administrator одного клуба без сетевого полномочия | Свой клуб | Может явно создать сеть из этого ещё не связанного клуба | Сотрудники этого клуба |
| Manager | Только назначенный клуб | Сетевых настроек нет | Назначение/отзыв только coach своего клуба |
| Coach | Административный реестр запрещён | Нет | Нет |

Обычная роль administrator, одинаковое название сети, семья, телефон или поступление не дают доступа к другим клубам. Сеть создаётся явной командой и включает только выбранный существующий клуб; остальные старые клубы не присоединяются автоматически. Новые клубы создаются внутри разрешённой сети. Перенос существующего клуба между сетями не поддержан и отвергается в БД. Профили людей остаются отдельными для каждого клуба; единый вход их не объединяет. Parent/athlete роли не добавлены в access #21.

Один вход возвращает объединение прямых клубных и отдельных сетевых/платформенных полномочий. Каждое чтение/команда заново разрешает текущую область под общей клубной блокировкой, затем работает в одной tenant-транзакции. Сетевой отзыв сериализуется с командами клубов сети; права и сессии перечитываются после блокировки. Отзыв owner/platform завершает сессии получателя; последний владелец и последний платформенный администратор защищены. Старый last-local-administrator guard #21 сохранён консервативно: наличие сетевого владельца не позволяет снять последнего прямого administrator старого клуба.

## Единый вход и приглашения

Прежние invite/install/reset/revoke #21 сохранены. Новая команда staff/assignments работает и с новым, и с уже настроенным входом: новому выдаётся invite для установки пароля, готовому — join. Join принимает только вошедший получатель с тем же Account и CSRF/Origin. Join нельзя использовать в redeem/reset пароля; wrong account, expiry и повтор отклоняются. Manager назначает только чистый coach grant и не меняет administrator/manager. При повторной выдаче pending-приглашения предыдущие ссылки прекращают действие. Перевыдача pending готового входа также выдаёт только join; вид ссылки возвращается клиенту явно. После изменения ролей/отзыва сессии перечитываются; права разных клубов объединяются только явно.

Для нового владельца сначала пригласите сотрудника в один из клубов; после установки входа укажите его проверенный login в настройках сети. Назначение владельца — явное организационное решение. Логин не связывает автоматически карточки людей или семьи. Короткие одноразовые ссылки передаются вручную; интеграция уведомлений не заявляется готовой.

## Миграции, аудит и запуск

Runtime требует schema **8**. Новые goose 00005/00006/00007/00008 добавляют people/athletes/guardian_links/households/members/private registry_operations и organization networks/owners/platform administrators/audit. Применённые 00001–00004 не меняются. FORCE RLS, составные tenant FK и FK primary link → именно этот Athlete действуют в PostgreSQL. Runtime не владеет таблицами, не получает DELETE/DDL/TRUNCATE/audit write/read или BYPASSRLS. Discovery definer функции имеют fixed search_path и возвращают только полномочия/организационные метаданные. Аудит хранит actor/request/action/type/id/time без имён, телефонов, токенов или снимков. Private OperationResult содержит ответы отдельно от аудита и не выдаётся без текущей проверки прав/ссылок/версий/периодов. Очистка production результатов не придумана.

Первый платформенный администратор создаётся **только явной операторской командой** с migration credential, отдельно от HTTP startup:

```sh
go run ./cmd/platform-bootstrap -login synthetic.platform
```

Команда читает MIGRATION_DATABASE_URL из среды, возвращает одноразовый token/expires_at для закрытого synthetic контура; secret нельзя коммитить/логировать/передавать в чат. Откройте локальную форму установки пароля по fragment-ссылке, затем войдите с этим login. Повтор возможен только для того же ещё не активированного первого администратора. Действующего администратора/обычную клубную роль команда не повышает. Последующие platform grants выдаются через панель действующего администратора; последний защищён. VPS, опубликованные релизы, эксплуатационные секреты и рабочие тома этим PR не меняются; rollout/restore отдельно #24.

Команды реестра хранят operation_id по tenant/actor и canonical v1/type/target/payload/base_version. Эффект, результат и metadata audit атомарны. Повтор совпавшего успешного результата возможен только пока все возвращаемые ссылки/версии/периоды актуальны; иначе 409 без старых контактов. Терминальный конфликт версии сохраняется и не применяется позднее; для разрешения нужен новый ID. Неизвестный сетевой результат реестра можно повторить тем же ID/payload. Сетевые POST пока не имеют operation_id: интерфейс не повторяет их автоматически, при неизвестном ответе сначала обновляют список. При неизвестном результате UI держит исходный ID/payload только в памяти и предлагает явный повтор; новые команды блокируются до известного ответа. При переключении клуба/выходе этот временный контекст очищается. UI не сохраняет контакты/токены в browser storage и не объявляет offline/PWA готовыми.

## Проверки

`make check-db` — disposable PostgreSQL 18.3: upgrade/repeat, реальные admin/migrator/runtime LOGIN, RLS/FK/metadata audit, права/отзыв/конкуренция, сохранение старых access сценариев и новые сеть/платформа/registry. `npm --prefix api run check`, `check:routes`, `check:swagger` — схемы/примеры/TS/реальные chi маршруты/Swagger. Capture `JUDEOS_TEST_RESPONSE_FILE` для Go HTTP tests можно проверить `check:postgres-responses`; файл приватный, только synthetic, не коммитится. Opt-in `TestRegistryBrowserFixture` читает только JUDEOS_TEST_* и JUDEOS_BROWSER_FIXTURE_DIR с приватным тестовым TLS сертификатом, пишет fixture.json; `check:registry-browser` использует его и проверяет HTTPS → UI → API → PostgreSQL. CA должен быть доверен; TLS bypass запрещён. Обычный test fixture пропускается без явной среды.

Effective membership сохраняет ID прямого активного назначения; область только из owner/platform имеет read-only клубный scope ID и authority_source. Staff-команды по-прежнему принимают ID реального staff ряда из listStaff/coaches; виртуальную область нельзя редактировать через changeStaffAccess.
