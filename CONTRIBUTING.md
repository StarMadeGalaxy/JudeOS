# Совместная разработка JudeOS

Рекомендуемый процесс для двух разработчиков: общий репозиторий, короткие ветки от основной ветки, Pull Request и ревью второго разработчика. Прямые изменения основной ветки и force-push в общие ветки не использовать. После появления CI включить обязательные проверки и защиту основной ветки. Это предлагаемая договорённость; настройки GitHub ещё не выполнены.

## Варианты

| Вариант | Когда выбирать | Как работать |
|---|---|---|
| Общий репозиторий + ветки + PR | Два доверенных разработчика с правом записи; рекомендуемый старт | Владелец приглашает коллегу в Collaborators; каждый работает в своей ветке, другой проверяет PR |
| Fork + PR | Нет права записи либо нужен независимый репозиторий | У каждого свой fork; origin указывает на fork, upstream на StarMadeGalaxy/JudeOS; изменения идут через PR |
| Git worktree поверх любого варианта | Несколько одновременных задач Codex на одном компьютере | Отдельная ветка и каталог на каждую задачу; worktree не заменяет PR и не синхронизирует компьютеры |

## Общий контекст для Codex

Git хранит документы и код, но не переносит автоматически историю чатов или память Codex. На другом компьютере клонируйте репозиторий и откройте его каталог как проект Codex. Начальный запрос: «Прочитай AGENTS.md, planning/README.md, planning/DECISIONS.md, planning/STATUS.md и CONTRIBUTING.md. Проверь git status. Продолжи задачу <номер Issue> в отдельной ветке. Не превращай рекомендации в утверждённые требования».

Планирование находится в planning/, дизайн — в DESIGN.md и design-system/. Оригинальные материалы перенесены снимком от 7 октября 2026 года; исторические ACTIONS.md и README.md описывают состояние на момент написания. Они не подтверждают выполненную загрузку этого пакета в GitHub. Актуальная передача отмечается в STATUS.md после push.

## Рабочий цикл

1. Создать Issue: цель, границы задачи, критерии готовности, затрагиваемые документы/API.
2. Обновить основную ветку через git pull --ff-only и создать свою ветку: feat/<issue>-<name>, fix/<issue>-<name> или docs/<name>.
3. Согласовать API-контракт перед параллельной работой над backend и frontend. Миграции координировать отдельно, чтобы не создавать одинаковые номера.
4. Выполнить задачу, обновить связанные документы, провести подходящие проверки.
5. Отправить ветку и открыть PR с результатом и проверками. Второй разработчик проверяет код и бизнес-сценарий; проверка Codex помогает ревью, но не заменяет договорённость команды.
6. После merge обновить локальную основную ветку. Продолжение задачи на другом компьютере требует commit и push рабочей ветки, затем fetch/checkout там.

Первое разделение: совместно согласовать модель данных и API; один разработчик делает Go/PostgreSQL и сценарий доступа, другой — мобильный интерфейс журнала по тому же контракту. Финансовую интеграцию начинать после получения фактических форматов iPay. Подробная последовательность — planning/NEXT-STEPS.md.

При конфликте DECISIONS.md или ADR сверить смысл вместе, не выбирать механически одну сторону. Не редактировать одни и те же файлы из двух задач в одном checkout; использовать отдельные worktree.

## Что передавать

После push достаточно ссылки на ветку/PR. Если репозиторий закрытый, коллегу должен пригласить владелец. До push можно передать JudeOS-onboarding.zip: он содержит документы и дизайн без исходных synced sources, историю чата и внешнюю память не включает. Доступность и видимость GitHub-репозитория пока не проверены; документы содержат внутреннее планирование клуба.
