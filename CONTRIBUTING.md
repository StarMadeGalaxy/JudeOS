# Совместная разработка JudeOS

Согласованный процесс для двух разработчиков: общий репозиторий, GitHub Issues, короткие ветки от основной ветки, Pull Request и ревью второго разработчика. Прямой push в main и force-push не использовать. Защита main пока выключена; после появления CI нужно включить обязательные проверки вместе с защитой ветки. Проверенное состояние и остающиеся настройки описаны в [planning/STATUS.md](planning/STATUS.md).

## Варианты

| Вариант | Когда выбирать | Как работать |
|---|---|---|
| Общий репозиторий + ветки + PR | Два доверенных разработчика с правом записи; рекомендуемый старт | Владелец приглашает коллегу в Collaborators; каждый работает в своей ветке, другой проверяет PR |
| Fork + PR | Нет права записи либо нужен независимый репозиторий | У каждого свой fork; origin указывает на fork, upstream на StarMadeGalaxy/JudeOS; изменения идут через PR |
| Git worktree поверх любого варианта | Несколько одновременных задач Codex на одном компьютере | Отдельная ветка и каталог на каждую задачу; в облачной среде дополнительный worktree создаётся только по явному запросу |

## Общий контекст для Codex

Каждый разработчик использует свой аккаунт ChatGPT/Codex и изолированное облачное окружение JudeOS. Git хранит документы и код, но не переносит автоматически историю чатов, рассуждения агентов или память Codex. Нельзя предполагать доступ к окружению коллеги. Если общая конфигурация среды недоступна, отдельное окружение для того же репозитория подходит для работы.

В облачной среде используйте существующий checkout, без дополнительного клонирования; дополнительные worktree создавайте только по явному запросу. Перед работой проверьте git status, ветку и HEAD, сохраните существующие изменения. На другом компьютере без checkout клонируйте репозиторий и откройте его каталог как проект Codex.

Начальный запрос для новой сессии: «Следуй AGENTS.md: проверь git status, ветку, HEAD и прочитай краткий статус. Выбирай остальные документы по задаче. Если задача уже указана, продолжай её; иначе ознакомься без изменений и согласуй конкретную задачу. Не превращай рекомендации в утверждённые требования».

Планирование находится в planning/, дизайн — в DESIGN.md и design-system/. Пакет документов интегрирован в main через [PR #1](https://github.com/StarMadeGalaxy/JudeOS/pull/1). Исторические ACTIONS.md и README.md описывают состояние на момент написания; актуальное состояние передачи отмечается в STATUS.md.

## Issues и канбан

У каждой Issue один ответственный, понятная цель, границы и критерии готовности. Перед началом проверьте назначение, обсуждение и связанные ветки/PR, чтобы не дублировать работу коллеги. Если ответственность неясна, сначала согласуйте её. Задача должна быть указана или согласована с пользователем до реализации.

Планируем GitHub Projects со статусами Backlog → Ready → In progress → Review → Done. Наличие доски, её автоматизаций и права доступа пока не подтверждены. Включённая функция Projects не доказывает, что доска создана. До подтверждения доски статус и результат задачи фиксируются в Issue и PR.

## Рабочий цикл

1. Проверить или создать согласованную Issue: один ответственный, цель, границы задачи, критерии готовности, затрагиваемые документы/API. Убедиться, что её не выполняет коллега.
2. Сохранить существующие изменения, обновить основную ветку через git pull --ff-only и создать одну ветку для задачи: feat/<issue>-<name>, fix/<issue>-<name> или docs/<issue>-<name>.
3. Согласовать и зафиксировать API-контракт или модель данных в репозитории до зависимой работы над backend и frontend. Миграции координировать отдельно, чтобы не создавать одинаковые номера.
4. Выполнить задачу, обновить связанные документы, провести подходящие проверки.
5. Отправить ветку и открыть PR с результатом, проверками и связью с Issue: Closes #12 закрывает её после merge. Второй разработчик проверяет код и бизнес-сценарий; проверка Codex помогает ревью, но не заменяет договорённость команды.
6. После merge обоим разработчикам получить актуальную main в своих checkout. Уже запущенные облачные задачи автоматически не обновляются. Продолжение задачи в другом окружении требует commit и push рабочей ветки, затем fetch/checkout там.

Первое разделение: совместно согласовать модель данных и API; один разработчик делает Go/PostgreSQL и сценарий доступа, другой — мобильный интерфейс журнала по тому же контракту. Финансовую интеграцию начинать после получения фактических форматов iPay. Подробная последовательность — planning/NEXT-STEPS.md.

При конфликте DECISIONS.md или ADR сверить смысл вместе, не выбирать механически одну сторону. Важные результаты сохранять в GitHub: подтверждённые требования — в DECISIONS.md с источником, технические предложения — отдельно с причинами и статусом, результат задачи — в PR и Issue, общий этап и передача незавершённой работы — в STATUS.md. Не приписывать пользователю неподтверждённые решения.

Не редактировать одни и те же файлы из двух задач в одном checkout. На локальном компьютере для одновременных задач использовать отдельные worktree; в облаке использовать изолированные окружения, а дополнительный worktree — только по явному запросу.

Доступ к GitHub сначала проверять операцией чтения через существующую аутентификацию. Возможности коннектора и CLI проверять отдельно; не запрашивать токены или секреты в чате. Для разработки использовать только синтетические данные, без реальных платежей, медицинских документов и персональных сведений.

## Что передавать

После push передать ссылку на Issue и ветку/PR с результатом и проверками. При смене этапа, существенном блокере или передаче незавершённой работы обновить planning/STATUS.md по AGENTS.md. Проверенный репозиторий публичный; для общей работы через ветки требуется право записи. У аккаунта NikishGum оно подтверждено GitHub-коннектором, административных прав нет. Для закрытого репозитория владелец должен пригласить коллегу.

Архив JudeOS-onboarding.zip, упомянутый в историческом пакете передачи, не заменяет актуальный checkout. Чаты и внешняя память в GitHub автоматически не переносятся.

## Инструкция в настройках проекта Codex

Каждый разработчик добавляет у себя короткую инструкцию ниже. Полную копию AGENTS.md в настройки не переносите: общие правила обновляются через репозиторий.

> Источник правил и контекста проекта — репозиторий JudeOS. Перед работой прочитай корневой AGENTS.md и следуй применимым инструкциям. Выбирай документы по задаче согласно AGENTS.md; не перечитывай весь репозиторий на каждое сообщение. Получай актуальный контекст связанных Issues и PR. Обновляй затронутые документы, контракты и миграции; сохраняй решения и результаты по правилам AGENTS.md. При передаче работы сообщай состояние commit, push и PR. История чата не является единственным источником контекста.

Настройки Codex не синхронизируются через Git. После получения изменений коллеги агент перечитывает затронутый контекст. Обсуждения Issues/PR доступны через GitHub-инструменты, а не через git pull.
