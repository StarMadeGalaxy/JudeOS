# Два шаблона — проект 0.1

**Владелец [подтвердил тексты, частичную сводку, исправление/возврат и ручной unknown в T46-01/02](https://github.com/StarMadeGalaxy/JudeOS/issues/46#issuecomment-6095725343).** Версия 0.1 обозначает документ, не активированную рассылку. Поля группировки/свежести/нулевых и неизменившихся проекций ниже — технические предложения до будущей реализации. Правила privacy и границ — [политика](README.md), исходы/активация — [runbook](ACTIVATION.md), [примеры](EXAMPLES.md), точные статусы решений — [APPROVAL](APPROVAL.md). Нет свободного текста из импорта, medical/attendance полей или произвольной рассылки. Это образцы сообщений, не реализация renderer.

## F — распределённая поддержка

```text
Распределённая поддержка · {клуб} · {месяц поддержки}
{разрешённое имя ребёнка}: {текущее распределение} BYN
{Подтверждено / Исправление распределения / Подтверждённый возврат}.
Версия сводки {версия}.
```

На нескольких разрешённых детей повторяется только строка ребёнка. Разные месяцы показываются отдельными блоками с месяцем; клубы не объединяются. `support_month` не выводится из даты поступления. В сообщении нет общей суммы Receipt, нераспределённого остатка, рекомендации/«долга», имени плательщика, bank ID, source payload, списка семьи или данных остальных детей. Нет ссылки, выдающей финансовый реестр. Суммы — точные целые копейки BYN в источнике, на экране десятичная запись `100,00 BYN`.

Предлагаемая единица сводки: одно подтверждённое поступление и его актуальная версия распределений внутри одного клуба; затем проекция только разрешённых пар ребёнок/месяц. Не общая поддержка месяца из разных поступлений. Числовые внутренние ID не нужны тексту получателя; версия позволяет сотруднику отличить исправление. Определение версии должно быть согласовано с принятым #38 до #50, не добавляется в его DTO здесь.

| Триггер | Предлагаемое поведение |
|---|---|
| Подтверждённый Receipt без Allocation, несопоставленная строка, dry run | Нет F; ручной финансовый разбор |
| Первое/частичное подтверждённое распределение | Только актуальная разрешённая распределённая сумма, без остатка; частичное не называется полным |
| Добавление распределения к другому ребёнку | Новая проекция; не уведомлять представителя, чьи разрешённые суммы не изменились |
| Перераспределение / исправление учёта | Та же форма F, новая версия, «Исправление распределения»; это не банковский возврат |
| Подтверждённый внешний возврат / отмена источника | Та же форма F, новая версия, «Подтверждённый возврат» только при доказанном денежном факте и согласованной семантике #38 |
| Полное обнуление ранее показанной разрешённой суммы | Показать `0,00 BYN` с видом исправления/возврата, только если сохраняются текущие права; не молча исчезнувшая строка |
| Возврат не затрагивает разрешённое распределение | Нет персонального изменения F; не раскрывать исходный семейный платёж |
| Меняется рекомендация добровольной поддержки | Нет F и нет просьбы заплатить |

По T46-02 старые ещё не отправленные версии заменяются актуальной, unknown разбирает manager. Номер версии не утверждает прочтение старой. Ранее принятое сообщение не редактируется/не удаляется автоматически; при новом подтверждённом изменении создаётся явная актуальная сводка. Если прежняя версия ещё не отправлена, она признаётся устаревшей и заменяется текущей после новой проверки. Если исход прежней попытки unknown, сначала ручной разбор: новая версия не обходит неопределённость. Нулевой результат допустим только для изменения ранее существовавшего распределения, а не как уведомление о пустом импорте.

Сверка с принятым #38/PR112: `refund` — денежный возврат, `recording_correction` — исправление учёта, `source_cancel` — отдельный вид отмены источника. Название последнего нельзя молча приравнять к возврату; его отображение и нулевые проекции — технический вопрос до #50. Это сохраняет принятую модель #38 и не добавляет финансовую команду.

Фраза «Подтверждённый возврат» не означает, что JudeOS сам отправил деньги: инициирование банковского возврата не входит в #46. Отличие source_cancel/refund/recording_correction повторно уточняется по принятому #38; если соответствие тексту не установлено, событие остаётся выключенным/на разборе.

## S — перенос или отмена

```text
Изменение занятия · {клуб}
{группа} · было: {исходная дата и время}
{Перенесено: новая дата и время, зал / Отменено}.
Версия изменения {версия}.
```

Время показывается в Europe/Minsk с датой; изменение зала отражается в новой сводке. Перенос сохраняет Session ID по контракту #30; политика не создаёт новый Session. Отмена и перенос — варианты одного шаблона S, не отдельные виды рассылки. В сводке нет списка детей, посещаемости, болезни, имени/контактов других представителей и свободной причины отмены. Название группы/зала раскрывается только в разрешённой области текущего занятия и roster.

Несколько переносов до первой отправки: только последнее актуальное состояние занятия; исходное время идентифицирует занятие, последняя версия задаёт новое время. Уже отправленная версия не отменяется базой; последующая актуальная версия явно обновляет прежнюю. Отмена после переноса делает ожидающий перенос устаревшим. После конца актуального занятия старое сообщение не отправляется автоматически; случай рассматривает сотрудник. Точный предел свежести и fallback при отсутствии времени требуют ответа перед #49.

Несколько разрешённых детей на одном занятии дают одному Person одну сводку без перечисления детей. Для разных занятий — отдельные сводки; семейный состав не подменяет проверку roster. Полная потеря права до попытки отменяет отправку; получение старого сообщения права на следующие не сохраняет.

## Повтор

После определённого временного отказа без приёма сообщения возможно повторить актуальный разрешённый вариант по правилам #48. `retry_after` соблюдается. Уже принятый message_id не повторяется автоматически. Для неизвестного исхода правила [ACTIVATION](ACTIVATION.md) требуют ручного решения; при разрешённом ручном повторе добавляется строка «Повтор актуальной сводки». Это вариант F/S, не третий шаблон.
