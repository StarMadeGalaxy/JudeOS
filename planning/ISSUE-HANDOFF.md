# Выбор следующей Issue и передача в новый чат

7 октября 2026 года · правило пользователя из [#93](https://github.com/StarMadeGalaxy/JudeOS/issues/93). Применяется перед выбором новой задачи и после подготовки каждого PR. Один чат ведёт одну Issue; новую работу передавать в новый чат. Ревью, исправления и продолжение текущей Issue остаются в её чате. Этот файл — единый порядок; живые статусы находятся в GitHub.

## Перед выбором

1. Прочитать AGENTS/CONTRIBUTING и краткий STATUS, проверить checkout/ветку/HEAD/чужие изменения. Определить текущий аутентифицированный GitHub-login, не брать имя из автора старого коммита.
2. Получить полный актуальный список открытых Issues, включая добавленные вне manifest. Учитывать пагинацию и ограничения инструмента; неполную выдачу не называть анализом всего backlog. Просмотреть цели, этапы, прямые зависимости и блокеры всех карточек; детали и обсуждения читать у готовых кандидатов и их зависимостей. Отложенные гипотезы и обзорные карточки не подменяют исполнимые задачи.
3. Посмотреть последние закрытые Issues и merged PR команды, особенно текущего разработчика. История помогает продолжить знакомый срез, но не вводит постоянного разделения ролей. Проверить приёмку, фактический merge/результат и незавершённые критерии: закрытая без реализации Issue и подготовительный merged PR не разблокируют зависимость автоматически.
4. Проверить открытые PR/ветки, assignee, последние claim-комментарии, Project Status и активные передачи. Пустой assignee сам по себе не доказывает свободу. Текущую чужую работу не перехватывать; если доказательств не хватает, явно обозначить неопределённость и запросить только недостающее подтверждение. Недоступность Projects обрабатывается существующим ручным порядком.
5. Выбрать один готовый свободный шаг, который продвигает ближайший рабочий срез или снимает важный блокер. При равной готовности учитывать продолжение завершённой работы этого разработчика, число разблокируемых задач, конфликты общих файлов и независимость от коллеги. Не выбирать по одному номеру, дате или последнему автору. Для явного поручения пользователя выполнить указанную задачу после проверки, не заменять её автоматически более удобной.
6. Показать номер, прямую ссылку, краткую причину и необходимые условия. Рекомендация ещё не резервирует задачу. При поручении выполнять — assignee и подтверждённый In progress по AGENTS, затем claim/ветка/работа. При ручном режиме дождаться ответа пользователя; не начинать на основании молчания.

Если готовых свободных задач нет, назвать конкретный блокер/PR для ревью и условный следующий шаг. Не придумывать готовность и не брать занятую задачу ради непрерывности цепочки. При недоступности GitHub передать предварительный вариант с ограничением и проверкой в новом чате.

## Один чат — одна Issue

После выбора и подтверждения задачи назвать текущий чат `Issue #N — краткое название`. После создания PR переименовать его в `PR #M · Issue #N — краткое название`. До создания PR номер не выдумывать. Если одна Issue требует нескольких PR, оставить номер Issue и основной/актуальный PR, остальные перечислить в передаче. Если инструмент переименования недоступен, предоставить точное название пользователю.

Новые чаты автоматически не создавать без явного поручения пользователя. Дать готовый промпт, который пользователь вставит в новый чат проекта. Уже существующие многоцелевые чаты не разбивать и не переименовывать массово; использовать правило с текущей выбранной задачей. История чата не заменяет GitHub/репозиторий.

## После каждого подготовленного PR

Обновить результат/проверки/ограничения в Issue/PR и необходимую передачу в STATUS. Сообщить ссылку на PR и требуемый Review; не заявлять merge, Done или приёмку без доказательств. Затем повторить анализ актуального backlog и предложить **одну** следующую Issue с короткой причиной и самостоятельным промптом. Если PR ещё открыт, отдельно указать, можно ли следующий шаг выполнять независимо или он ждёт принятия/merge. После merge/закрытия при продолжении чата актуализировать рекомендацию.

Не назначать заранее следующую Issue, не менять её Status и не начинать предметную работу в завершаемом чате. Новый чат проверяет занятость повторно: рекомендация может устареть за минуты. Не переносить старое ручное подтверждение In progress на другую Issue. В финальном ответе рекомендация и промпт обязательны, даже если следующий шаг условный или готового шага нет.

## Шаблон самостоятельного промпта

Подставлять реальные номера/названия/ссылки и фактические условия; не оставлять пользователю собирать ссылки по истории чата.

```text
Проект JudeOS, GitHub StarMadeGalaxy/JudeOS. Рекомендуемая задача: Issue #N — название, https://github.com/StarMadeGalaxy/JudeOS/issues/N.
Предыдущий результат: PR #M — ссылка; состояние на момент передачи: открытый/merged, что подготовлено и какие ограничения остались.
Почему следующий шаг: краткая причина и условия готовности; не считать открытый PR принятой зависимостью.
Следуй AGENTS.md, CONTRIBUTING.md и planning/ISSUE-HANDOFF.md. Проверь git status, ветку, HEAD, получи актуальную main без потери чужой работы; прочитай краткий STATUS и документы по задаче. Повторно проверь все открытые Issues, последние закрытые задачи/merged PR команды и текущего GitHub-пользователя, зависимости, обсуждения/claim и занятость. Если рекомендация устарела или задача занята, предложи актуальный свободный шаг и объясни замену.
До работы назначь выбранную Issue текущему GitHub-пользователю и подтверди In progress. Если Projects API недоступен, дай прямую ссылку/исполнителя и дождись ручного подтверждения пользователя. Не начинай раньше.
Назови чат «Issue #N — название» после выбора и подтверждения. Выполни только объём этой Issue, одна ветка/PR, подходящие проверки и документация. Не расширяй MVP, не используй реальные данные и не объединяй PR автоматически. После создания PR переименуй чат «PR #M · Issue #N — название», укажи результат/проверки и ручной Review при необходимости. Повторно выбери следующую свободную готовую задачу и дай её номер, причину и готовый промпт для отдельного чата; заранее её не резервируй.
```

Не копировать секреты, расшифровки диалога или устаревшие списки статусов. Полезный контекст — ссылки на интегрированные решения, принятый контракт, открытый блокер и проверенный результат. Передача достаточно подробна для нового агента, но не дублирует спецификацию Issue.
