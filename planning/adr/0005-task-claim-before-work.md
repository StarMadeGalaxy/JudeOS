# ADR 0005: резервирование задачи до начала работы агента

Дата: 7 октября 2026 года. Статус: **принят** по прямому поручению пользователя. Источник: [U2026-10-07-CLAIM-01](../DECISIONS.md); задача [#76](https://github.com/StarMadeGalaxy/JudeOS/issues/76).

## Контекст

Два разработчика и их агенты работают в отдельных окружениях. Начало анализа решения не отражалось в Project, поэтому другая сессия могла выбрать ту же задачу. Назначение только перед коммитом слишком поздно; локальный журнал не показывает актуальную занятость в Web.

## Решение

Каждый запрос на выполнение требует обязательного резервирования до предметного анализа, изменений и тестов. Разрешено минимальное чтение для определения поручения, зависимостей и свободной Issue. Получить текущий login из аутентифицированного GitHub-канала, проверить Issue/Status/claims/PR, назначить этого пользователя единственным assignee и выставить карточке существующего Project #1 In progress. Проверить результат чтением, записать исполнителя и уникальный chat/run ID в claim-комментарий. После этого выполнять задачу.

Правило действует во всём репозитории через корневой AGENTS.md для обоих разработчиков, включая Codex Web. Нельзя фиксировать один login для всех сессий или выводить его из git author/владельца репозитория. Для продолжения проверить собственный claim и фактическое назначение; не создавать дубликаты. Несколько чатов одного аккаунта тоже различаются по claim/ветке. Полный протокол — [CONTRIBUTING.md](../../CONTRIBUTING.md#резервирование-задачи-до-начала-работы).

Чужую занятую задачу не перехватывать. При отсутствии API/прав не объявлять локальную пометку заменой Status и не начинать основную работу; сообщить точный частичный результат и получить исправление доступа/ручную установку с подтверждением. Готовый PR переводится в Review; Done после приёмки/merge. Пауза и передача явно описываются в Issue.

## Альтернативы и последствия

Только сообщение в чате или локальный manifest не видны коллеге. Назначение перед коммитом не предотвращает дублирование анализа/реализации. Предварительное распределение всего backlog нарушает свободный выбор задач. Автоматический claim только по факту нового PR слишком поздний.

Последовательные GitHub API-операции не дают атомарной блокировки. Проверка перед записью/после записи и уникальный claim снижают риск, но при конкурирующих назначениях оба агента должны остановиться и согласовать одного исполнителя. Нельзя обещать техническую невозможность коллизии без отдельного сервиса блокировок. Такой сервис здесь не реализуется.

Ограничение доступа к Projects теперь блокирует старт основной работы; исправлять его нужно до реализации. Скрипт общей синхронизации backlog не резервирует задачи и сохраняет активные статусы. Личные глобальные настройки чужого аккаунта не меняются; старый Web-checkout требует получения новой main и повторного чтения инструкций.

## Уточнение ручного режима — Issue #79

По дальнейшему поручению пользователя ручное резервирование оформляется первым компактным сообщением после выбора: ссылка/номер/название Issue, текущий исполнитель, результат назначения и требуемый In progress. Агент ждёт явного ответа или скриншота; «нет»/молчание не разрешают начало. Когда Projects API недоступен, подтверждение пользователя разрешает продолжить, а источник подтверждения фиксируется в Issue. Для того же неизменившегося продолжения не требуется повторно двигать карточку. [Шаблон](../../AGENTS.md#первое-сообщение-при-ручном-резервировании).
