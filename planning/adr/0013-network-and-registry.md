# ADR 0013: реестр людей и явный сетевой доступ

Дата: 9 октября 2026. Статус: технический вариант для независимого review #27. Бизнес-объём подтверждён владельцем в чате #27; [источник](https://github.com/StarMadeGalaxy/JudeOS/issues/27#issuecomment-6082017900), [согласование границы с #21](https://github.com/StarMadeGalaxy/JudeOS/issues/21#issuecomment-6082018467). Этот ответ отклоняет предложенную отсрочку единого входа; #21 дополняется в #27, а не объявляется уже реализованным сетевым механизмом.

## Решение

Сеть имеет стабильный ID; каждый её клуб хранит явную принадлежность. Отдельное сетевое назначение владельца даёт эффективную роль administrator только в клубах этой сети. Роль administrator одного клуба сама сетевого доступа не создаёт. Создание сети — явная команда действующего администратора выбранного ещё не связанного клуба, включающая только этот клуб. Другие существующие клубы автоматически не присоединяются. Создание новых клубов выполняется внутри разрешённой сети. Передача клубов между сетями не входит в этот поток.

Один глобальный вход и серверная сессия сохраняются. Discovery возвращает объединение прямых клубных назначений и явно выданного сетевого доступа. Каждый предметный запрос по-прежнему проверяет актуальную сессию/права и работает в транзакции конкретного клуба с FORCE RLS; составные FK не становятся межклубными. Сетевые настройки также имеют RLS и отдельный metadata-only аудит. Смена/отзыв прав сериализуются с командами; последний действующий владелец защищён.

Администратор назначает менеджеров/тренеров. Менеджер имеет отдельную команду назначения/отзыва только coach в своём клубе; она не позволяет повысить себя, менять administrator/manager или чужую сеть. Уже настроенный вход присоединяется к новому клубу через одноразовое приглашение, которое принимает вошедший получатель. Такой токен нельзя использовать для смены пароля; login отправителя не является доказательством личности получателя. Старый install/reset поток #21 сохраняется.

Person/Athlete независимы от входа. Имена/телефоны не уникальны; ручного автоматического merge нет. Семьи/члены семьи имеют собственные ID и периоды, не дают доступ. GuardianLink имеет ручную проверку, основание/период/автора и отзыв; основная связь одна и необязательна. Истечение/отзыв/архив человека скрывают контакт без fallback. Архив Person каскадно архивирует его Athlete и отзывает связи с этим человеком; архив Athlete не удаляет Person. История сохраняется в административном реестре и metadata audit, без автоматического бессрочного срока. Account-профили не связываются автоматически, поэтому архив не отзывает независимые рабочие права сотрудника; кабинеты parent/athlete остаются выключены.

Команды реестра используют operation_id и версии; эффект/результат/аудит атомарны. Replay проверяет текущие права и актуальность всех возвращаемых объектов, не раскрывает прежние контакты после отзыва. Отдельные семьи и стабильный Athlete ID достаточны для S2; правила скидок/порядок детей/платежи появляются в S2, не выдаются за готовые.

## Уточнение платформенного администратора

[Источник](https://github.com/StarMadeGalaxy/JudeOS/issues/27#issuecomment-6082178440), [граница с #21](https://github.com/StarMadeGalaxy/JudeOS/issues/21#issuecomment-6082178906).

Ответственный за настройку — отдельный администратор платформы с панелью всех сетей, по прямому уточнению владельца в чате #27. Первоначальное платформенное полномочие выдаётся только явным операторским bootstrap, не HTTP startup и не обычной клубной ролью. Панель управляет сетями/клубами/назначениями владельцев; владелец самостоятельно персонализирует собственную сеть. Платформенная настройка не превращает телефон/семью в доступ и не объединяет клубные профили; RLS/составные FK сохраняются. Обычные клубные API продолжают проверять самостоятельные разрешения; платформенные действия имеют собственную проверку и metadata audit.

## Последствия и проверки

Новые миграции 00005/00006/00007/00008/00009/00010/00011, применённые 00001–00004 не переписываются. Только synthetic. Проверяются upgrade/repeat, разные LOGIN, RLS/составные FK/аудит/отзыв/конкуренция, чужие сети, manager→coach, consent готового входа, последний владелец, OpenAPI/runtime/TS/Swagger и рабочие browser-потоки. Новая schema требует отдельного согласованного rollout; VPS/release/secret/working volumes и production/restore #24 не затрагиваются. Независимый review технического варианта остаётся условием merge.

Практические правила, схема11, bootstrap и browser checks — [docs/people](../../docs/people/README.md). Parent/athlete кабинеты, данные реального пилота, network transfer и rollout не входят в выполненный срез.

## Уточнения независимого review #111

Миграция00009 закрывает захват общего входа через прежний клубный reset: выдача/redeem разрешены только входу без owner/platform и назначений других клубов (активных либо действующих pending). Под account lock оба этапа заново проверяют область. Общий recovery для расширенной области добавлен последующим прямым поручением в разделе ниже. Полностью отозванный ready-account с действующим pending join может получить password-authenticated сессию без клубных прав только для собственного согласия; без приглашения вход запрещён.


## Базовое восстановление общего входа без email

По [прямому поручению владельца](https://github.com/StarMadeGalaxy/JudeOS/issues/27#issuecomment-6084409663), DECISIONS U2026-10-09-S1-27-RECOVERY,00010 добавляет отдельные глобальные recovery tokens и append-only metadata audit с FORCE RLS. POST platform/password-recovery требует текущей platform-сессии/CSRF и явного утверждения внешней проверки человека; club administrator и network owner эту возможность не получают. Token TTL30m, raw secret только в ответе, повтор заменяет прежний. Получатель устанавливает пароль через прежний public/preauth redeem. При использовании повторно проверяются recipient/issuer полномочия; отзыв platform-роли окончательно гасит её ссылки. Права/назначения не активируются, сессии/старые ссылки погашаются атомарно с audit. Rare global recovery берёт platform→ordered network→ordered club→account locks, hashing до транзакции; это сознательная простая сериализация S1.

Operator-only cmd/platform-recovery с migration connection может выдать ссылку только готовому действующему platform administrator, после --identity-verified и с символическим operator-ref. Нельзя создать/повысить/реактивировать вход. Runtime не имеет EXECUTE на операторскую/internal функции и прямого доступа к токенам/аудиту. Все capabilities имеют fixed search_path, PUBLIC EXECUTE отозван. [Подробный контракт/команда/ограничения](../../docs/access/RECOVERY.md). Альтернатива ручной правке hash отвергнута: она обходит отзыв ссылок/сеансов и audit. Self-service email/Telegram/recovery codes откладываются, поскольку сейчас нет заранее проверенного канала. Это технический вариант на независимое review; поручение реализации не заменяет приёмку ADR/CI/PR.

Независимое review recovery выявило: прежний local reset не гасил ранее выданный global recovery. Не переписывая проверенную00010,00011 добавляет trigger на фактическую смену password_hash; под уже удержанным account lock он consumes все recovery получателя без новых advisory locks/инверсии порядка. Enclosing local/global reset остаётся атомарным с audit. Выдача повторно проверяет issuer session после ожидания target lock. Регрессия global-issued→local-reset→old-global rejected обязательна.
