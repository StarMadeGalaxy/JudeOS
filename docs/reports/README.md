Состав из [плана §6](../../planning/MVP-DEVELOPMENT-PLAN.md) подтверждён владельцем ответом [«Я владелец, эти отчёты подходят»](https://github.com/StarMadeGalaxy/JudeOS/issues/38#issuecomment-6085573173). **Это не восстановление неизвестного D61.** Подтверждены четыре назначения отчётов; поля/фильтры/формулы и ограничения ниже остаются предложениями; [реестр источников и открытых пунктов](APPROVAL.md). ## Общая семантика выборок

Все отчёты требуют выбранный клуб и действующие права; фильтр никогда не расширяет scope. Club-local даты Europe/Minsk преобразуются в UTC, интервалы `[from,to)`, месяц — `YYYY-MM`. `as_of` — включительная граница снимка: факт виден, если `recorded_at <= as_of`, а денежное событие также `occurred_at <= as_of`. Allocation/Change видны по recorded_at; snapshot рекомендации — по recorded_at/version. Данные не вычисляются из сегодняшних семьи/группы/контактов. Поздняя запись с более ранней датой события не переписывает уже выданный снимок. Исправления посещения/состояния Session используют последнюю сохранённую версию на as_of; текущие права проверяются независимо от исторической даты.

В синтетическом примере срез конца31 октября задан точно: `2026-10-31T20:59:59.999999Z` (23:59:59.999999 Europe/Minsk), до исключительной границы периода `2026-10-31T21:00:00Z`. Факт ровно на границе принадлежит ноябрю; время среза не подменяется округлённой датой.

Ответ/экспорт включает `report_id`, `definition_version`, `tenant`, нормализованные фильтры, `as_of`, `generated_at`, currency для денежных величин, число строк/полный итог, предупреждения несверенных источников. `as_of` не позже времени выдачи; отчёт за будущий период/неполный месяц явно помечается. Для повторения исторического снимка нужны сохранённые версии и действующие права. Метаданные среза CSV выдаются отдельными фиксированными колонками, а не невалидными строками перед заголовком.

Фильтры `group/venue/coach` в посещаемости относятся к сохранённому занятию/roster. В поддержке фильтр группы, если включён, означает членство Athlete **на первый день support_month**, использует DISTINCT Athlete и подписан этим правилом; посещение нескольких групп не умножает деньги. Такой фильтр не используется для денежного контроля Receipt. Экспорт ограничен 12 месяцами/10 000 строками/5 MiB/10 секундами по техническому предложению, без молчаливого truncation; поле суммы — целые копейки BYN. Имя/сырой payer/contact/медицинские причины не выгружаются сверх разрешённого минимума.

Финансовые выгрузки R2–R4 — **только владельцу** в его разрешённом клубе, [источник «только владелец»](https://github.com/StarMadeGalaxy/JudeOS/issues/38#issuecomment-6085799340). Чтение и ручные финансовые действия manager не отменены, но права просмотра не дают финансовый экспорт. R1 сохраняет отдельный scope журнала/назначений; ответ о финансовом экспорте не расширяет и не отменяет его правила. Минимизация полей/CSV и технические лимиты остаются детализацией для независимого review.

## R1 — Посещаемость

**Вопрос:** сколько участий было и насколько полно отмечен журнал? Единица исходного факта — `(tenant, session_id, athlete_id)` в сохранённом roster; не число групп ребёнка. Неактивные/excluded roster сохраняют историю, но исключаются из обычного знаменателя. Session cancelled исключается целиком из обычных итогов, даже если отметки сохранены; число таких сохранённых участий показано отдельно. Trial/временное добавление — признаки участия, а не пятое состояние Attendance.

**Фильтры:** обязательны даты начала занятия и as_of; необязательны venue, group, coach, Athlete (только при допустимом чтении), state (planned/in_progress/closed). По умолчанию все неотменённые состояния, включая незакрытые; `closed_only` явно меняет выборку. Coach-only получает только разрешённые назначенные занятия. Финансовых полей нет.

| Поле | Смысл/формула |
|---|---|
| group/venue или Athlete ID/разрешённое отображение | Выбранный уровень `group/athlete`; одинаковые имена не склеиваются |
| roster_count | N = число допустимых уникальных участий |
| present_count / absent_count / sick_count / unmarked_count | Четыре статуса принятого журнала; отсутствующая Attendance = unmarked |
| marked_count | M = present + absent + sick; N = M + unmarked |
| attendance_percent | `100 * present / M`, если M>0; иначе null/«нет отметок» |
| completeness_percent | `100 * M / N`, если N>0; иначе null |
| trial_count | Число trial в том же N; оно уже включено в остальные счётчики |
| cancelled_roster_count / excluded_roster_count | Контроль сохранённой истории вне N, не скрытый absent |
| open_session_count | Число незакрытых занятий; неполнота видна явно |

Проценты показываются с двумя знаками, half-up; итоги вычисляются из полных счётчиков, **не средним строковых процентов**. «Болел» не создаёт автоматическую скидку. Детальные статусы разрешены в текущей области журнала; обычный экспорт по детям содержит только N/M/present/unmarked/проценты/trial, без именованных sick_count/медицинской причины. Групповой агрегат sick_count — только для administrator/manager; coach export ограничен минимальными счётчиками своей области. Это предлагаемое ограничение экспорта, требует согласования.

Синтетический октябрь: 3 неотменённых занятия × 3 участника, всего9; present3, absent2, sick2, unmarked2; M7, посещаемость42.86%, полнота77.78%, trial1. Отменённое занятие с сохранённым присутствием: cancelled_roster_count1, в N не входит. Есть одна excluded строка: excluded_roster_count1, в N не входит. Две незакрытых записи не превращаются в absent. Пустой допустимый roster даёт N0 и оба процента null.

## R2 — Рекомендации и распределённая поддержка по детям/месяцам

**Вопрос:** какая рекомендация была зафиксирована, сколько подтверждённых денег отнесено к месяцу и какова разница? Не отчёт о долгах и не кассовый оборот месяца.

**Фильтры:** обязательны support_month (диапазон до12 месяцев) и as_of; необязательны Athlete, Household snapshot ID, group с указанной выше семантикой, «есть разница», «нет рекомендации», «архивные». По умолчанию исторические строки месяца включают архивных участников с фактами. Household — фильтр сохранённого снимка, не текущая семья и не право просмотра. Coach-only не имеет доступа.

| Поле | Смысл/формула |
|---|---|
| Athlete ID/минимальное имя, support_month | Один Athlete × месяц, даже при нескольких группах/Receipt |
| recommendation_id/version, policy_version, family_snapshot/order | Происхождение рекомендаций; контактов/Account нет |
| base_kopecks / adjustment_kopecks / recommendation_kopecks | B, применённое уменьшение C≤B, Q=max(0,B−C) из сохранённого снимка |
| allocated_gross_kopecks | Сумма Allocation этого Athlete/месяца на as_of |
| allocation_released_kopecks | Компенсации этих Allocation: возврат/перераспределение/освобождение |
| allocated_net_kopecks | P=gross−released≥0, независимо от даты Receipt |
| difference_kopecks | Q−P, **знаковое**; положительное «ниже рекомендации», отрицательное «выше рекомендации», не долг |
| recommendation_state | recorded/missing; при missing Q/difference=null, не0 |

Набор строк — объединение зафиксированных рекомендаций и распределений. Распределение без рекомендации не теряется; итог P включает его, итог Q только известные рекомендации, число missing подписано. Общая difference для неполной рекомендации=null; отдельно можно показать difference по complete rows с явной подписью. Если нет ни факта ни рекомендации, строка не выдумывается; неполнота рекомендаций — отдельное предупреждение.

Семейный пример: базовые11000/8800/7700/0/0, сумма27500; уменьшение6000 после льгот применено сначала к первому ребёнку — [подтверждённый владельцем пример](https://github.com/StarMadeGalaxy/JudeOS/issues/38#issuecomment-6085728153) → рекомендации5000/8800/7700/0/0, сумма21500. Уменьшение30000 даёт итог0 и неиспользованные2500, не отрицательную сумму. При смене семьи в ноябре октябрьский снимок остаётся прежним.

| Синтетический Athlete / октябрь | Рекомендация | Gross allocations | Компенсации | Net allocated | Разница |
|---|---:|---:|---:|---:|---:|
| A | 5000 | 26000 | 2000 | 24000 | -19000 |
| B | 8800 | 12800 | 4000 | 8800 | 0 |
| C | 7700 | 0 | 0 | 0 | 7700 |
| D | 0 | 0 | 0 | 0 | 0 |
| E | 0 | 0 | 0 | 0 | 0 |
| **Итого** | **21500** | **38800** | **6000** | **32800** | **-11300** |

В P входят сентябрьское R4/11000, отнесённое на октябрь, но **не** ноябрьское распределение3000 из октябрьского R2. Значение P32800 поэтому не должно равняться октябрьскому денежному итогу31000. В обычном UI: 215.00 BYN и 328.00 BYN; −113.00 BYN — разница, без ограничения посещения.

## R3 — Реестр поступлений и возвратов/исправлений

Два явно выбираемых режима одного отчёта. По умолчанию — **движения**; «остатки когорты» показывают распределение денег выбранных Receipt. Смешивать эти итоги нельзя.

**Движения:** фильтр occurred_at события `[from,to)` + as_of, source kind/provider account, вид (`receipt/refund/source_cancel/recording_correction`). Строка = одно подтверждённое денежное событие; возврат попадает в период своего подтверждённого события, даже когда Receipt старше. Поля: event ID/type, Receipt ID, событие/запись, источник/evidence reference (без сырья), gross receipt/refund/cancellation/correction_kopecks, signed_effect_kopecks, actor, reason_code. Плательщик по умолчанию отсутствует. Итого: `cash_gross − cash_refunds − source_cancellations − recording_corrections = net_accounted_movement`. Не называть net банковской выплатой; комиссии/банковские даты не установлены. Recording correction выделяется отдельно от денег фактического возврата.

**Остатки когорты:** фильтр даты события **исходного Receipt** `[from,to)` + as_of, source/provider account, состояние (confirmed/partially/fully reversed), «есть остаток». Одна строка = Receipt. Поля: Receipt ID, occurred_at/recorded_at, source, G, V по видам, N, A всех детей/месяцев на срезе, U, состояние/version, warning. Формулы [контракта](../finance/CONTRACT.md): N=G−V=A+U. При фильтре Athlete/support_month показывается отдельная отобранная сумма allocations, а денежный контроль всё равно использует **все** allocations выбранных Receipt. Суммы не умножаются JOIN по распределениям. При фильтре «есть остаток» итог только по оставшимся строкам, фильтр указан.

| Октябрьская когорта / срез31 октября | G | V | N | A (все месяцы) | U |
|---|---:|---:|---:|---:|---:|
| R1 | 20000 | 0 | 20000 | 19800 | 200 |
| R2 | 9000 | 3000 | 6000 | 5000 | 1000 |
| R3 | 5000 | 0 | 5000 | 0 | 5000 |
| R5 | 4000 | 4000 | 0 | 0 | 0 |
| **Итого** | **38000** | **7000** | **31000** | **24800** | **6200** |

Движения октября в этом примере тоже38000−7000=31000, но это совпадение выборок. На срез30 ноября R1 получает возврат1000 с компенсацией800; октябрьская когорта N30000=A24000+U6000. **Движения октября остаются31000**: ноябрьский возврат в них не входит. Поздно записанное2 ноября R6/2500 с датой20 октября на срез31 октября исключено; на ноябрьском срезе оно входит в расширенную октябрьскую когорту, поэтому фактический итог всей октябрьской когорты с R6 — N32500=A24000+U8500. Для проверки только прежних четырёх Receipt фильтр IDs явно фиксируется. В пересчитанных движениях октября с поздней записью gross40500/net33500, версия/as_of объясняют изменение.

## R4 — Очередь несопоставленного и нераспределённого

**Вопрос:** что требует разбора и какие уже подтверждённые деньги ещё не отнесены? Две секции, денежные итоги которых **не складываются**.

**Фильтры:** as_of, source/provider account/batch, state/reason, даты received_at для входа, occurred_at для Receipt, возраст в днях; необязательны candidate Athlete только для входа и «без сопоставления/частично распределён». Различие осей подписано. Лимиты срока поиска не заменяют срок хранения. Coach-only доступа не имеет.

| Секция/единица | Поля | Формулы/итоги |
|---|---|---|
| Вход без принятого эффекта / ProviderInput | batch/row, source, received_at, known amount/currency или null, state=`needs_review/conflict/invalid`, reason_code, допустимые candidates, protected source reference | Counts по исходам; суммы только известного BYN отдельно по статусу; unknown_amount_count. Нет Receipt ⇒ нет денег в N/U |
| Подтверждённый остаток / Receipt с U>0 | Receipt ID, источник/дата, G/V/N/A/U, `unmatched/partially_allocated`, связанные input IDs, дата последнего разбора/возраст | Count DISTINCT Receipt и ΣU. Возврат/компенсация отражены на as_of |

Строка импорта с applied Receipt не дублируется в секции «вход»; повторные/применённые строки доступны в контроле пакета, не увеличивают очередь. Несколько inputs одного Receipt не умножают U. Неизвестный внешний возврат/конфликт помечает предупреждение несверенного источника; не добавляется в «подтверждённые возвраты» до применения.

Синтетический B1:8 строк. Applied4/38000, duplicate1/20000, needs_review1/6000, conflict1/9001, invalid1/сумма неизвестна (`110,001`). Число8 сходится; известная исходная сумма73001 =38000+20000+6000+9001. Она не равна подтверждённым Receipt38000 из-за повторов/непринятых строк. Контрольный итог поставщика, если он есть, показывается отдельным значением; в этом синтетическом наборе он **не предоставлен**.

Очередь входа:3 строки, известные суммы6000 и9001 по разным статусам, unknown_amount_count1. Остатки: R1/200, R2/1000, R3/5000, всего3 Receipt/6200. Нельзя показывать «всего денег21201» как сумму очереди и подтверждённых остатков.

## Проверяемые образцы и ограничения

[fixture.json](examples/fixture.json) содержит только вымышленные club-alpha/club-beta, Athlete A–E, условные даты и суммы, без настоящих имён/телефонов/платежей. [expected.json](examples/expected.json) содержит ожидаемые строки и полные итоги четырёх отчётов; [verify_examples.py](verify_examples.py) воспроизводит арифметику как документальную проверку:

```sh
python3 docs/reports/verify_examples.py
```

Это не реализация отчётов/команд и не runtime-проверка доступа/SQL. Проверяются точные суммы/связи/две временные оси, три среза, два клуба, отменённый/excluded roster, zero denominator, семьи1–5/нулевой предел, missing recommendation, исходы импорта и отсутствие двойного счёта. Runtime-проверки при реализации описаны в контракте; реальные iPay/форматы и D61 неизвестны.

Состав четырёх отчётов принят с сохранённым источником; это не утверждение всех режимов/полей/формул/фильтров v0.1. Начало семейного уменьшения с первого ребёнка подтверждено владельцем в примере60 BYN; владелец также подтвердил финансовый экспорт только владельцу. Поля выгрузки/минимизация остаются технической детализацией. Остальная детализация проходит независимое review. «Готово» о Project In progress не утверждает отчёты. Общая матрица прав выровнена по согласованию27/28; замечание независимого review о replay исправлено в финансовом контракте с примером4→5→повтор4. До повторной технической приёмки результат остаётся draft; общие wire/SQL и чужие модели не изменяются.
