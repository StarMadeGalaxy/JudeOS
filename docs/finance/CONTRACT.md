## Термины и деньги

- **Recommendation**: рекомендация добровольной суммы Athlete на календарный месяц поддержки; не счёт к оплате, долг, доступный остаток или факт получения денег.
- **Receipt**: подтверждённый денежный факт из проверенного источника внутри одного клуба. Предложение сопоставления, строка импорта, нажатие плательщика или HTTP 200 таким фактом не являются.
- **Allocation / ReceiptAllocation**: подтверждённая часть Receipt, отнесённая менеджером к Athlete и месяцу поддержки. Распределение не создаёт второе поступление.
- **Reversal / ReceiptReversal**: подтверждённый возврат, отмена источника или исправление ошибочного учёта. Каждая запись указывает вид; исправление учёта не выдаётся за банковский возврат.
- **AllocationChange**: положительная величина отменяемой части конкретного Allocation. Перераспределение — компенсация старой части и новое Allocation атомарно.

Везде обязательна валюта `BYN`. `amount_kopecks` — целое число; 1 BYN = 100 копеек. Предлагаемый JSON-совместимый предел одной суммы/версии: 0…9 007 199 254 740 991; создание Receipt/Allocation/Reversal требует строго положительную сумму. Нулевые рекомендации/остатки допустимы. Ни float, ни отрицательная входная сумма, ни конверсия, ни округление лишнего десятичного знака не допускаются. Это технический предел, не договорный максимум оплаты. SQL в будущей реализации — bigint для строк, проверяемый numeric для сумм; JSON-итог за пределом точного integer отклоняется как слишком большая выборка, а не округляется.

Внешняя десятичная сумма преобразуется целочисленно по **подтверждённому формату источника**. Например, синтетическое `"110,00" → 11000`; `"110,001"`, `NaN`, дробные копейки, иная валюта отклоняются. Предложение синтетического parser не задаёт реальный формат iPay.

`occurred_at` — время подтверждённого денежного события UTC/RFC3339; `recorded_at` — время его записи; дата банковского зачисления, комиссия и выплата банком неизвестны до #17. `support_month` — `YYYY-MM` в Europe/Minsk, не вычисляется из времени оплаты. Поздний сентябрьский платёж может относиться к октябрю; возврат в ноябре может уменьшать октябрьское распределение. Дата без зоны из источника ждёт разбора, зона не угадывается.

## Проект сущностей

Общее для финансовых записей: устойчивый ID, `tenant_id` конкретного клуба, неизменяемое авторство/время, ссылки только внутри этого tenant. Здесь названия полей описывают **логический** контракт, не новый DTO общего OpenAPI.

| Сущность | Обязательные поля и правила | Необязательные поля |
|---|---|---|
| SupportPolicy | ID, version, effective_from/to `[from,to)`, BYN, суммы для порядков 1/2/3/4+ | Основание изменения |
| RecommendationSnapshot | ID, Athlete, support_month, policy/version, family snapshot ID/порядок/действующие периоды, base_kopecks, adjustment_kopecks, final_kopecks, version | Household ID, если семья есть; ссылки на основания корректировок |
| RecommendationAdjustment | ID, target family/athlete, месяц, положительное уменьшение, автор/время/основание | Ссылка на обращение без текста контактов/медицинских данных |
| ImportBatch | ID, source_kind/profile/version, parser_version, source_key, hash, uploader/time, version, status, число строк/контрольные итоги | Ссылка на защищённое сырьё, дата контрольного документа |
| ProviderInput | ID, batch/row key, source identifiers, исходная сумма/валюта/даты, нормализованный результат, status/error code | Candidate Athlete IDs, Receipt ID после проверки, ограниченная ссылка на сырьё |
| Receipt | ID, tenant, amount_kopecks>0, BYN, source_kind, confirmation/evidence reference, occurred_at, recorded_at, actor, version | Provider account + external operation ID в проверенной области; batch/row; минимум сведений плательщика при необходимости |
| Allocation | ID, Receipt, Athlete, support_month, amount_kopecks>0, recorded_at, actor | Recommendation ID, подтверждённое основание сопоставления |
| AllocationChange | ID, Allocation, amount_kopecks>0, kind=`release/reassign/reversal`, actor/time/reason | Reversal ID, ссылка на replacement Allocation |
| Reversal | ID, Receipt, amount_kopecks>0, kind=`refund/source_cancel/recording_correction`, occurred_at, recorded_at, actor/reason, confirmation/evidence | Надёжный внешний refund ID в области источника |
| OperationResult | tenant/actor/operation_id, canonical request hash, effect references, result/version, recorded_at | Безопасная минимальная проекция ответа |

Person ID, Athlete ID и Account ID не взаимозаменяемы. Receipt не обязан иметь Athlete/Household/GuardianLink; payer name не доказывает ни получателя, ни представительство. Семейный платёж распределяется отдельными строками на детей, иногда на разные месяцы. Семья не становится владельцем кошелька; межклубный перенос остатка, валютный учёт и платформенный billing вне этого контракта. Архив Athlete сохраняет финансовые ссылки и доступную историю; разрешённость новых распределений архивному Athlete требует явного разбора, по умолчанию они запрещены.

Снимок рекомендации не пересчитывается при смене семьи. В месяце менеджер фиксирует порядок и применимую версию политики. Семейное уменьшение применяется **после** суммы льготных детских рекомендаций с нижним пределом ноль. Предлагаемый детерминированный способ разнести семейное уменьшение: по сохранённому порядку детей, `min(оставшееся уменьшение, базовая сумма ребёнка)`; неиспользованное превышение явно показывается, автоматически дальше не переносится. Это отдельное предложение, не новая подтверждённая формула D19. Если принят иной способ, образцы/формулы нужно изменить до реализации. Правка прошлого — новая версия с основанием, старый снимок остаётся доступен; Receipt и Allocation от этой правки не изменяются.

## Состояния и происхождение

У Receipt подтверждённая исходная сумма неизменяема. Представление состояния вычисляется: `confirmed` (нет компенсаций), `partially_reversed`, `fully_reversed`. Возврат в ожидании и отказ возврата — записи процесса/источника, не Reversal и не уменьшение денег. Исправление неправильного подтверждённого Receipt компенсирует его и при необходимости создаёт новый связанный Receipt; удаление, UPDATE суммы/валюты и задним числом незаметное переписывание запрещены.

ImportBatch: `received → validated → ready → applying → completed/completed_with_errors`; до применения возможен `rejected`. Это состояния приёма/проверки, не гарантия поступлений. Каждая строка получает один результат: `invalid`, `needs_review`, `ready`, `applied`, `duplicate`, `conflict`, `rejected`. Перепарсинг создаёт новую попытку с parser version и ссылкой на прежнюю; уже подтверждённые деньги не создаются повторно.

1. Проверить размер/тип/кодировку файла и доступ, сохранить защищённый вход и source key.
2. Dry run: проверить строки, точно нормализовать суммы, дать контрольные итоги и кандидатов. Сопоставление неоднозначного имени не автоматическое.
3. Пользователь отдельно подтверждает состав допустимых строк и распределение. Version/hash предпросмотра входят в команду применения. Изменившийся вход требует нового предпросмотра.
4. Применять атомарно **каждую строку** (денежный эффект, история, row result, OperationResult). Частичный пакет допустим и явно обозначен; успешные строки не откатываются удалением из-за соседней ошибки. Возобновление применяет лишь неуспешные строки с прежними ключами.
5. Сверка показывает суммы применённых, повторных, спорных, ошибочных и отклонённых строк отдельно. Контрольный итог поставщика не подменяется суммой выбранных строк; расхождение требует разбора.

`source_key + row_key` предотвращают повтор одного входа, content hash обнаруживает изменённый пакет. Дубликаты файлов разных имён с тем же содержимым проверяются в рамках источника; изменённое содержимое того же source_key — конфликт. Уникальность Receipt по `(tenant, подтверждённый provider account/environment/service scope, external operation ID)` включается только после проверки #17. Одинаковый ключ и одинаковая нормализованная сумма/валюта/семантика — ссылка на существующий эффект; изменённая сумма/валюта/состояние требует новой проверяемой переходной обработки или conflict. Сторно не пропускается как «дубликат оплаты». Без надёжного ID отпечаток только предлагает дубль: два похожих настоящих платежа могут дать два Receipt после ручной проверки. RequestId iPay, имя, телефон, номер строки и Athlete ID не являются универсальным внешним ключом платежа.

## Логические команды и результаты

Это операции предметного контракта, **без назначения HTTP method/path**. Автор/tenant выводятся из текущего доступа, не принимаются произвольно из формы. Общие входы: неизменяемый `operation_id`, версия определения, версия изменяемого агрегата; у операций на деньги — `receipt_id/base_version`.

| Команда | Дополнительные входы | Результат/инвариант |
|---|---|---|
| ConfirmReceipt | source/evidence, сумма/BYN, подтверждённая дата, source key | Новый Receipt либо существующий проверенный эффект; отсутствие evidence остаётся needs_review |
| ApplyImportRow | batch/row, preview version/hash, подтверждённое сопоставление | Атомарный эффект строки + row result; соседняя ошибка не дублирует успех |
| Allocate | Athlete, support_month, положительная сумма, необязательная Recommendation | Allocation, новая Receipt.version, N/A/U |
| ReleaseAllocation | Allocation ID, положительная освобождаемая часть, reason | AllocationChange без Reversal; N неизменен, A уменьшается, U растёт |
| Reassign | Освобождаемые части + новые Athlete/month/amount | Компенсации и новые Allocation в одной транзакции; суммы/остаток проверены |
| RecordReversal | type/сумма/событие/evidence/reason, список Allocation/частей компенсации | Reversal и связанные Changes атомарны; исходные строки сохранены |
| AdjustRecommendation | snapshot/base_version, месяц/точное уменьшение/reason | Новая версия снимка; денежные Receipt/Allocation неизменны |

Результат различает applied/replayed/version_conflict/idempotency_conflict/invalid/forbidden/needs_review, содержит ссылки на эффекты и безопасные текущие версии/суммы при действующем доступе. Машинные HTTP codes/DTO будут определены общей OpenAPI до реализации, не этим документом. Ошибка/rollback не возвращает applied; validation и conflict не расходуют деньги. ID не заменяется автоматически при неизвестном результате.

## Остаток и транзакция

Для одного Receipt на одном согласованном снимке:

```
G = исходная подтверждённая сумма
V = сумма подтверждённых Reversal (все виды отдельно подписаны)
N = G - V                         (чистый подтверждённый учёт)
A = Σ(Allocation.amount - Σ AllocationChange.amount)
U = N - A                         (нераспределённый остаток)
0 <= V <= G; 0 <= A <= N; U >= 0
для каждого Allocation: 0 <= Σchanges <= amount
N = A + U
```

Рекомендация не входит в равенство. Нельзя проверять его на сумме всех Receipt и лишь распределениях одного ребёнка/месяца. Отчёт с таким фильтром показывает отобранную часть отдельно; контроль использует полную когорту Receipt.

Каждая онлайн-команда распределения, перераспределения, возврата, отмены, импорта и будущего job использует один протокол:

1. Проверить сессию/клубные финансовые права. Сериализовать эффект с отзывом права по принятому access-контракту; #27 нельзя предполагать merged. Порядок блокировок: authority по действующему контракту → idempotency key → Receipt в устойчивом порядке ID → их строки. Не блокировать другой Receipt в обратном порядке.
2. Найти/зарезервировать `(tenant, actor, operation_id)` уникальным ключом. Хеш включает вид, цели, суммы, месяц, список компенсаций, `base_version`, версию контракта; один ID с иным payload — конфликт. Проверка полномочий предшествует выдаче сохранённого результата.
3. Заблокировать Receipt (`SELECT … FOR UPDATE` в будущей реализации), прочитать текущую version и все эффекты. Несовпадение `base_version` — конфликт без денежного изменения. Две команды на остаток не используют UI-значение как гарантию.
4. Проверить BYN, положительные/точные суммы, tenant/FK, ссылки и инварианты; для возврата согласовать **явный список** компенсаций. Минимальная освобождаемая сумма `max(0, refund-U)`, можно освободить больше с явным подтверждением; отмена распределений должна покрывать дефицит. Не угадывать ребёнка/месяц для снятия денег.
5. Атомарно записать Allocation/Change/Reversal, историю, увеличение Receipt.version и результат. При сбое откатить всё; сетевое подтверждение успеха — после commit. DB-ограничения и повторная проверка страхуют все пути записи.
6. При потере ответа повторить **тот же ID/payload**; второй эффект не создаётся. После конфликта получить свежую версию и потребовать новое явное решение с новым ID. Автоматический retry с новым ID запрещён.

Возврат с внешним неизвестным исходом не применяется до доказательства. Если внешний источник уже подтвердил возврат, но компенсации не определены, он виден как `needs_review`, с предупреждением о несверенном учёте; исходные подтверждения сохраняются. Документальные отчёты помечают такую очередь, не называют баланс полностью сверенным. После определения компенсаций атомарно принять весь эффект. Внешний запрос возврата не вызывается из DB-транзакции; доступность частичного iPay-возврата не установлена.

Синтетические сценарии: остаток 9000, version4; менеджеры одновременно хотят 6000 и 5000. Один выигрывает, version5/U3000; второй получает version conflict, после обновления 5000 недопустимы. Гонка распределения с возвратом на одном version также даёт один эффект и один конфликт. Повтор победителя с тем же ID не увеличивает суммы. Полный возврат компенсирует все активные распределения и даёт N=A=U=0; частичный — только явно выбранные части.

## История и безопасность

Финансовая история — тип/ID эффекта, tenant, автор, серверное время, денежные величины, версия, ссылка на источник, причина, связи исходной/компенсирующей записи. Неизменяемость фактов не означает бессрочного хранения PII. В технический audit идут IDs/тип/версия/суммы; сырые файлы, телефоны, ФИО плательщика и полные причины не попадают в логи. Причины должны объяснять денежное действие без медицинских подробностей.

OperationResult хранит ключ/хеш/ссылку на эффект так, чтобы очистка полного ответа не позволяла повторное финансовое применение. Сроки сырья, финансовой истории, причин, полных ответов и erasure не придуманы: их утверждают в #18/#24/#52 до реальных данных. После restore смена recovery epoch требует сверки с внешним источником до возобновления импорта/повторов; старый ID не получает новый эффект автоматически.

## Scope, выдача и экспорт

| Субъект | Финансовые записи/команды/отчёты | Посещаемость |
|---|---|---|
| Administrator/manager с текущим разрешением выбранного клуба | Чтение, ручное подтверждение/распределение/компенсации и разрешённый экспорт этого клуба | Область принятого журнала |
| Coach-only | Нет финансовых сумм, payer, списка оплат, остатков или финансового экспорта | Только текущая разрешённая область назначенных занятий; отзыв прекращает чтение/экспорт |
| Parent/athlete | Кабинеты и финансовое чтение вне MVP; GuardianLink сам не даёт доступа к этому API | Вне первого выпуска |
| Network owner/platform admin | Не выводить права из непринятого #27/PR111; будущая статистика — только после принятия явного grant и отдельного финансового scope | Не расширяется этим документом |

Каждый запрос проверяет выбранный tenant и текущий grant, не доверяет tenant из ссылки/импорта. Составные FK/RLS обязательны в будущих таблицах; одна роль в другом клубе, семья или имя плательщика не дают доступа. При dual role применяются реально действующие финансовые права, не произвольный client role. Архивный профиль не восстанавливает старый телефон в отчёте.

Предлагаемый MVP-экспорт: синхронный CSV UTF-8 с фиксированными колонками выбранного отчёта, до **10 000 строк, 5 MiB и 10 секунд**, лимит периода 12 месяцев; значения — технические предложения для измерения, не подтверждённые договорные лимиты. При превышении — понятная ошибка/сужение фильтра, без молчаливого обрезания/тяжёлого job. Агрегаты и строки принадлежат одному DB snapshot; пагинация экрана не ограничивает итог. Money экспортируется в целых копейках с currency, экран формирует BYN точно; имя/идентификатор ребёнка только где нужны для отчёта.

По умолчанию нет сырых ProviderInput, подписи/ключей, payer address/телефона, GuardianLink/контактов, болезни по именам или причин с PII. Дополнительная выгрузка сырья не часть отчёта, требует отдельно принятого доступа/основания. CSV quoting и нейтрализация начальных `= + - @`/tab/CR/LF в текстовых ячейках обязательны; числа не преобразуются в формулы. Ограничения проверяются и до сериализации и при записи байтов.

Сессия/scope проверяются до построения и непосредственно перед выдачей снимка, отзыв сериализуется с выдачей по access-контракту. Отозванный доступ не возвращает старый cached export/OperationResult с PII. HTTPS, `Cache-Control: no-store`, отсутствие публичных download URLs/browser storage; имя файла без PII. Скачанный пользователем файл нельзя отозвать технически — интерфейс предупреждает об области/чувствительности. Audit экспорта хранит авторство, report/version, фильтры без текстового поиска/PII, as_of/число строк/итог/результат, не сам CSV.

## Предложенные экраны и ошибки

Mobile-first, реализация UI здесь отсутствует; apps/web не изменяется. Экран показывает подписи и серверный результат, технические ID скрыты из основного потока.

- «Рекомендация»: месяц, ребёнок/семейный снимок, исходная/уменьшенная сумма, история. Надпись «разница с рекомендацией», без «долг» и блокировки допуска.
- «Поступления»: дата события, исходная сумма, возвраты/исправления, распределено и остаток; отдельные статусы подтверждения источника.
- «Распределить»: получатель/месяц/сумма, оставшийся остаток и предпросмотр. Пустое/неоднозначное сопоставление остаётся на разбор.
- «Возврат/исправление»: тип, доказательство, причина, явно выбранные распределения для компенсации и итог до/после. Объяснение, что действие учёта не само отправляет деньги в банк.
- «Импорт»: dry run/число и суммы всех исходов, отдельное подтверждение и результат частичного применения; повтор без дублирования.
- «Отчёты»: обязательные период/дата среза, подпись денежного измерения, разрешённые фильтры, полный итог, отдельная кнопка экспорта/лимиты.

Пусто, запрещено, offline (финансы только онлайн), ошибка источника/строки, конфликт версии и неизвестный исход показаны отдельно. При неизвестном исходе повторяется исходная команда; при conflict ввод сохраняется для сравнения, кнопка не объявляет success. Суммы и статусы различаются текстом, поддерживаются клавиатура/focus; на 320px таблица превращается в краткие строки с раскрытием подробностей.

## Граница поставки и следующей реализации

Новых HTTP операций, общих OpenAPI/DTO, SQL-миграций, provider adapter, финансового backend, Telegram и apps/web в #38 нет. Поэтому текущие api/openapi и применённые миграции сохраняются. Это ограничение нельзя трактовать как реализованный финансовый API. До затронутого wire/SQL нужны согласование owners #27/#28, принятие технического варианта и действующего people/access контракта; реальные форматы — #17.

Проверки этой поставки: точная арифметика синтетических примеров, четыре спецификации/ожидаемые строки, неверный scope/повтор/возврат в документальных сценариях, локальные ссылки/Markdown/diff. Не доказаны DB-блокировки/RLS/runtime-конкуренция, реальный iPay/CSV-export и работа телефона. При реализации S2 обязательны эти проверки на disposable PostgreSQL и настоящем HTTP, включая одновременный расход остатка/возврат, частичный сбой импорта, повторы, отзыв перед выдачей и контрольные суммы источника.
