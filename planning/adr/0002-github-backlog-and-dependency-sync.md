# ADR 0002: задачи срезов и синхронизация GitHub-планирования

Дата: 7 октября 2026 года. **Статус: предложено.** Пользователь подтвердил Issues/milestones/Project #1 и свободный выбор задач; manifest, способ API-синхронизации и правила вычисления готовности — техническое предложение для ревью этого PR. ADR 0001 не заменяется.

## Контекст

План MVP 1.1 задаёт S0–S5 и параллельные ветви, но ещё не содержит конкретной очереди реализации в GitHub. Два разработчика равноправны и не хотят предварительных назначений. Нужны полное покрытие, зависимости и различение синтетической готовности, реальных интеграций и полного MVP. CLI в текущей среде получает Forbidden для REST/GraphQL; коннектор позволяет публиковать Issues/PR, но не управлять milestones/Projects.

## Предложение

Публиковать проверяемые задачи с отдельными контрактами, реализацией и приёмкой; группировать их обзорными Issues и milestones по S0–S5. Будущее развитие — отдельный отложенный milestone с подтверждаемыми триггерами. Конкретные прямые зависимости являются блокировками; обзорный этап не блокирует всё следующее направление. Это сохраняет ранний S2 после модели людей, независимые переносы Telegram и параллельный офлайн после онлайн-журнала.

Хранить номера и граф в planning/ISSUE-BACKLOG.json, а человекочитаемый порядок и правила в ISSUE-BACKLOG.md. Состояние работы/assignees/обсуждения остаются в GitHub; manifest не является вторым журналом статусов. Изменение графа согласуется через Issue/PR вместе с обновлением источника плана, если затронуты его правила.

Скрипт scripts/sync-github-planning.py сначала проверяет доступ чтением. По умолчанию не меняет GitHub; явный --apply создаёт недостающие milestones, назначает их, добавляет native blocked-by/sub-issues, размещает Issues в существующем Project #1 и вычисляет исходную готовность. Существующие In progress/Review сохраняются; сроки и assignees не меняются. Изменение заполненного Status не выполняется автоматически, чтобы не потерять чужие значения. Граф проверяется локально на отсутствующие зависимости и циклы.

Начальные Ready — задачи сбора/согласования S0 без программных зависимостей. Остальные остаются Backlog до принятых результатов зависимостей; not planned/duplicate не удовлетворяет зависимость. Реальные внешние условия/триггеры по-прежнему требуют решения человека. Review и старт работы отражаются командой; настройки автоматизаций проверяются в UI, а не объявляются работающими по наличию Projects.

## Альтернативы и последствия

Линейное выполнение всех milestones лишает команду разрешённого планом параллелизма. Только текстовый backlog не даёт пользователю видимости в GitHub Projects; только доска без документов затрудняет проверку полноты и восстановление контекста. Универсальный инструмент project management здесь не нужен: узкий manifest и скрипт обслуживают данный план.

Появляется необходимость согласовывать изменение графа и повторять синхронизацию при разблокировании задач. Частично применённые API-операции остаются видимыми; повторный запуск добавляет недостающее без повторных Issues. Удаление устаревших связей требует отдельного согласования. Применение API пока не проверено из-за доступа; нельзя закрывать настройку как выполненную до read-back milestones, связей и состава/статусов Project. Результаты текущей передачи — Issue #8 и документационный PR.
