# ADR 0008: транзакционная изоляция и синтетический аудит

Дата: 7 октября 2026 года. Статус: **предложено для ревью**. Issue: [#20](https://github.com/StarMadeGalaxy/JudeOS/issues/20). Основание — архитектура §5 и модель данных; приёмка #19 и резервирование #20 — DECISIONS U2026-10-07-S0-02 / S0-20-CLAIM. Это технический выбор для синтетической основы, не новые требования пользователя или права на реальные данные.

## Контекст

Каркас #19 подключал API и migrator к локальному администратору PostgreSQL. Его две таблицы development — fixtures; auth и предметный журнал отсутствуют. RLS не защищает владельца без FORCE и суперпользователя. Одного tenant-фильтра мало: PostgreSQL проверяет FK вне RLS, а session-level SET может оставить чужой контекст следующему запросу пула.

## Выбор

Явный `bootstrap-local` с локальной административной credential создаёт три технические роли: `judeos_migrator` (LOGIN, владелец схемы/таблиц), `judeos_runtime` (LOGIN, без владения/DDL/чтения аудита), `judeos_audit_reader` (NOLOGIN, только чтение tenant-аудита). Все без SUPERUSER, BYPASSRLS, CREATEDB, CREATEROLE и наследования членств. Bootstrap проверяет существующие роли, не переопределяет их пароли и не выдаёт членства. Административная credential отсутствует в API; migrator тоже использует отдельную credential. Bootstrap предназначен только для отдельного локального синтетического кластера: роли PostgreSQL глобальны для кластера. Production provision/backup — отдельные задачи.

Миграция 00003 создаёт `core.clubs` с `tenant_id` как ID самого клуба и переносит все прежние fixtures (включая нештатные строки) до включения RLS. Прежняя development.sample_clubs сохраняется для совместимости upgrade, доступ runtime к ней не выдаётся. `development.sample_objects` — синтетическая иерархия с ключом `(tenant_id,id)`, ссылкой на клуб и FK `(tenant_id,parent_id)` к объекту того же клуба. Это проверяемый образец ограничения, не предметные Account/Person/Athlete или будущая схема журнала. Новые предметные миграции появятся в своих задачах.

На clubs, sample_objects и audit_events включены ENABLE/FORCE RLS с USING/WITH CHECK. `core.current_tenant()` требует локальный tenant и выдаёт нейтральную ошибку при его отсутствии. SQL-проверка выполняется при обращении к строкам: пустая выборка сама по себе не гарантирует вызов policy. Поэтому application boundary всегда заранее проверяет полный контекст. Runtime читает Club и выполняет CRUD только синтетических объектов; никаких продуктовых ролей/прав сотрудников здесь нет.

`database.WithinTenant` проверяет tenant/actor UUID и серверный request_id, открывает короткую транзакцию, параметризованным set_config(..., true) устанавливает tenant/actor/request на её соединении, передаёт только tx репозиторию и делает commit/rollback. Ошибка, panic и отмена тоже приводят к rollback; контекст исчезает до повторного использования соединения. Сервер должен разрешить tenant и actor по актуальным правам до вызова; заголовок/URL/body не являются разрешением. Auth реализуется в #21. RLS не защищает от произвольного SQL с полномочиями runtime и не заменяет объектный scope.

Триггеры значимых INSERT/UPDATE/DELETE клуба и синтетического объекта атомарно записывают tenant, actor, серверный request_id, действие, тип/ID объекта и время. Неизменившийся UPDATE не добавляет событие. Имена, label, контакты, SQL, payload и произвольные before/after не сохраняются. Перенос старых fixtures не выдумывает прежних авторов/событий; seed имеет явно синтетического actor/request. SECURITY DEFINER имеет фиксированный search_path, whitelist таблиц и закрытый EXECUTE; он пишет только через триггер, учитывая FORCE RLS. Runtime не может читать, добавлять, менять/удалять аудит, отключать триггер/RLS или TRUNCATE. Чтение — только отдельная техническая capability audit_reader с тем же tenant-контекстом, не автоматически администратор/менеджер продукта; никакой LOGIN ей не назначен.

HTTP генерирует request_id независимо от клиентских заголовков, кладёт его в context и X-Request-ID/ошибку. Это тот ID, который будущая application service передаст в TenantContext. Логи содержат только серверный ID, зарегистрированный pattern маршрута, status/duration и безопасный code при panic; входные URL/query/header/body, произвольный method, ошибка драйвера и panic value не логируются. Ошибки транзакционного слоя сохраняют только нейтральные категории denied/constraint/database и cancellation, без SQLSTATE/detail/constraint/value в публичном тексте. Предметный HTTP-маппинг категорий добавится вместе с endpoint'ами; он не выдаёт existence чужого объекта.

## Доступ и хранение аудита

В синтетическом контуре события живут только в disposable БД/томе до явного сброса среды; тестовые БД check-db удаляются после проверки. TTL/автоматическое удаление не включено. Это временный технический режим, а не согласованный числовой срок для реальных данных. До реального пилота #18/#24 должны определить основание, классы/сроки хранения и удаления, продуктовые права чтения/экспорта, ответственного, копии и восстановление. Отсутствующие решения остаются блокером реальных данных. Migration/admin являются доверенными техническими операторами; аудит не объявляется защитой от администратора БД или tamper-proof журналом.

## Альтернативы и последствия

Session-level SET отвергнут из-за риска пула; только приложение без RLS/FK не даёт второй границы. Глобальная роль runtime с BYPASSRLS для bootstrap отвергнута. Пустые предметные таблицы ради проверки FK не создаются. Универсальный JSONB before/after раскрывал бы лишние поля; расширять аудит нужно whitelist конкретной команды в её задаче.

У каждой будущей таблицы нужны явные RLS/FK/grants/audit и негативная проверка; default grants runtime отсутствуют. Обёртка не гарантирует безопасность запросов, выполненных вне переданного tx. API readiness проверяет версию схемы и безопасную роль runtime, но не доказывает готовность всех предметных политик/маршрутов. Seed повторяемый, по одному tenant-транзакционному шагу на клуб, без повторных событий при отсутствии изменений. Совместимый откат приложения/backup и реальный HTTPS проверяются отдельно в #22/#24; CLI миграций по-прежнему только up.

## Проверка

`make check-db` использует реальный PostgreSQL 18.3 и отдельные LOGIN-соединения. В disposable БД воспроизводит ownership/upgrade #19→00003, сохранение существующей строки, повтор bootstrap/migrate/seed, runtime readiness и запрет privileged API. Проверяет чужую запись/FK/смену tenant, чтение/изменение чужих строк, отсутствие контекста, DDL/TRUNCATE/SET ROLE/доступ к старым fixtures и аудит, атомарные события/rollback, очистку соединения после commit/error/panic/cancel и конкуренцию двух клубов на одном соединении. HTTP-тест проверяет нейтральный panic/ошибку, серверную корреляцию и отсутствие чувствительного синтетического ввода в логах. Auth, права внутри клуба, бизнес-команды, реальное хранение/восстановление остаются в своих задачах.
